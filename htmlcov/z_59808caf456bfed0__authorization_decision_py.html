1"""The one place an authorization decision is reached. 

2 

3Three callers ask whether a request is permitted, and until this module 

4existed all three answered by calling `evaluate(policy, ...)` themselves: 

5the production gate (`TrustAuthorize`), and the two query slices that 

6answer questions about a named policy (`evaluate_policy`, 

7`list_permissions`). While the gate consults nothing but the Policy the 

8three answers are identical, so the duplication is invisible. It stops 

9being invisible the moment the gate consults anything else: the gate 

10would refuse a request on a window, a lifecycle, or an operation class 

11while the query slices, still evaluating the Policy alone, report the 

12same request as permitted. Nothing in the type system would notice. 

13 

14This module is the seam that makes that divergence impossible rather 

15than merely discouraged. A conjunct is added HERE, once, and every 

16caller's answer moves together or is explicitly, visibly excluded. 

17 

18## Why the context is resolved, never passed 

19 

20The split between `AuthorizationRequest` and `DecisionContext` is the 

21load-bearing rule, not a grouping convenience: 

22 

23 AuthorizationRequest what an enforcement point legitimately knows 

24 and therefore supplies: subject, action, 

25 resource 

26 

27 DecisionContext what the decision point resolves for itself: 

28 the policy, and in time the standing, the 

29 beamtime, the clock, the budgets 

30 

31Letting a caller supply anything in the second group inverts the 

32relationship between enforcement and decision. The concrete failure is 

33already closed elsewhere in this codebase and must not be reopened here: 

34a caller who can name the policy it is judged by can name one that 

35permits it. That is why `TrustAuthorize` binds its policy at 

36construction and why nothing in `AuthorizationRequest` names a policy. 

37 

38## Why two context arms that look identical today 

39 

40`ResolvedContext` and `PolicyOnlyContext` carry the same single field 

41and will read as duplication inviting a merge. The duplication IS the 

42enforcement, in the same way the per-window authority types elsewhere in 

43this bounded context delete a forbidden-field error class by making the 

44field unrepresentable. Merging them into one type with a nullable 

45"resolved" flag returns the decision to a runtime check that a future 

46conjunct can silently skip. 

47 

48The arms exist so that adding a conjunct is a question the author cannot 

49avoid answering. When the window conjunct lands, the `ResolvedContext` 

50arm gains it and the `PolicyOnlyContext` arm must state what it does 

51instead, because a hypothetical about another principal at another time 

52has no window to resolve without either leaking that principal's state 

53or accepting the caller's assertion of it. Both of those are worse than 

54returning a partial answer that says it is partial. 

55 

56## Partiality is a return value, not a convention 

57 

58Every result carries `evaluated`, the set of conjuncts actually 

59consulted. A query slice cannot forget to mark its answer partial, 

60because the same function that answered also reported what it skipped. 

61That is what makes "necessary but not sufficient" checkable at the call 

62site, in a log, and in a test, rather than a caveat in a docstring 

63somebody has to have read. 

64"""

75@dataclass(frozen=True) 

76class AuthorizationRequest: 

77 """The subject, action, and resource an enforcement point supplies. 

78 

79 Everything here is caller-supplied by design. Nothing the decision 

80 point must resolve for itself belongs on this type; see the module 

81 docstring for why that boundary is load-bearing. 

82 """ 

83 

84 principal_id: UUID 

85 command_name: str 

86 conduit_id: UUID 

87 surface_id: UUID = NIL_SENTINEL_ID 

88 

89 

90@dataclass(frozen=True) 

91class ResolvedContext: 

92 """Every input the decision point resolved for the calling principal. 

93 

94 The live request path. A decision reached with this context is the 

95 system's actual answer, and its `evaluated` set names every conjunct 

96 the gate consults. 

97 """ 

98 

99 policy: Policy 

100 

101 

102@dataclass(frozen=True) 

103class PolicyOnlyContext: 

104 """A hypothetical, where only the Policy conjunct is answerable. 

105 

106 Carried by the query slices, which ask about a principal other than 

107 the caller, a policy other than the deployment's configured one, or 

108 both. The decision point cannot resolve the remaining conjuncts for 

109 a subject that is not making the request, so the answer it returns 

110 is necessary and not sufficient, and says so through `evaluated`. 

111 """ 

112 

113 policy: Policy 

114 

115 

116type DecisionContext = ResolvedContext | PolicyOnlyContext 

117 

118 

119def decide_authorization( 

120 request: AuthorizationRequest, 

121 context: DecisionContext, 

122) -> AuthzResult: 

123 """Reach the authorization decision for `request` under `context`. 

124 

125 Returns `Allow` or `Deny`, each stamped with the conjuncts it 

126 consulted. The two context arms currently reach the same answer 

127 because the Policy is the only conjunct that exists; they are kept 

128 apart so that the next conjunct cannot be added to the live path 

129 without a decision about the hypothetical one. 

130 """ 

131 match context: 

132 case ResolvedContext(): 

133 return evaluate( 

134 context.policy, 

135 principal_id=request.principal_id, 

136 command_name=request.command_name, 

137 conduit_id=request.conduit_id, 

138 surface_id=request.surface_id, 

139 ) 

140 case PolicyOnlyContext(): 

141 return evaluate( 

142 context.policy, 

143 principal_id=request.principal_id, 

144 command_name=request.command_name, 

145 conduit_id=request.conduit_id, 

146 surface_id=request.surface_id, 

147 ) 

148 case _: # pragma: no cover - exhaustiveness guard 

149 assert_never(context)
