1"""`ClosedValueObject`: marker for a frozen VO the record exporter may 

2KEEP whole rather than resolve field by field. 

3 

4Per `project_record_export_v3.md` F5, the generated redaction 

5disposition table (`tools/gen_record_dispositions.py`) resolves a field 

6by its DECLARED TYPE. A frozen value object normally RECURSES: each of 

7its own fields gets classified in turn, and a bare `str` field inside it 

8drops by the same fail-closed default as everywhere else. That is 

9correct for a VO like `DatasetEncoding`, whose `media_type` is a loose, 

10unvalidated string with no closed range. 

11 

12It is the WRONG answer for a VO whose constructor closes every field's 

13range completely: a hex digest is a fixed-length, fixed-charset string, 

14and a checksum algorithm tag is drawn from a short closed set. Neither 

15can carry free text, so dropping them is not caution, it is the specific 

16defect this marker exists to fix: the record's own checksum, dropped by 

17the same rule that correctly protects an operator's free-text comment. 

18 

19Subclass `ClosedValueObject` ONLY when EVERY field of the VO is closed 

20by construction: a fixed-length charset check (a hex digest), a closed 

21literal set, a bounded number, another `ClosedValueObject`. If any field 

22could carry unconstrained text (a name, a free-form reason, a URI), do 

23not use this marker; let the field recurse and drop like any other. 

24 

25The generator checks this marker BEFORE recursing into a value object's 

26fields (see `_classify` in `tools/gen_record_dispositions.py`) and, when 

27it matches, emits `keep:closed:<ClassName>` for the whole VO. At 

28export time this keeps the VO's rendered form (already a dict of JSON 

29primitives) verbatim, exactly like any other `keep:*` disposition. 

30 

31This is a marker only: it adds no fields, no methods, and no runtime 

32behavior. It exists purely so a build-time tool can ask a type object 

33"does this VO close its own range?" without hand-maintaining a list of 

34class names to keep. 

35 

36Nothing checks the claim mechanically. Whether a subclass truly closes 

37every field is enforced today by code review at subclass-creation time 

38plus review of the generated table's diff, not by a fitness test: 

39`DatasetChecksum`, the only subclass as of this writing, is covered by 

40direct unit tests of its own `__post_init__` rejection paths (see 

41`tests/unit/data/test_dataset.py`), which is a proportionate check for 

42one instance. Rule of three: once a SECOND subclass exists, add a 

43fitness test that enumerates every `ClosedValueObject` subclass and 

44verifies each field's own validation actually closes it (a property 

45test over arbitrary strings/numbers is one way), rather than trusting 

46the marker and this docstring indefinitely. 

47"""
