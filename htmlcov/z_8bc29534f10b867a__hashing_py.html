1"""Hash an exported record with `cora.shared.content_hash`, no exclusions. 

2 

3Per `project_record_export_v3.md` F6: one canonicalization, `content_hash`'s 

4profile, for both serialization and hashing. `canonical_json` (used 

5elsewhere in the codebase) is a DIFFERENT recipe; mixing the two means the 

6committed file is not the bytes the hash covers. `cora.shared` is exactly 

7what `tach.toml` allows `cora.infrastructure` to depend on, so this import 

8is the dependency the layering rule exists to permit. 

9 

10No exclusions: every rendered stream row and every rendered logbook row 

11goes into the hashed body. Re-exporting the same database twice is 

12measured stable (`test_hashing.py`'s integration test); a regenerated 

13record hashing differently across genuinely different content is content 

14addressing working, not a defect, and cross-record comparison is the 

15shape layer's job, not this module's. 

16 

17Payload types follow the scheme 

18`application/vnd.cora.<event-type>+json` (`content_hash.py`'s own 

19convention) and the three names `project_record_export_v3.md`'s "Naming" 

20section already picked: `record`, `record-streams`, `record-logbooks`. 

21That section calls `record+json` the manifest's type; nothing writes a 

22manifest yet (step 4), so there is no live collision today. Used here for 

23the whole-bundle hash because `{streams, logbooks}` together *is* the 

24record the manifest will describe -- if step 4 wants manifest.json to 

25carry its own distinct wrapping type when it starts writing bytes to 

26disk, that is a decision for whoever builds it, made with an actual 

27manifest body in hand rather than guessed at here. 

28"""

54class TwoTierRecord(Protocol): 

55 """The shape both `ExportedRecord` and `RedactedRecord` share. 

56 

57 Structural, not a base class, so `_hashing` can hash a redacted 

58 record without importing `_redaction` (which imports this module: 

59 the dependency runs one way only). 

60 """ 

61 

62 @property 

63 def streams(self) -> tuple[dict[str, object], ...]: ... 

64 

65 @property 

66 def logbooks(self) -> dict[str, tuple[dict[str, object], ...]]: ... 

67 

68 

69def _two_tier_body(record: TwoTierRecord) -> dict[str, object]: 

70 """The hashed body shape shared by H1 and H3, so the two can never 

71 disagree about what "the whole bundle" means.""" 

72 return { 

73 "streams": list(record.streams), 

74 "logbooks": {kind: list(rows) for kind, rows in record.logbooks.items()}, 

75 } 

76 

77 

78def hash_streams(streams: tuple[dict[str, object], ...]) -> str: 

79 """SHA-256 content hash over the streams tier alone, in its own order.""" 

80 return compute_content_hash(STREAMS_PAYLOAD_TYPE, list(streams)) 

81 

82 

83def hash_logbooks(logbooks: dict[str, tuple[dict[str, object], ...]]) -> str: 

84 """SHA-256 content hash over the logbooks tier alone. 

85 

86 Kind keys are NFC-normalized and sort themselves via 

87 `json.dumps(sort_keys=True)`; each kind's row order is preserved 

88 (the registry's own order-by), never re-sorted. 

89 """ 

90 body = {kind: list(rows) for kind, rows in logbooks.items()} 

91 return compute_content_hash(LOGBOOKS_PAYLOAD_TYPE, body) 

92 

93 

94def hash_record(record: TwoTierRecord) -> str: 

95 """SHA-256 content hash over the whole bundle, both tiers, no exclusions. 

96 

97 This is THE record hash (H1): per F2, it covers everything 

98 `export_record` produced. Re-running the export against an unchanged 

99 database reproduces this value exactly; any single differing byte 

100 anywhere in either tier changes it. 

101 

102 Takes the structural `TwoTierRecord`, not `ExportedRecord` by name, 

103 so `_bundle.write_bundle`'s binding check can call this on whatever 

104 it was actually handed and compare against what a manifest claims, 

105 without needing to know which concrete type that is. 

106 """ 

107 return compute_content_hash(RECORD_PAYLOAD_TYPE, _two_tier_body(record)) 

108 

109 

110def hash_redacted_record(record: TwoTierRecord) -> str: 

111 """SHA-256 content hash over the PUBLISHED record: H3. 

112 

113 The third of `project_record_export_v3.md` F5's three hashes (full 

114 record H1, redaction profile H2, published record H3), and the one 

115 the paper actually prints beside its locator, because it is the only 

116 one covering the bytes a reader can hold. 

117 

118 The payload type is deliberately distinct from 

119 `RECORD_PAYLOAD_TYPE`. `compute_content_hash` binds the payload type 

120 into the DSSE-PAE preamble, so an unredacted and a redacted record 

121 that happened to reduce to identical bodies still hash differently. 

122 That matters: without it, an export whose redaction dropped nothing 

123 (every field already publishable) would produce H1 == H3, and a 

124 reader could not tell a published record from a full one by its hash 

125 alone. They must never collide. 

126 

127 Takes the structural `TwoTierRecord` rather than `RedactedRecord` 

128 only because importing `_redaction` here would invert this module's 

129 dependency; callers pass `RedactionResult.redacted_record`. Passing 

130 an unredacted `ExportedRecord` alongside a manifest whose 

131 `published_record_hash` was computed from the real redacted record 

132 is a caller error this function's signature cannot catch by itself 

133 -- `write_bundle` is what catches it, by recomputing this same hash 

134 over whatever record it was actually handed and refusing on 

135 disagreement (`ManifestRecordMismatchError`) before writing a single 

136 byte. 

137 """ 

138 return compute_content_hash(PUBLISHED_RECORD_PAYLOAD_TYPE, _two_tier_body(record))

141def hash_registered_kinds(kinds: Iterable[str]) -> str: 

142 """SHA-256 content hash over the sorted registered logbook kind set. 

143 

144 Takes the kind strings directly rather than importing 

145 `_registry.all_specs` here: `_hashing` stays a leaf module hashing 

146 whatever body a caller hands it, the same posture every other 

147 `hash_*` function in this file takes. `_manifest.py` is the caller 

148 that actually reads the registry. 

149 

150 Per `project_record_completeness_design.md`'s "Two authorities, two 

151 times": this is the build-time half. A reader comparing a bundle's 

152 `registered_kinds_hash` against a hash it computes from ITS OWN 

153 checkout's registry can tell whether the universe of kinds this 

154 export was measured against has since grown a tenth member, without 

155 needing to trust the manifest's `extent_by_logbook_kind` keys alone. 

156 """ 

157 return compute_content_hash(REGISTERED_KINDS_PAYLOAD_TYPE, sorted(kinds))

160def hash_redaction_profile() -> str: 

161 """SHA-256 content hash over every table that decides what a 

162 published record discloses: tier 1's generated per-field 

163 `DISPOSITIONS` AND its hand-authored fixed-column dispositions 

164 (`FIXED_KEEP_COLUMNS` / `FIXED_TOKEN_COLUMNS` / `FIXED_DROP_COLUMNS` 

165 in `_redact_tier1.py`, which govern `stream_id`, `principal_id`, 

166 `signature`, and every other `events` column outside `payload`), AND 

167 tier 2's hand-authored `TIER2_DISPOSITIONS` / 

168 `TIER2_JSONB_CLEARED_POINTERS` / `TIER2_JSONB_DROPPED_COLUMNS`. 

169 

170 This IS the redaction profile hash (H2). Step 7's security re-review 

171 found the tier-2 tables missing from this hash and fixed that; this 

172 fixes the same class of gap one seam over. `_redact_tier1.py`'s three 

173 fixed-column tuples decide, unconditionally for every event, whether 

174 `principal_id` tokens or `signature` drops -- editing either was 

175 invisible to `redact_record`'s `expected_redaction_profile_hash` 

176 check, so moving `principal_id` from TOKEN to KEEP, or `signature` 

177 from DROP to KEEP (republishing a signature beside a redacted payload, 

178 the exact confirmation oracle F5's anti-hooks forbid), would not have 

179 moved H2 at all. Every table that decides a disposition must be in 

180 H2, or "the hash matches" does not mean what 

181 `RedactionProfileMismatchError`'s docstring claims it means. 

182 

183 Tuple-keyed dicts (`TIER2_JSONB_CLEARED_POINTERS` / 

184 `TIER2_JSONB_DROPPED_COLUMNS`) are flattened to `"kind/column"` 

185 string keys before hashing rather than relying on 

186 `compute_content_hash`'s `str(key)` fallback for non-string Mapping 

187 keys, which would hash a Python tuple's `repr()` instead of a 

188 reviewable string. 

189 

190 Regenerating tier 1's table via `make record-dispositions` after a 

191 real event-model change, or hand-editing either tier's fixed tables, 

192 is expected to change this value; `test_record_dispositions_drift.py` 

193 guards tier 1's generator output specifically, and 

194 `test_redact_tier2.py`'s live-schema drift test guards tier 2's 

195 column coverage, but only THIS hash is what a caller's 

196 `expected_redaction_profile_hash` actually pins. 

197 """ 

198 body = { 

199 "tier1": DISPOSITIONS, 

200 "tier1_fixed_keep_columns": sorted(FIXED_KEEP_COLUMNS), 

201 "tier1_fixed_token_columns": sorted(FIXED_TOKEN_COLUMNS), 

202 "tier1_fixed_drop_columns": sorted(FIXED_DROP_COLUMNS), 

203 "tier2_dispositions": TIER2_DISPOSITIONS, 

204 "tier2_jsonb_cleared_pointers": { 

205 f"{kind}/{column}": sorted(pointers) 

206 for (kind, column), pointers in TIER2_JSONB_CLEARED_POINTERS.items() 

207 }, 

208 "tier2_jsonb_dropped_columns": sorted( 

209 f"{kind}/{column}" for kind, column in TIER2_JSONB_DROPPED_COLUMNS 

210 ), 

211 } 

212 return compute_content_hash(REDACTION_PROFILE_PAYLOAD_TYPE, body)
