1"""Projection + Reaction Protocols, both satisfying the internal Subscriber primitive. 

2 

3Two public kinds of Subscriber: 

4 

5 - `Projection`: read-side fold of an event stream into a queryable 

6 `proj_*` table. Fast (sub-millisecond apply), batches large 

7 (`batch_size=100` default), idempotent at the SQL layer 

8 (`ON CONFLICT`). Failure mode: stale read model until next poll. 

9 

10 - `Reaction`: side-effecting consumer that produces NEW events 

11 (often cross-BC) or calls the outside world (LLMs, storage, 

12 signers). Slow (LLM-bounded, 5-15 s apply), batches small 

13 (`batch_size=1` recommended), idempotent via deterministic 

14 UUIDv5 stream ids + `expected_version=0` + `ConcurrencyError`- 

15 as-no-op. Failure mode: wedged bookmark on poison event; 

16 recoverable via the `dismiss_event_in_reaction` operator slice. 

17 

18`Subscriber` is the framework-internal primitive the worker advances 

19along the event stream; both Projection and Reaction satisfy it via 

20structural typing. The worker iterates Subscribers without caring 

21which kind they are; per-subscriber `batch_size` lets each kind tune 

22its own throughput vs latency tradeoff. 

23 

24The Protocols are structurally identical today (same field set, same 

25callable shape). The split is operational, not type-theoretic: it 

26documents the two distinct failure-and-tuning regimes a BC author is 

27opting into. 

28"""

49@runtime_checkable 

50class Subscriber(Protocol): 

51 """Internal framework primitive: anything the projection worker 

52 advances along the event stream via a bookmark. 

53 

54 Not exported publicly as a vocabulary BC authors write against; 

55 they write Projections or Reactions. Both satisfy this Protocol 

56 via structural typing. 

57 

58 `name`, `subscribed_event_types`, and `batch_size` are declared 

59 as plain attrs (not ClassVar) so test fixtures can construct 

60 varying instances inline. Production subscribers typically 

61 declare them as class-level constants since they're immutable 

62 per subscriber — that satisfies this Protocol via structural 

63 typing. 

64 

65 `batch_size` is intentionally NOT on the Subscriber Protocol so 

66 the 14 existing Projections that pre-date the per-subscriber knob 

67 continue to satisfy the contract without a sweeping update. The 

68 worker reads `getattr(subscriber, "batch_size", DEFAULT_BATCH_SIZE)` 

69 so a Subscriber that omits the attribute inherits the default 

70 transparently. The Reaction Protocol DOES require `batch_size` 

71 because Reactions must opt into the slow-batch-1 regime explicitly. 

72 """

84@runtime_checkable 

85class Projection(Protocol): 

86 """Read-side fold of an event stream into a queryable `proj_*` table. 

87 

88 A BC's projection lives at `cora.<bc>.projections.<name>` and is 

89 registered via `register_<bc>_projections(registry, deps)`. The 

90 framework owns advance, bookmarking, and at-least-once delivery; 

91 the projection owns the `apply` logic and the schema of its 

92 `proj_<bc>_<name>` table. 

93 

94 Contract: 

95 

96 - `name` MUST match the projection's `proj_*` table name AND 

97 the bookmark row inserted in the projection's migration. 

98 This is the key the worker uses to look up the bookmark 

99 (`projection_bookmarks.name = self.name`) and the convention 

100 that lets the arch-fitness test verify the registration ↔ 

101 migration ↔ bookmark all line up. 

102 

103 - `subscribed_event_types` is the set of `event_type` strings the 

104 projection cares about. The advance query pushes the predicate 

105 down to SQL (`event_type = ANY($subscribed)`); events outside 

106 the set are never delivered to `apply`. 

107 

108 - `apply` MUST be idempotent. The framework delivers at-least- 

109 once: under crash-restart between `apply()` and bookmark 

110 update, the next batch will re-deliver the event. Standard 

111 patterns: `INSERT ... ON CONFLICT (key) DO NOTHING/UPDATE`, 

112 UPDATE-to-same-value, or any operation whose net effect is 

113 independent of how many times it runs. The arch-fitness test 

114 scans every projection's `apply` source for an idempotency 

115 marker (an `ON CONFLICT` substring or an explicit 

116 `# idempotent: <reason>` comment). 

117 

118 - `apply` runs INSIDE the worker's advance transaction. The 

119 bookmark advance + the projection writes commit together; 

120 if `apply` raises, the entire batch rolls back and the 

121 bookmark stays at its previous position so the same events 

122 are retried on the next iteration. 

123 

124 - The connection passed to `apply` is the same connection the 

125 worker uses for the advance scan and the bookmark UPDATE. 

126 Don't acquire your own connection from the pool; use the one 

127 you're given. 

128 

129 Operational notes: 

130 

131 - Long-running transactions in the same database PAUSE all 

132 projections (`pg_snapshot_xmin` returns the lowest active 

133 xid8; events from later-started transactions become visible 

134 to projections only after the long transaction commits). By 

135 design — operational mode worth knowing. Avoid `BEGIN;` in 

136 psql sessions while debugging projection lag. 

137 

138 - The advance query orders by `(transaction_id, position)` so 

139 events appear in commit order across streams. Within a single 

140 transaction (one xid8 covering N events), order is by 

141 position. 

142 

143 - Per-projection bookmarks mean projections advance independently 

144 and at their own pace. One projection lagging does not block 

145 others. 

146 

147 - `batch_size` is intentionally NOT in the Projection Protocol. 

148 The worker reads `getattr(projection, "batch_size", DEFAULT_BATCH_SIZE)` 

149 so a Projection that overrides it (e.g., a high-throughput 

150 projection that wants 250) wins, and one that omits it 

151 inherits the default 100 transparently. Reactions, by 

152 contrast, MUST declare `batch_size` because the Reaction 

153 Protocol enforces the opt-in to the slow-apply regime. 

154 """ 

155

172@runtime_checkable 

173class Reaction(Protocol): 

174 """Side-effecting Subscriber: consumes events and produces NEW 

175 events (often into other BCs) or calls the outside world 

176 (LLMs, storage, signing services). 

177 

178 Parallel to `Projection`; both satisfy `Subscriber`. The split 

179 is operational, not type-theoretic: 

180 

181 - Projections are fast (sub-millisecond apply), batch large 

182 (`batch_size=100` default), and idempotent at the SQL layer 

183 (`ON CONFLICT`). Their failure mode is "stale read model 

184 until next poll" and the operator playbook is "wait." 

185 

186 - Reactions are slow (LLM-bounded, 5-15 s apply), batch small 

187 (`batch_size=1` recommended), and idempotent via 

188 deterministic UUIDv5 stream ids + `expected_version=0` + 

189 `ConcurrencyError`-as-no-op. Their failure mode is "wedged 

190 bookmark on poison event" and the operator playbook is the 

191 `dismiss_event_in_reaction` slice. 

192 

193 Contract: 

194 

195 - `batch_size` SHOULD be 1 unless the apply path is provably 

196 fast (no LLM call, no external HTTP, no signer round-trip). 

197 Holding a pool connection across N * 15 s LLM calls 

198 starves Projection advance loops sharing the same pool. 

199 

200 - `apply` MUST achieve at-most-once delivery via deterministic 

201 stream-id derivation. Pattern: derive the side-effect's 

202 stream_id as `uuid5(NAMESPACE_OID, f"{name}:{event.event_id}")` 

203 and call `event_store.append(..., expected_version=0)`; catch 

204 `ConcurrencyError` and treat as success (the side effect was 

205 already applied on a previous attempt). 

206 

207 - `apply` runs INSIDE the worker's advance transaction. The 

208 bookmark advance + any conn-bound writes commit together; if 

209 `apply` raises, the entire batch rolls back and the bookmark 

210 stays at its previous position so the same events are retried 

211 on the next iteration. 

212 

213 - Cross-BC `EventStore.append` calls inside `apply` use a 

214 SEPARATE pool connection from the advance loop's connection. 

215 Cross-TX writes are unavoidable for cross-BC side effects; 

216 the UUIDv5 + ConcurrencyError pattern absorbs the resulting 

217 at-least-once retries. 

218 

219 - The cross-BC append cannot be rolled back if the bookmark 

220 update later fails. Reactions writing to multiple BC streams 

221 in one `apply` accept this asymmetry by design: the side 

222 effect is recorded; the worker re-fires; the second attempt 

223 is absorbed by ConcurrencyError. 

224 

225 Operational notes: 

226 

227 - Wedge recovery: if `apply` raises a non-recoverable error 

228 (poison event, schema drift, deserialization failure), the 

229 bookmark stays put and `consecutive_failures` increments on 

230 each retry. Operator response: invoke the 

231 `dismiss_event_in_reaction` slice to advance the bookmark 

232 past the poison event with an auditable Decision. 

233 

234 - Today every Reaction runs in the same pool as Projections. 

235 Watch-item: when a third Reaction lands OR the first wedge 

236 incident occurs, split off a `ReactionWorker` with its own 

237 pool budget. 

238 """
