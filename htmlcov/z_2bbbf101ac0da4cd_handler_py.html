1"""Projection Protocol + the internal Subscriber primitive it satisfies. 

2 

3`Projection` is the public concept users write per BC. `Subscriber` is 

4the framework-internal primitive the worker advances along the event 

5stream; today every Subscriber is a Projection. Future sagas / external 

6adapters land as additional Protocols satisfying Subscriber, sharing 

7the same advance machinery without duplicating it. 

8 

9The Protocols are structurally identical right now (same field set, 

10same callable shape). The split is intentional: it documents the 

11extensibility seam without surfacing two concepts to BC authors. When 

12a saga framework lands, the worker iterates `Subscriber`-shaped 

13objects regardless of whether they happen to be Projections or Sagas. 

14"""

55@runtime_checkable 

56class Projection(Protocol): 

57 """Read-side fold of an event stream into a queryable `proj_*` table. 

58 

59 A BC's projection lives at `cora.<bc>.projections.<name>` and is 

60 registered via `register_<bc>_projections(registry, deps)`. The 

61 framework owns advance, bookmarking, and at-least-once delivery; 

62 the projection owns the `apply` logic and the schema of its 

63 `proj_<bc>_<name>` table. 

64 

65 Contract: 

66 

67 - `name` MUST match the projection's `proj_*` table name AND 

68 the bookmark row inserted in the projection's migration. 

69 This is the key the worker uses to look up the bookmark 

70 (`projection_bookmarks.name = self.name`) and the convention 

71 that lets the arch-fitness test verify the registration ↔ 

72 migration ↔ bookmark all line up. 

73 

74 - `subscribed_event_types` is the set of `event_type` strings the 

75 projection cares about. The advance query pushes the predicate 

76 down to SQL (`event_type = ANY($subscribed)`); events outside 

77 the set are never delivered to `apply`. 

78 

79 - `apply` MUST be idempotent. The framework delivers at-least- 

80 once: under crash-restart between `apply()` and bookmark 

81 update, the next batch will re-deliver the event. Standard 

82 patterns: `INSERT ... ON CONFLICT (key) DO NOTHING/UPDATE`, 

83 UPDATE-to-same-value, or any operation whose net effect is 

84 independent of how many times it runs. The arch-fitness test 

85 scans every projection's `apply` source for an idempotency 

86 marker (an `ON CONFLICT` substring or an explicit 

87 `# idempotent: <reason>` comment). 

88 

89 - `apply` runs INSIDE the worker's advance transaction. The 

90 bookmark advance + the projection writes commit together; 

91 if `apply` raises, the entire batch rolls back and the 

92 bookmark stays at its previous position so the same events 

93 are retried on the next iteration. 

94 

95 - The connection passed to `apply` is the same connection the 

96 worker uses for the advance scan and the bookmark UPDATE. 

97 Don't acquire your own connection from the pool; use the one 

98 you're given. 

99 

100 Operational notes: 

101 

102 - Long-running transactions in the same database PAUSE all 

103 projections (`pg_snapshot_xmin` returns the lowest active 

104 xid8; events from later-started transactions become visible 

105 to projections only after the long transaction commits). By 

106 design — operational mode worth knowing. Avoid `BEGIN;` in 

107 psql sessions while debugging projection lag. 

108 

109 - The advance query orders by `(transaction_id, position)` so 

110 events appear in commit order across streams. Within a single 

111 transaction (one xid8 covering N events), order is by 

112 position. 

113 

114 - Per-projection bookmarks mean projections advance independently 

115 and at their own pace. One projection lagging does not block 

116 others. 

117 """
