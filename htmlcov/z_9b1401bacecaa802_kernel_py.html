1"""Process-wide dependency kernel. 

2 

3`Kernel` carries the cross-BC primitives (settings, clock, 

4id_generator, authorize, event_store, idempotency_store) plus the 

5asyncpg `pool` (None for `app_env=test`). It's the "Shared Kernel" 

6in the DDD sense: a deliberately-shared set of dependencies every 

7bounded context's `wire_<bc>(deps)` function pulls from. 

8 

9## Why this lives in its own module 

10 

11This module has **zero BC imports**. That's the point: every BC's 

12wire / handler / route imports `Kernel` from here without 

13transitively pulling in any other BC. Phase-8d hardening: the 

14prior `Kernel` (then `SharedDeps`) lived alongside the production- 

15construction logic that lazy-imported `cora.trust` for the 

16authorize factory. That lazy import was tagged `deprecated = true` 

17in tach.toml because tach couldn't tell that the import was 

18control-flow-guarded. Splitting the data class out of the 

19construction module breaks the cycle at the namespace level: 

20`cora.infrastructure.kernel` knows about ports, not adapters, with two 

21deliberate carve-outs: the `canonicalization_registry` and 

22`signing_registry` fields are concrete version-dispatch containers 

23(`CanonicalizationRegistry` / `SigningRegistry`) because version 

24selection needs the registry container, not a single port instance. 

25 

26## BC-specific stores stay BC-internal 

27 

28`Kernel` carries cross-BC primitives only. BC-specific entry 

29stores (Trust BC's `VerdictStore`, Decision BC's `InferenceStore`, 

30etc.) are constructed inside each BC's own `wire_<bc>(deps)` from 

31`deps.pool` and live BC-internal. This keeps the kernel clean as 

32more BCs adopt the logbook-and-entries pattern. 

33"""

78@dataclass(frozen=True) 

79class Kernel: 

80 """Process-wide dependencies. Immutable after construction. 

81 

82 `pool` is the asyncpg connection pool (None when 

83 `app_env=test`). BCs that need additional Postgres-backed 

84 adapters (entry stores, projections, etc.) construct them in 

85 their own `wire_<bc>(deps)` from this pool, keeping BC-specific 

86 stores out of the kernel. 

87 

88 `clearance_lookup`: cross-BC port consumed by 

89 Run BC's `start_run` handler to gate Run.start on the presence 

90 of an Active Safety Clearance covering the Run's scope. Safety 

91 BC ships `PostgresClearanceLookup` as the production adapter 

92 (reads `proj_safety_clearance_summary`). Test environments 

93 default to `AlwaysCoveredClearanceLookup` (synthetic Active 

94 clearance bypass) so existing Run tests don't have to seed 

95 real clearances; gate-specific tests override with the real 

96 adapter explicitly. Mirrors the `Authorize` / `AllowAllAuthorize` 

97 test-default pattern. 

98 

99 `clearance_template_lookup`: cross-aggregate port consumed by 

100 Safety BC's own `version_clearance_template` handler to validate 

101 the supersedes_template_id parent chain stays within one 

102 facility (per the cross-facility identity lock). 9E extends the 

103 consumer set with `register_clearance` / `amend_clearance`. 

104 Safety BC ships `PostgresClearanceTemplateLookup` as the 

105 production adapter (reads `proj_safety_clearance_template_summary`). 

106 Test environments default to `InMemoryClearanceTemplateLookup`; 

107 chain-validation tests seed parent templates via the adapter's 

108 `register(...)` helper. 

109 

110 `caution_lookup`: cross-BC port consumed by Run 

111 BC's `start_run` handler to snapshot operator-authored cautions 

112 onto the `RunStarted` event payload. Caution BC ships 

113 `PostgresCautionLookup` as the production adapter (reads 

114 `proj_caution_summary`). Test environments default to 

115 `AlwaysQuietCautionLookup` (returns `[]`) so existing Run tests 

116 don't have to seed cautions; snapshot-specific tests override 

117 with the real adapter explicitly. NON-BLOCKING by construction 

118 (see `cora.infrastructure.ports.caution_lookup` module 

119 docstring): the snapshot informs the payload but the decider 

120 never gates on it. 

121 

122 `capability_lookup`: cross-BC port consumed by Equipment BC's 

123 `get_asset_integration_view` handler to fetch the set of 

124 Recipe Capabilities whose `required_affordances` are covered 

125 by an Asset's combined Family affordances. Recipe BC ships 

126 `PostgresCapabilityLookup` as the production adapter (reads 

127 `proj_recipe_capability_summary`). Test environments default 

128 to `AlwaysEmptyCapabilityLookup` (returns `[]`) so existing 

129 Equipment tests do not have to seed Capability projection 

130 rows; surface-specific tests override with a fake that returns 

131 seeded references or with the real adapter explicitly. The 

132 port preserves Family's vocabulary discipline ("Capability" 

133 stays a Recipe word) by isolating the Recipe reference type 

134 behind a Protocol the handler maps onto the local 

135 `CapabilityView` response shape. 

136 

137 `supply_lookup`: cross-BC port consumed by Run BC's `start_run` 

138 handler and Operation BC's `start_procedure` handler to gate 

139 start on Method.needed_supplies satisfaction (at least one 

140 AVAILABLE Supply per required kind). Supply BC ships 

141 `PostgresSupplyLookup` as the production adapter (reads 

142 `proj_supply_summary`, excludes Decommissioned rows per the 

143 partial UNIQUE INDEX semantics in 

144 [[project_deregister_supply_design]]). Test environments default 

145 to `AllSatisfiedSupplyLookup` (synthetic Available per kind) so 

146 existing Run / Procedure tests don't have to seed real Supplies; 

147 gate-specific tests override with the real adapter or with 

148 `NoSuppliesRegisteredLookup` for the missing-kind path. Mirrors 

149 the `ClearanceLookup` / `CautionLookup` test-default pattern. 

150 See [[project_supply_preflight_gate_design]]. 

151 

152 `credential_lookup`: cross-BC port consumed by Federation BC's 

153 seal handlers (`initialize_seal`, `rotate_seal_online_key`) to 

154 validate cross-aggregate purpose binding (the referenced 

155 Credential's purpose must match the seal slot: 

156 `SealOnlineSigning` for `online_credential_id`, `SealOfflineRoot` for 

157 `offline_credential_id`) and the status-Active invariant (Rotating or 

158 Revoked secrets cannot back a Seal). Federation BC ships 

159 `PostgresCredentialLookup` as the production adapter (reads 

160 `proj_federation_credential_summary` keyed by `credential_id`). 

161 Test environments default to `InMemoryCredentialLookup`; seal 

162 handler / decider tests seed credentials explicitly via the 

163 adapter's `register(...)` helper. The handler does the async 

164 lookup and threads the result through to the decider as part of 

165 the slice's context dataclass, keeping the decider pure (mirrors 

166 the start_run -> ClearanceLookup pattern). 

167 

168 `facility_lookup`: cross-aggregate port consumed by Federation BC's 

169 `register_facility` handler to validate parent.kind=Site at 

170 cross-stream boundary (per [[project-slice6-design]] L2; closes the 

171 Slice 5 deferral). Future Slice 6 Sub-Slice B consumers 

172 (`add_facility_trust_anchor_credential` decider) will also consume 

173 this port. Federation BC ships `PostgresFacilityLookup` as the 

174 production adapter (reads `proj_federation_facility_summary` shipped 

175 Slice 5 Sub-Slice B, keyed by `facility_id`). Test environments 

176 default to `InMemoryFacilityLookup`; register_facility handler / 

177 decider tests seed facilities explicitly via the adapter's 

178 `register(...)` helper. Mirrors the credential_lookup pattern: the 

179 handler does the async lookup and threads the result through to the 

180 decider as the slice's parent-lookup parameter, keeping the decider 

181 pure. 

182 

183 `asset_lookup`: cross-aggregate port consumed by cross-BC 

184 consumers that hold an `AssetId` from the wire and need to 

185 validate the Asset exists before committing a command. First 

186 consumer is Supply BC's `register_supply` handler (Session 5 

187 Slice 7B): it resolves `command.containing_asset_id` to an 

188 `AssetLookupResult` and threads the result into the decider. 

189 Future Slice 8 (Asset.facility_id back-binding) and potential 

190 Safety / Caution BC consumers will also consume this port. 

191 Equipment BC ships `PostgresAssetLookup` as the production 

192 adapter (reads `proj_equipment_asset_summary` shipped Phase 

193 8e-3a). Test environments default to `InMemoryAssetLookup`; 

194 cross-BC binding tests seed assets via the adapter's 

195 `register(...)` helper. 

196 

197 `family_lookup`: cross-aggregate port consumed by Layer-3 sub-slice 

198 3D's `bind_plan_role` handler (per 

199 [[project-role-aggregate-design]] Lock 17). Walks 

200 Asset.family_ids -> FamilyLookup.lookup -> presents_as ∩ 

201 affordance-superset using the ANY-single-family disjunction 

202 semantic. Equipment BC ships `PostgresFamilyLookup` as the 

203 production adapter (reads `proj_equipment_family_summary` with 

204 the Layer-3 sub-slice 3B presents_as + affordances columns). 

205 Test environments default to `InMemoryFamilyLookup`; 3D consumer 

206 tests seed Families via the adapter's `register(...)` helper. 

207 

208 `assembly_lookup`: cross-aggregate port consumed by 3D's 

209 `bind_plan_role` handler for the Assembly satisfaction branch. 

210 When the candidate Asset carries `fixture_id`, the handler 

211 loads the Fixture, then `AssemblyLookup.lookup(fixture.assembly_id)`, 

212 and the decider ORs-in `role_kind in assembly.presents_as` on 

213 top of the Family disjunction (closes the Microscope-Assembly 

214 worked example from the design memo). Equipment BC ships 

215 `PostgresAssemblyLookup` as the production adapter (reads 

216 `proj_equipment_assembly_summary` with the 3C presents_as 

217 column). Test environments default to `InMemoryAssemblyLookup`. 

218 

219 `role_lookup`: cross-aggregate port consumed by Layer-3 sub-slices 

220 of [[project-role-aggregate-design]]. 3B `add_family_presents_as` 

221 decider validates role_id resolves AND that the Family's 

222 Affordances superset Role.required_affordances. 3C 

223 `add_assembly_presents_as` decider validates role_id resolves 

224 (affordance-superset deferred to register_fixture layer). 3D 

225 `bind_plan_role` handler walks Asset.family_ids -> 

226 FamilyLookup.batch_lookup -> RoleLookup.lookup for the role_kind 

227 satisfaction path (Lock 17 ANY-single-family disjunction). 3E 

228 `update_capability_suggested_roles` handler validates every 

229 proposed RoleId resolves (Lock 10 documentation-only event). 

230 Equipment BC ships `PostgresRoleLookup` as the production adapter 

231 (reads `proj_equipment_role_summary` shipped Layer-3 sub-slice 

232 3A). Test environments default to `InMemoryRoleLookup`; consumer 

233 tests seed Roles via the adapter's `register(...)` helper or 

234 leave the registry empty for the missing-role path. 

235 

236 `llm`: optional LLM-chat port consumed by Agent BC subscribers 

237 (RunDebriefer, CautionDrafter). Production wires 

238 `AnthropicLLM` when `Settings.anthropic_api_key` is set; 

239 otherwise this is `None` and subscribers that depend on it must 

240 short-circuit or fail fast at registration time. Tests use 

241 `FakeLLM` (zero network) when an LLM is needed and leave 

242 this `None` otherwise. 

243 

244 `logbook_mirror`: optional mirror to operator-facing logbook 

245 systems (Olog / SciLog / SciCat). No production implementor 

246 yet; the field exists to reserve the wiring slot and let the 

247 RunDebriefer subscriber short-circuit cleanly on `is None`. An 

248 adapter lands when a pilot facility's logbook is wired. 

249 

250 `token_verifier`: process-singleton 

251 `TokenVerifier` (concretely `IdentityProviderRegistry`) built 

252 from `Settings.identity_providers`. `None` when no IdPs are 

253 configured (today's default): the legacy 

254 `X-Principal-Id`-with-`SYSTEM`-fallback path stays in effect. 

255 Non-`None` is the production-edge-auth posture: middleware 

256 extracts `Authorization: Bearer <token>`, verifies via this 

257 port, stores the resulting `VerifiedPrincipal` on the request 

258 state. Typed as the port (not the registry adapter) so the 

259 kernel-construction primitives can stay in 

260 `cora.infrastructure.deps` without `cora.infrastructure.kernel` 

261 importing `cora.infrastructure.auth` (kernel boundary: ports 

262 only, no adapters). 

263 

264 `profile_store`: process-singleton `ProfileStore` for the 

265 `actor_profile` PII vault. Required (not optional) because 

266 BOTH Access BC (`register_actor`) AND Agent BC (`define_agent`) 

267 upsert through it on the genesis path — a missing 

268 profile_store breaks the cross-BC atomic write. Constructed in 

269 `make_*_kernel` as `PostgresProfileStore(pool)` (production) 

270 or `InMemoryProfileStore()` (tests / `app_env=test`). The 

271 Protocol lives in `cora.infrastructure.ports.profile_store`; 

272 adapters in `cora.access.aggregates.actor.profile`. Sibling- 

273 BC instances all read this one field so the in-memory dict is 

274 shared across slices, mirroring how `EventStore` and 

275 `IdempotencyStore` are shared. 

276 """

307 beam_availability_lookup: BeamAvailabilityLookup = field(default_factory=AllBeamOpenLookup) 

308 """Cross-BC port consumed by Run BC's `start_run` and Operation 

309 BC's `start_procedure` to read live beam-availability state (the 

310 front-end + station `BeamBlockingM` shutters and the ACIS FES-permit 

311 composite) at the start instant and gate the start (BEAM-1). 

312 

313 UNIQUE among the cross-BC lookups in carrying a default: every other 

314 lookup reads a projection and is built at Kernel-construction time, 

315 but the production beam adapter (`ControlPortBeamAvailabilityLookup`) 

316 reads LIVE through the Operation BC's `ControlPort`, which is not on 

317 the Kernel and is only materialised during wiring. So the Kernel 

318 defaults to the always-open `AllBeamOpenLookup` stub (preserving the 

319 pre-BEAM-1 no-gate behavior + the test default) and the composition 

320 root overrides it post-construction via `dataclasses.replace` with a 

321 `ControlPortBeamAvailabilityLookup` over the shared ControlPort when 

322 `BEAM_AVAILABILITY_PVS` is configured. Gate-specific tests likewise 

323 `replace` it with a stub returning the reading under test."""
