1"""Recipe aggregate state, status enum, errors, and value objects. 

2 

3`Recipe` is the EXECUTABLE PARAMETERIZED STEP SEQUENCE at the 

4operations layer: a deployment-bound, ordered tuple of templated 

5steps that, once an operator supplies parameter bindings, expands 

6into a flat list of `Step`s the Operation BC Conductor walks. Each 

7Recipe references one `Capability` via `capability_id`; that 

8Capability declares the contract (parameters_schema, required 

9affordances, executor shapes) the Recipe realizes. 

10 

11Per [[project-recipe-aggregate-design]] (the 5th aggregate added to 

12Recipe BC after [[capability-naming-split-lock]]), Recipe sits BESIDE 

13Capability rather than absorbing Method/Plan: Method (technique-class 

14contract) and Plan (Asset-bound binding) keep their roles; Recipe 

15carries the body that previously squatted on `Capability.template_body`. 

16 

17Distinct from siblings: 

18- `Capability` declares the operations-layer contract: code, name, 

19 required affordances, parameters_schema, executor shapes. Slow-changing 

20 namespaced declaration. 

21- `Recipe` (this aggregate) is the deployment-specific executable body: 

22 capability_id + ordered tuple of typed step VOs with embedded 

23 BindingRef sentinels. Iterates faster than Capability. 

24- `Method` is the technique-class contract (the science-side declaration). 

25- `Plan` is the Asset-bound binding (Plan.wires + Plan.default_parameters). 

26 

27Genesis + FSM `Defined -> Versioned -> Deprecated`, matching 

28Capability/Method/Plan/Practice/Family precedent. Slice verbs: 

29`define_recipe`, `version_recipe`, `deprecate_recipe`, `get_recipe`. 

30 

31## Status as enum-in-state, derived-from-event-type-in-evolver 

32 

33`RecipeStatus` is a `StrEnum` so the values would serialize naturally 

34as JSON-friendly strings IF carried in event payloads. Today they 

35aren't: state holds the enum (typed) and the evolver derives status 

36from the event TYPE, same precedent as `CapabilityStatus` / 

37`FamilyStatus` / `MethodStatus`. 

38 

39## Non-emptiness invariant on `steps` 

40 

41A Recipe without steps has no operational meaning (expansion would 

42produce zero work). `Recipe.__post_init__` raises `EmptyRecipeStepsError` 

43when `steps` is empty. The invariant is carried by Recipe construction 

44and re-runs every time the evolver folds a `RecipeDefined` or 

45`RecipeVersioned` event into a `Recipe(...)` call. The retired 

46worktree `TemplateBody` wrapper VO that previously enforced this is 

47not reintroduced; Recipe owns the invariant directly. 

48 

49## Immutable capability_id 

50 

51`Recipe.capability_id` is REQUIRED at define_recipe time and IMMUTABLE 

52across `version_recipe`: re-binding a Recipe to a different Capability 

53is forbidden. Operators wanting a different binding author a new 

54Recipe. Mirrors `Method.capability_id` immutability. 

55 

56## No `description` field 

57 

58Intentional divergence from the Capability mirror. Per anti-hook 17 in 

59[[project-recipe-aggregate-design]]: human annotation belongs on 

60Capability (the contract), not on Recipe (the executable derivative). 

61A Recipe is identified by `capability_id + name`. 

62"""

207@dataclass(frozen=True) 

208class Recipe: 

209 """Aggregate root: a deployment-bound executable step sequence. 

210 

211 `capability_id` is REQUIRED at define time and IMMUTABLE across 

212 versions. Re-binding a Recipe to a different Capability is 

213 forbidden; operators create a new Recipe instead. 

214 

215 `steps` is the ordered tuple of templated `RecipeStep` instances, 

216 each potentially carrying `BindingRef` sentinels resolved against 

217 operator-supplied bindings at expansion time. Replaced wholesale 

218 by `version_recipe`; non-empty enforced in `__post_init__`. 

219 

220 `version` is the operator-supplied label of the most recent 

221 `version_recipe` call (None until first version). State holds the 

222 latest tag; past tags live in the event stream as `RecipeVersioned` 

223 events. `version_tag` carries no UNIQUE constraint; re-tagging is 

224 allowed (re-attestation is a legitimate audit moment per 

225 `version_capability`/`version_method` precedent). Replay determinism 

226 comes from first-match-from-head tag-string lookup via 

227 `load_recipe_at_version`; the earlier `RecipeVersioned` binds the 

228 earlier `RecipeExpansionRecorded` by construction (the later 

229 re-tagging cannot retroactively change which version was pinned). 

230 See [[project-run-procedure-replay-design]] Locks. 

231 

232 `replaced_by_recipe_id`: pointer to a successor Recipe when this 

233 one is deprecated with replacement. None on 

234 Deprecated-without-replacement and on Defined/Versioned. LOINC 

235 `MAP_TO` precedent matching `Capability.replaced_by_capability_id`. 

236 """ 

237 

238 id: UUID 

239 name: RecipeName 

240 capability_id: UUID 

241 steps: tuple[RecipeStep, ...] 

242 status: RecipeStatus = RecipeStatus.DEFINED 

243 version: str | None = None 

244 replaced_by_recipe_id: UUID | None = None

246 def __post_init__(self) -> None: 

247 if not self.steps: 

248 raise EmptyRecipeStepsError
