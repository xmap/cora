1"""Ratification aggregate state, value objects, enum, and domain errors. 

2 

3`Ratification` is the consequence gate's aggregate: the record that a 

4consequential action is awaiting, or has received, a second independent 

5principal's co-signature before it may proceed. It is the "must a second 

6principal co-sign?" member of the governance-gate family, the deontic 

7co-action counterpart to Trust's permission gate (Policy / Authorize). 

8 

9Where it sits 

10------------- 

11A Ratification is requested for a target action (a command against a run or 

12other aggregate) whose declared consequence class requires co-signature. The 

13pending action is parked in the shared reversible hold; a second, independent 

14principal grants or denies the ratification; a grant releases the hold and lets 

15the action proceed. This aggregate owns only the co-signature lifecycle; the 

16consequence-class declaration and the decider gate that consults it are the 

17wiring increment (see the implementation plan), and the hold reuse is the 

18shipped kill-switch. This increment lands the aggregate DORMANT: nothing gates 

19on it yet, so it changes no existing behavior. 

20 

213-state FSM 

22----------- 

23 

24 Requested -> Granted (a different, independent principal co-signs) 

25 Requested -> Denied (a different, independent principal refuses; + reason) 

26 

27`Requested` is genesis; `Granted` and `Denied` are terminal. There is no 

28re-open: a denied action's requester issues a fresh request if warranted, the 

29same strict-not-idempotent stance the sibling FSM aggregates take. 

30 

31Kind-blindness (consequence-gate invariant) 

32------------------------------------------- 

33The co-signature requirement attaches to the action's consequence, never to the 

34actor's kind: a human running a first-of-a-kind irreversible action is held for 

35co-signature identically to an agent. `requested_by` and the granting/denying 

36principal are bare identifiers; no decider in this aggregate reads actor kind. 

37 

38Independence 

39------------ 

40The grant/deny principal must differ from `requested_by`: a principal cannot 

41ratify its own pending action. This is the four-eyes property the gate exists to 

42provide, enforced in the grant/deny deciders and pinned by a unit test. 

43"""

52class RatificationStatus(StrEnum): 

53 """The Ratification's lifecycle state. 

54 

55 Three values, locked day one: 

56 

57 - `Requested` -- genesis; a co-signature is required and not yet given. 

58 The target action is parked in the shared reversible hold. 

59 - `Granted` -- a different, independent principal co-signed; terminal. 

60 The hold on the target action may be released. 

61 - `Denied` -- a different, independent principal refused; terminal. 

62 The target action stays held (+ operator-supplied reason). 

63 """ 

64 

65 REQUESTED = "Requested" 

66 GRANTED = "Granted" 

67 DENIED = "Denied"

115class RatificationRequesterCannotSelfRatifyError(Exception):

170@dataclass(frozen=True) 

171class Ratification: 

172 """A co-signature record for a consequential target action. 

173 

174 Slim by design: the aggregate owns the co-signature lifecycle and a 

175 reference to the target action it gates, nothing more. The target's own 

176 state (its hold) lives on the target aggregate; this record only tracks 

177 whether the required second signature is pending, given, or refused. 

178 

179 Fields: 

180 - `id` -- the Ratification stream id. 

181 - `target_action_id` -- opaque identifier of the action being gated 

182 (e.g. the run id whose consequential command is 

183 held). Not existence-checked here per the 

184 cross-BC eventual-consistency stance. 

185 - `command_name` -- the canonical name of the gated command. 

186 - `consequence_class` -- the declared class that triggered the requirement. 

187 - `requested_by` -- bare principal id of the requester (the actor 

188 whose action is held). Independence is checked 

189 against this on grant/deny. 

190 - `status` -- lifecycle state. 

191 - `last_reason` -- operator-supplied reason on deny (None otherwise). 

192 """ 

193 

194 id: UUID 

195 target_action_id: UUID 

196 command_name: str 

197 consequence_class: str 

198 requested_by: UUID 

199 status: RatificationStatus 

200 last_reason: str | None
