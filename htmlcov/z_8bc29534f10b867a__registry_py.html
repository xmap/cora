1"""Registry: logbook ``kind`` -> (table, order key, reader). 

2 

3Per `project_record_export_v3.md` F0/F2 and 

4`project_record_is_two_tier.md`. The exporter walks the event stream and, 

5on each ``<X>LogbookOpened`` envelope, reads the envelope's ``kind`` (a 

6bare ``str``, not a closed enum) and resolves it through this ONE 

7registry to the entries table that holds the fine-grained doing. An 

8unknown ``kind`` refuses loudly rather than being skipped. 

9 

10Nine entries, not six. Six kinds come from an envelope event on the 

11main stream; three tables, `entries_run_feed_heartbeats`, 

12`entries_enclosure_permit_probes`, and `entries_run_capture_probes`, 

13have no envelope at all and are declared here explicitly, with 

14`envelope_class` set to `None`, per `project_record_is_two_tier.md`'s 

15"declare or exclude, in writing" finding. The operator decided at S4 

16(`project_record_completeness_design.md`) that all three are pulled 

17into the published bundle rather than excluded as operational 

18telemetry; `unscoped_reader` below is how S5a/S5b/S5c carried that 

19decision into code. This registry's own job stays the same regardless: 

20make every table reachable and refuse to silently drop any of them. 

21 

22The order key lives per kind because `sampled_at` exists on only four of 

23the nine tables (activity, diagnostic, outcome, observation). The other 

24five order by `event_id` alone: CORA mints it with `UUIDv7Generator`, so 

25it is total and insertion-ordered without a separate timestamp column, 

26and `occurred_at` is never the tiebreak because it ties across a whole 

27append batch (one Clock read per handler call). 

28 

29The six envelope-driven tables are scoped by `logbook_id`, the join 

30column the envelope carries. Heartbeats and probes are not 

31Logbook-and-Entry instances (no `logbook_id` column at all) and are 

32scoped by their owning aggregate's id instead: `run_id` for heartbeats, 

33`enclosure_id` for permit probes. `entries_run_capture_probes` differs 

34from BOTH: a capture code has no backing aggregate at all (see that 

35table's migration header and `run.aggregates.run.capture_probes`'s 

36module docstring), so it scopes on `capture_code`, a deployment-declared 

37string, not a UUID. `EntriesReader`'s scope-id type is widened 

38(`UUID | str`) for exactly this one case; every other spec still passes 

39a `UUID` at runtime, unaffected. 

40 

41`unscoped_reader` (S5, 

42`project_record_completeness_design.md`) is a SEPARATE, optional field 

43rather than a nullable scope argument on `reader`: an unscoped read 

44(`SELECT * FROM <table> ORDER BY ...`, no `WHERE`) is a different 

45operation from a scoped one, and letting a caller pass `None` as a 

46scope id against one of the six envelope specs would silently read the 

47whole table where the exporter meant to read one logbook's slice. 

48`heartbeat` (S5a), `capture_probe` (S5b) and `permit_probe` (S5c) all 

49set it now; every other spec's `reader` and its own call sites are 

50unchanged. Every kind owed its own disclosure review before a bundle 

51could carry it; see each kind's disposition entries in 

52`_redact_tier2.py` and its own slice's commit message for the 

53reasoning, including `permit_probe.status_claimed`'s verdict (S5c). 

54"""

71@dataclass(frozen=True, slots=True) 

72class EntriesTableSpec: 

73 """One registry row: how to read one kind's entries-tier rows. 

74 

75 `envelope_class` names the `*LogbookOpened` class that carries this 

76 kind on the main stream, or `None` for the three tables with no 

77 envelope. `scope_column` is the column `reader` filters on: the 

78 envelope's `logbook_id` for the six logbook-backed kinds, the owning 

79 aggregate's id for `heartbeat`/`permit_probe`, and `capture_code` (a 

80 deployment-declared string, no backing aggregate) for 

81 `capture_probe`. `scope_type` names which of those `reader` expects 

82 (`UUID` for every spec but `capture_probe`, which is `str`) so a 

83 generic caller can self-classify a spec rather than hardcoding an 

84 exclusion list keyed on `kind` (see 

85 `tests/integration/test_record_export_registry_postgres.py`, which 

86 derives its UUID-scoped parametrization from this field). 

87 """ 

88 

89 kind: str 

90 table: str 

91 envelope_class: str | None 

92 scope_column: str 

93 scope_type: type[UUID] | type[str] 

94 order_by: tuple[str, ...] 

95 reader: EntriesReader 

96 count_reader: CountReader 

97 """Unscoped `SELECT count(*) FROM table`: no predicate, no envelope, no 

98 scope column, and no `ORDER BY` (a count has no order to carry). Set on 

99 EVERY spec, unlike `unscoped_reader` below, because independence from 

100 `reader`/`unscoped_reader` is the whole point of this field (S2b, 

101 `project_record_completeness_design.md`'s "The independent count") and 

102 that point applies to a scoped six-envelope kind exactly as much as an 

103 unscoped one. Backs `_export.py`'s 

104 `capture_source_row_count_by_logbook_kind`; see that function's 

105 docstring for what this count can and cannot prove per kind.""" 

106 unscoped_reader: UnscopedEntriesReader | None = None 

107 """Reads every row of `table`, unscoped, when set. `heartbeat` (S5a), 

108 `capture_probe` (S5b) and `permit_probe` (S5c) all set it today; 

109 every six-envelope spec leaves it `None`. See the module docstring."""

123def _make_reader(table: str, scope_column: str, order_by: tuple[str, ...]) -> EntriesReader: 

124 # table, scope_column and order_by are all registry-declared constants 

125 # below, never caller input, so the interpolation cannot carry 

126 # attacker-controlled SQL. 

127 sql = f"SELECT * FROM {table} WHERE {scope_column} = $1 ORDER BY {', '.join(order_by)}" 

128 

129 async def read(conn: asyncpg.Connection, scope_id: UUID | str) -> list[asyncpg.Record]: 

130 return await conn.fetch(sql, scope_id) 

131 

132 return read

135def _make_unscoped_reader(table: str, order_by: tuple[str, ...]) -> UnscopedEntriesReader: 

136 """`SELECT * FROM <table> ORDER BY <order_by>`, no `WHERE`. 

137 

138 `table` and `order_by` are registry-declared constants below, never 

139 caller input, so the interpolation cannot carry attacker-controlled 

140 SQL, matching `_make_reader`'s reasoning. 

141 

142 Unbounded: fetches the whole table in one round trip. DECIDED at S5b 

143 (`capture_probe`, `project_record_completeness_design.md`): one fetch 

144 stays acceptable for now, not because the row count is small (it is 

145 not, and it does not stabilize -- `run.aggregates.run.capture_probes`'s 

146 own docstring documents a per-(capture_code, PV) rate from zero, while 

147 the substrate is reachable and `capture_watch_probe_tick_seconds` is 

148 left at its push-only default, up to roughly 8,640 rows/day/PV while a 

149 code's substrate is fully unreachable, and this repo has no retention 

150 policy on this table at any rate), but because a streaming cursor HERE 

151 alone would not lower the export's peak memory: `export_record` 

152 already holds every row of every kind it reads in one place at once 

153 (`ExportedRecord.logbooks`, a `dict` of tuples), so the rows would 

154 still all end up materialized before a single bundle file is written. 

155 Swapping this call for an `asyncpg` server-side cursor without also 

156 changing how `ExportedRecord` and `_bundle.write_bundle` consume a 

157 kind's rows would move the buffering point, not remove it, and would 

158 claim a memory fix it did not deliver. Trigger for revisiting, per 

159 this design's own already-locked phrasing for the identical risk on 

160 this same table (see the design memo's Watch items): the first export 

161 measured in minutes. The fix at that point is coordinated across this 

162 reader, `ExportedRecord`'s shape, and the bundle writer, not a cursor 

163 swapped in here alone. 

164 

165 RE-EXAMINED at S5c (`permit_probe`, now wired the same way): this is 

166 the largest unscoped table in the tier, `count(*)` reported at 

167 50,085 rows across two enclosures at 21:00 CDT 2026-08-17, growing 

168 on a 60-second probe tick per enclosure -- roughly five times the 

169 9,554 `capture_probe` figure S5a recorded (cbab110f1c) as a 

170 forward-looking note about that table's own eventual disposition; 

171 S5b's own commit (937abe4707) explicitly could NOT re-measure that 

172 figure from its session, so this comparison is against the last 

173 recorded number for that table, not a number S5b itself confirmed. 

174 Still growing without a retention policy. The argument above is 

175 about WHERE the buffering happens, not how many rows fit in it, and 

176 that argument is row-count-independent: it still holds at this 

177 size, because `ExportedRecord` still materializes every kind's rows 

178 in one dict regardless of which kind is largest, so a cursor 

179 swapped in here alone would still just move the same rows to a 

180 different Python object. What DOES scale with row count is 

181 wall-clock and network transfer, neither measured directly this 

182 session (arcturus, the pilot database, was not reachable from this 

183 environment; the count above is the figure this slice was given, 

184 not one this session queried itself). Fifty thousand rows of seven 

185 narrow columns each is not yet the "export measured in minutes" 

186 trigger this design already named as the point to revisit; it is 

187 the closest any unscoped table has come to it so far, which is 

188 worth carrying forward rather than re-deciding silently next time a 

189 table in this tier grows past it. 

190 """ 

191 sql = f"SELECT * FROM {table} ORDER BY {', '.join(order_by)}" 

192 

193 async def read(conn: asyncpg.Connection) -> list[asyncpg.Record]: 

194 return await conn.fetch(sql) 

195 

196 return read

199def _make_count_reader(table: str) -> CountReader: 

200 """`SELECT count(*) FROM <table>`, no `WHERE`, no `ORDER BY`. 

201 

202 `table` is a registry-declared constant below, never caller input, so 

203 the interpolation cannot carry attacker-controlled SQL, matching 

204 `_make_reader`'s and `_make_unscoped_reader`'s reasoning. Deliberately 

205 independent of both: it shares no predicate with `reader` (which 

206 filters on `scope_column`) and is built by its own factory rather than 

207 reusing `_make_unscoped_reader`'s SQL, even though the two coincide in 

208 shape for the three kinds that set `unscoped_reader` -- see 

209 `EntriesTableSpec.count_reader`'s own docstring for why that 

210 coincidence does not make this field redundant there. 

211 """ 

212 sql = f"SELECT count(*) FROM {table}" 

213 

214 async def count(conn: asyncpg.Connection) -> int: 

215 value = await conn.fetchval(sql) 

216 assert value is not None 

217 return int(value) 

218 

219 return count

324def resolve(kind: str) -> EntriesTableSpec: 

325 """Look up `kind`'s table spec. 

326 

327 Raises `UnknownLogbookKindError` rather than returning `None`: an 

328 envelope carrying a kind this registry has never heard of must stop 

329 the export, not be skipped. 

330 """ 

331 try: 

332 return _REGISTRY[kind] 

333 except KeyError: 

334 raise UnknownLogbookKindError(kind) from None
