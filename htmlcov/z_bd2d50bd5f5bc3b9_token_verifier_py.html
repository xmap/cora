1"""TokenVerifier port — edge auth. 

2 

3Validates an inbound `Authorization: Bearer <token>` against a 

4configured identity provider and resolves the calling principal. 

5 

6`TokenVerifier` is the hexagonal port; two adapters implement it: 

7 

8 - `JwtTokenVerifier` — local JWKS-based JWT verify (RFC 9068). 

9 Industry IdPs that issue JWTs (Microsoft Entra, 

10 Google, Auth0, Okta, AWS Cognito, Helmholtz 

11 AAI, ORCID-via-OIDC) plug into this path. 

12 - `IntrospectionTokenVerifier` — RFC 7662 token introspection. Required 

13 for Globus Auth (opaque-by-default) and any 

14 future IdP that doesn't issue JWTs. Also the 

15 revocation-strong path for cases where a 

16 compromised JWT must be invalidated before 

17 its `exp` ticks past. 

18 

19Both adapters return the same `VerifiedPrincipal` shape so the 

20downstream call path (FastAPI middleware → `request.state.principal` 

21→ `get_principal_id` resolver → handler.authorize) is verifier- 

22agnostic. 

23 

24## Adapter selection 

25 

26The `IdentityProviderRegistry` (`cora.infrastructure.auth.idp_registry`) 

27owns the per-issuer adapter mapping at process startup. The HTTP/MCP 

28middleware does NOT make the adapter choice per request — it always 

29asks the registry, which routes by either: 

30 

31 - JWT shape detection (3 dot-separated base64 chunks) + unverified 

32 `iss` claim peek → matching `JwtTokenVerifier`. 

33 - Otherwise → the deployment's configured `IntrospectionTokenVerifier`. 

34 

35## Why a port, not a function 

36 

37Two production adapters today; rule-of-three would trigger an 

38extraction. We're at two because Globus + non-Globus IdPs are 

39operationally distinct paths. Unit tests use a local fake implementing 

40`verify` (see tests/unit/auth/test_bearer_auth_middleware.py), so the 

41port stays testable without an IdP round-trip. 

42The Protocol shape lets the kernel hold a `TokenVerifier` field 

43without leaking which adapter implementation; same architectural 

44move as `Authorize` (AllowAllAuthorize for tests / TrustAuthorize 

45for production). 

46 

47## Errors 

48 

49`InvalidTokenError` (→ HTTP 401 by the route layer) is the 

50catch-all for "the token failed verification" — bad signature, 

51expired, wrong audience, wrong issuer, malformed structure. Carries 

52a short machine-readable `reason` so logs distinguish modes without 

53leaking IdP details to the client. 

54 

55`IntrospectionUnavailableError` (→ HTTP 503) is the introspection- 

56specific failure when the IdP can't be reached or returns 5xx. The 

57JWT path can't raise this (local verify, no network). Distinct from 

58`InvalidTokenError` so operators distinguish "your token is bad" 

59from "our upstream is down." 

60 

61## What is NOT here 

62 

63- The Authorize port stays unchanged — it already takes 

64 `principal_id: UUID`. `TokenVerifier.verify` returns the principal, 

65 Authorize gates the call. 

66- No session / cookie / CSRF concerns — CORA is stateless bearer. 

67- No OAuth client flows — CORA is a Resource Server (RS); the 

68 client obtains the token from the IdP and brings it. WI11 captures 

69 the trigger for revisiting OAuth-client capability. 

70"""

77PrincipalKind = Literal["human", "service_account"] 

78"""Closed StrEnum-style discriminator. Aligned with `Actor.kind` in 

79the Access BC; the three values are `human`, `agent`, and 

80`service_account` (see Decision 9 of the edge-auth design lock)."""

83SubjectMapper = Callable[[str, str], Awaitable[tuple[UUID, PrincipalKind]]] 

84"""Resolve `(issuer, subject)` → `(principal_id, kind)`. 

85 

86The Access BC owns the IdP-subject → Actor.id mapping (the 

87`actor_idp_bindings` projection). Verifiers call this after token 

88verification and surface the result on `VerifiedPrincipal`. 

89 

90Defined here on the port (not on each adapter) so the registry + 

91both adapters import a single canonical alias. 

92 

93Failure modes the adapter wraps: 

94 - Mapper raises (unknown subject, projection lookup error, etc.) → 

95 `InvalidTokenError("unknown_subject", str(exc))`. 

96 - Mapper returns `principal_id == UUID(int=0)` (NIL_SENTINEL_ID) → 

97 `InvalidTokenError("unknown_subject", "subject mapped to nil sentinel")`. 

98 - Mapper returns `kind` not in the `PrincipalKind` closed set → 

99 `InvalidTokenError("malformed", "subject mapper returned invalid kind")`. 

100""" 

101 

102 

103@dataclass(frozen=True) 

104class VerifiedPrincipal: 

105 """The outcome of a successful `TokenVerifier.verify` call. 

106 

107 `principal_id` is the UUID the downstream Authorize port keys on. 

108 Comes from the verifier's mapping of the token's `sub` claim to 

109 a registered `Actor.id` (the IdP-`sub`-to-Actor mapping lives in 

110 the Access BC; the verifier just returns the matched `principal_id`). 

111 

112 `subject` is the raw `sub` claim string from the token, kept for 

113 forensics + structlog. Distinct from `principal_id` because 

114 operators may want to grep logs by IdP subject without joining 

115 against the Actor projection. 

116 

117 `issuer` is the verified `iss` claim — which IdP minted this 

118 token. Forensic + per-IdP rate-limiting / metrics. 

119 

120 `kind` discriminates human vs service-account callers, derived 

121 from the token's claims at issuance time (for example `aud` per-Surface 

122 + `client_credentials` grant → `service_account`). 

123 

124 `scopes` carries the token's OAuth scopes if any (RFC 6749 §3.3). 

125 Empty `frozenset()` is fine — edge-auth ships without scope-aware 

126 authorization (scope→capability mapping is WI6). 

127 """ 

128 

129 principal_id: UUID 

130 subject: str 

131 issuer: str 

132 kind: PrincipalKind 

133 scopes: frozenset[str] = frozenset()

136class InvalidTokenError(Exception): 

137 """The presented token failed verification. 

138 

139 Mapped to HTTP 401 + `WWW-Authenticate: Bearer error="invalid_token"` 

140 (RFC 6750 §3.1) by the route-layer exception handler. The 

141 `reason` short string distinguishes modes for logs without 

142 leaking IdP details to the client response body. 

143 

144 Reason codes (closed set, expand if a new verifier path needs): 

145 - "bad_signature" — JWT signature verify failed 

146 - "expired" — `exp` claim past 

147 - "not_yet_valid" — `nbf` claim future 

148 - "wrong_audience" — `aud` doesn't match expected Surface 

149 - "wrong_issuer" — `iss` not in registered IdPs 

150 - "malformed" — token structure unparseable 

151 - "unknown_subject" — `sub` claim doesn't map to a known Actor 

152 - "introspection_inactive" — RFC 7662 returned `active=false` 

153 - "unsupported_algorithm" — JWT `alg` not in whitelist 

154 """ 

155 

156 def __init__(self, reason: str, detail: str = "") -> None: 

157 super().__init__(f"{reason}: {detail}" if detail else reason) 

158 self.reason = reason 

159 self.detail = detail

162class IntrospectionUnavailableError(Exception): 

163 """The IdP's introspection endpoint couldn't be reached or returned 5xx. 

164 

165 Mapped to HTTP 503 + `Retry-After: 5` by the route-layer exception 

166 handler. Distinct from `InvalidTokenError` so operators can 

167 distinguish "your token is bad" from "our upstream is down" in 

168 logs + dashboards. 

169 

170 Only the `IntrospectionTokenVerifier` adapter raises this; the JWT 

171 path is fully local once the JWKS is cached. 

172 """ 

173 

174 def __init__(self, issuer: str, detail: str = "") -> None:

177 + (f": {detail}" if detail else "") 

178 ) 

179 self.issuer = issuer 

180 self.detail = detail

183class TokenVerifier(Protocol): 

184 """Verify an `Authorization: Bearer <token>` value against a configured IdP. 

185 

186 Implementations: `JwtTokenVerifier` (PyJWT + PyJWKClient), `IntrospectionTokenVerifier` 

187 (httpx + LRU cache); unit tests use a local fake implementing `verify`. 

188 

189 Per Decision 4 of the design lock: `expected_audience` is the 

190 resolved Surface UUID from `get_surface_id` / `get_mcp_surface_id`. 

191 The verifier looks up the configured audience string for that 

192 Surface and asserts `token.aud` matches. RFC 8707 §3 + 

193 RFC 9068 §4 — multi-audience tokens cross trust boundaries, so 

194 each Surface gets its own `aud`. 

195 """
