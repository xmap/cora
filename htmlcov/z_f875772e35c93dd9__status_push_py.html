1"""StatusPush runtime: pushes a live, read-only snapshot outbound to an 

2external relay, for a status page served from a host outside this 

3deployment's own network. 

4 

5## Why this exists, and why it is not a `list_*` consumer over HTTP 

6 

72-BM's deployment runs on a host with no inbound reachability from outside 

8its own controls network (see docs/deployments/2-bm's serving design). A 

9status page that should be viewable from elsewhere therefore cannot be 

10served FROM this host; instead this host must PUSH state OUT to a relay on 

11a host that does have reach, over a connection this host itself opens. That 

12asymmetry, push rather than serve, is the entire reason this module exists 

13alongside the `list_*` REST/MCP surfaces rather than instead of them. 

14 

15## Why this is a bespoke loop, not `_flag_watcher.flag_watcher_lifespan` 

16 

17Every other composition-root watcher in this package (`_calibration_watcher`, 

18`_clearance_watcher`, `_procedure_watcher`, `_campaign_watcher`) does one 

19self-contained unit of work per tick: drain a query, compare against a rule, 

20maybe append one Decision. `flag_watcher_lifespan` is built for exactly that 

21shape. This module instead holds one PERSISTENT outbound connection across 

22many ticks (reopening it every 1-2 seconds would be pure handshake overhead 

23for a live feed), and reconnects with backoff when the relay is unreachable 

24rather than treating each drop as an isolated tick failure. That is closer 

25to `_run_witness.py`'s hand-rolled shape than to the flag-watcher family. 

26 

27## Current scope 

28 

29Each tick reads and pushes: 

30 

31 - open Runs (`Running` + `Held`), each with `progress` from 

32 `RunWitnessRecorder.progress_readings()` and a `progress_trail` from 

33 `progress_trails()` (`{}` when unavailable; see `_render_progress` / 

34 `_render_progress_trail`) 

35 - open Subjects (`Received` / `Mounted` / `Measured` / `Removed`; 

36 `Returned` / `Stored` / `Discarded` are terminal and dropped) 

37 - open Campaigns (`Planned` / `Active` / `Held`; `Closed` / `Abandoned` 

38 are terminal and dropped) 

39 - Datasets produced by an on-screen Run (bounded by the open-run count, 

40 not a separate unbounded drain) 

41 - Active Clearances (the safety-gate status a viewer most wants: is 

42 something required to start a run currently in force) 

43 - Active Enclosures (permit status: the most direct "is it safe right 

44 now" answer CORA records) 

45 - the most recent Decisions since this process started, tail-followed 

46 (see `_DecisionTail`) rather than paged from the beginning, since 

47 Decisions have no "open" status to filter on and the table is 

48 unbounded 

49 - each open Run's full exact-timestamped history (`get_run_history`), 

50 pushed as a SEPARATE message kind on the same socket (see 

51 `_RunHistoryTail`, `build_run_history_message`), refreshed 

52 periodically while open and once more, marked terminal, the instant a 

53 run leaves the open set -- this is REWIND mode's entire feed 

54 - event metadata (`stream_type`, `stream_id`, `event_type`, timestamps 

55 only, NEVER `payload`) tail-followed across the WHOLE `events` table 

56 since this process's own "now" (`_ActivityTail`, 

57 `EventActivityTrail`), pushed as a third message kind whenever 

58 something new has happened -- this is flowing mode's entire feed 

59 - answers, on demand, a relay-originated `run_history_request` for ONE 

60 run's full history (`_read_requests` / `_answer_request` / 

61 `build_run_history_response`), reusing the very same `get_run_history` 

62 read the periodic push above already makes -- this is REWIND's path to 

63 ANY run in the record, not only the up-to-20 most recently pushed one 

64 the relay happens to still be caching 

65 

66The snapshot payload is a full snapshot every push, never a delta: a 

67fresh viewer, a reconnecting viewer, and a restarted relay are all served 

68by "here is the current one". Run-history messages are the opposite: each 

69one is pushed only when genuinely new (a fresh fetch or a terminal 

70checkpoint), never repeated, since `_RunHistoryTail.poll` already tracks 

71what is new itself. 

72 

73Deliberately reads ONLY the in-memory `RunWitnessRecorder` for progress, 

74not the Postgres-durable `entries_run_observations` fallback 

75`PostgresRunChannelLookup` would offer for a run whose capture is not open 

76in this process: that path is capped at `capture_progress_flush_tick_seconds` 

77(10s by default) and never carries `commanded_total` (dropped at the 

78`ObservationInput` boundary), so it would not feel live and would silently 

79lack the "of M" figure. Revisit if this ever runs against a Run witnessed 

80by a different process than the one pushing. 

81 

82## On-demand requests: one reader task, the tick loop stays the sole writer 

83 

84The socket was write-only through Step 1: `sock.send` was called from 

85exactly one coroutine, and nothing ever called `sock.recv`. Answering a 

86relay-originated request needs the socket to read too, and the design 

87below is deliberately conservative about how. 

88 

89`_read_requests` is a single reader task, created inside the same 

90`async with connect(...)` block as the tick loop, that ONLY parses 

91inbound frames onto a bounded inbox (`_REQUEST_INBOX_SIZE`); it never 

92sends and never touches `deps`. The tick loop remains the sole writer 

93AND the sole consumer of that inbox, draining up to 

94`status_push_request_max_per_tick` items per tick via `_serve_requests`, 

95after that tick's snapshot send and before its sleep -- so a slow or 

96misbehaving request delays only the NEXT tick's snapshot, never the 

97current one's, and snapshot cadence never depends on how many requests 

98happen to be waiting. 

99 

100**The one rule that matters more than the others here**: `_answer_request` 

101must never let an exception escape, `UnauthorizedError` most of all. If it 

102did, the exception would propagate out of the tick loop into `_push_loop`'s 

103own `except _UNAUTHORIZED_ERRORS` / `except (ConnectionClosed, ...)` 

104handlers, which exit the `async with connect(...)` block and reopen 

105arcturus's only outbound channel. A browser could then force the 

106beamline's entire live feed to drop and reconnect just by requesting a 

107run it is not allowed to read. `_answer_request` therefore catches 

108`_UNAUTHORIZED_ERRORS` and any other `Exception` itself and turns each 

109into an ordinary `"unauthorized"` / `"error"` response instead. 

110 

111A response is served from `_RunHistoryTail`'s own ring 

112(`_RunHistoryTail.cached_terminal`) when the requested run is already 

113cached there, and ONLY when that entry is marked terminal: a live run's 

114timeline already refreshes every `_RUN_HISTORY_REFRESH_TICKS`, so REWIND 

115on a running scan should never show a stale cached copy. That lookup is 

116read-only by design -- a request-triggered read must never insert into or 

117evict from the ring, whose eviction order otherwise mirrors only what 

118this tail has genuinely pushed. 

119 

120## Principal identity: the widening trigger has now fired 

121 

122Every other watcher here authenticates as its own seeded Agent (a real 

123Actor with its own grant set, so a missing grant is auditable per-agent). 

124This module still uses `SYSTEM_PRINCIPAL_ID` for every read: the read scope 

125has now widened past the single `ListRuns` command this module started 

126with, to EIGHT commands across seven BCs (`GetRunHistory` joins the 

127original seven, still within the Run BC), which is exactly the trigger this 

128docstring named for standing up a dedicated seeded identity (mirroring 

129`agent/seed_calibration_watcher.py`). That identity is NOT built in this 

130change; doing so is a follow-up, tracked so the deferral is visible rather 

131than silently indefinite. Until then, a Trust Policy that denies any of the 

132eight read commands to `SYSTEM_PRINCIPAL_ID` blinds this feature for that 

133domain only (each drain is independently try/except-guarded; see 

134`_push_loop`), never the others. 

135 

136The on-demand request path above makes `GetRunHistory` reachable from a 

137browser at any time, not only on this module's own fixed tick, which is 

138a materially larger claim on `SYSTEM_PRINCIPAL_ID` than the periodic push 

139alone -- it does not add a NINTH command (it is the same `GetRunHistory` 

140call the periodic push already makes, under the same identity, with the 

141same `_UNAUTHORIZED_ERRORS` catch), but it does mean a wider surface can 

142now trigger it on demand. The seeded-identity follow-up named above 

143applies here with more force as a result; it remains deferred rather than 

144bundled into this change, which is scoped to the transport itself. 

145 

146`_ActivityTail`'s read is a NINTH, and it is a different KIND of gap, not 

147just a bigger one: `EventActivityTrail` is a raw infrastructure port, not 

148a `list_*`/`get_*` command handler, so it never calls `deps.authz.authorize` 

149at all. Every other read here can be individually denied by a Trust Policy 

150naming its command; this one cannot be denied at all short of disabling 

151StatusPush entirely. That is acceptable for what it ships (event metadata 

152across every BC, never a value, never PII) but it is a real asymmetry with 

153the eight commands above, not an equivalent case of the same debt -- flagged 

154here so it is a deliberate, visible trade-off rather than something a future 

155reader has to rediscover by reading past the authorize call that is not 

156there.

303async def _drain_all(call: Callable[[str | None], Awaitable[Any]]) -> list[Any]: 

304 """Page through a list_* handler call until `next_cursor` is `None`. 

305 

306 `call` closes over everything but the cursor (the query's other 

307 filters, the handler, the principal), so this stays generic across 

308 every domain's distinct item shape. 

309 """ 

310 items: list[Any] = [] 

311 cursor: str | None = None 

312 while True: 

313 page = await call(cursor) 

314 items.extend(page.items) 

315 if page.next_cursor is None: 315 ↛ 317line 315 didn't jump to line 317 because the condition on line 315 was always true

316 break 

317 cursor = page.next_cursor 

318 return items

321def _render_progress(run_id: UUID, witness_recorder: RunWitnessRecorder | None) -> dict[str, Any]: 

322 """The run's progress readings, JSON-safe, or `{}` when unavailable. 

323 

324 `{}` covers three cases alike, deliberately not distinguished on the 

325 wire: witnessing is disabled entirely (`witness_recorder is None`), the 

326 capture behind this run is not open in this process, and the capture is 

327 open but has not produced a reading yet. All three mean the viewer has 

328 no progress number to show; none of them is an error. 

329 """ 

330 if witness_recorder is None: 

331 return {} 

332 readings = witness_recorder.progress_readings().get(run_id) 

333 if not readings: 

334 return {} 

335 return { 

336 role: { 

337 "value": observation.value, 

338 "commanded_total": observation.commanded_total, 

339 "observed_at": render_value(observation.observed_at), 

340 } 

341 for role, observation in readings.items() 

342 }

366 for role, trail in trails.items()

577class _RunHistoryTail: 

578 """Pushes each open run's full exact-timestamped history to the relay

580 separate message kind -- never inside the snapshot payload itself.
