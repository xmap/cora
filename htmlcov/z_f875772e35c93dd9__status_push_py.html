1"""StatusPush runtime: pushes a live, read-only snapshot outbound to an 

2external relay, for a status page served from a host outside this 

3deployment's own network. 

4 

5## Why this exists, and why it is not a `list_*` consumer over HTTP 

6 

72-BM's deployment runs on a host with no inbound reachability from outside 

8its own controls network (see docs/deployments/2-bm's serving design). A 

9status page that should be viewable from elsewhere therefore cannot be 

10served FROM this host; instead this host must PUSH state OUT to a relay on 

11a host that does have reach, over a connection this host itself opens. That 

12asymmetry, push rather than serve, is the entire reason this module exists 

13alongside the `list_*` REST/MCP surfaces rather than instead of them. 

14 

15## Why this is a bespoke loop, not `_flag_watcher.flag_watcher_lifespan` 

16 

17Every other composition-root watcher in this package (`_calibration_watcher`, 

18`_clearance_watcher`, `_procedure_watcher`, `_campaign_watcher`) does one 

19self-contained unit of work per tick: drain a query, compare against a rule, 

20maybe append one Decision. `flag_watcher_lifespan` is built for exactly that 

21shape. This module instead holds one PERSISTENT outbound connection across 

22many ticks (reopening it every 1-2 seconds would be pure handshake overhead 

23for a live feed), and reconnects with backoff when the relay is unreachable 

24rather than treating each drop as an isolated tick failure. That is closer 

25to `_run_witness.py`'s hand-rolled shape than to the flag-watcher family. 

26 

27## Current scope 

28 

29Each tick reads and pushes: 

30 

31 - open Runs (`Running` + `Held`), each with `progress` from 

32 `RunWitnessRecorder.progress_readings()` and a `progress_trail` from 

33 `progress_trails()` (`{}` when unavailable; see `_render_progress` / 

34 `_render_progress_trail`) 

35 - open Subjects (`Received` / `Mounted` / `Measured` / `Removed`; 

36 `Returned` / `Stored` / `Discarded` are terminal and dropped) 

37 - open Campaigns (`Planned` / `Active` / `Held`; `Closed` / `Abandoned` 

38 are terminal and dropped) 

39 - Datasets produced by an on-screen Run (bounded by the open-run count, 

40 not a separate unbounded drain) 

41 - Active Clearances (the safety-gate status a viewer most wants: is 

42 something required to start a run currently in force) 

43 - Active Enclosures (permit status: the most direct "is it safe right 

44 now" answer CORA records) 

45 - the most recent Decisions since this process started, tail-followed 

46 (see `_DecisionTail`) rather than paged from the beginning, since 

47 Decisions have no "open" status to filter on and the table is 

48 unbounded 

49 - each open Run's full exact-timestamped history (`get_run_history`), 

50 pushed as a SEPARATE message kind on the same socket (see 

51 `_RunHistoryTail`, `build_run_history_message`), refreshed 

52 periodically while open and once more, marked terminal, the instant a 

53 run leaves the open set -- this is REWIND mode's entire feed 

54 - event metadata (`stream_type`, `stream_id`, `event_type`, timestamps 

55 only, NEVER `payload`) tail-followed across the WHOLE `events` table 

56 since this process's own "now" (`_ActivityTail`, 

57 `EventActivityTrail`), pushed as a third message kind whenever 

58 something new has happened -- this is flowing mode's entire feed 

59 

60The snapshot payload is a full snapshot every push, never a delta: a 

61fresh viewer, a reconnecting viewer, and a restarted relay are all served 

62by "here is the current one". Run-history messages are the opposite: each 

63one is pushed only when genuinely new (a fresh fetch or a terminal 

64checkpoint), never repeated, since `_RunHistoryTail.poll` already tracks 

65what is new itself. 

66 

67Deliberately reads ONLY the in-memory `RunWitnessRecorder` for progress, 

68not the Postgres-durable `entries_run_observations` fallback 

69`PostgresRunChannelLookup` would offer for a run whose capture is not open 

70in this process: that path is capped at `capture_progress_flush_tick_seconds` 

71(10s by default) and never carries `commanded_total` (dropped at the 

72`ObservationInput` boundary), so it would not feel live and would silently 

73lack the "of M" figure. Revisit if this ever runs against a Run witnessed 

74by a different process than the one pushing. 

75 

76## Principal identity: the widening trigger has now fired 

77 

78Every other watcher here authenticates as its own seeded Agent (a real 

79Actor with its own grant set, so a missing grant is auditable per-agent). 

80This module still uses `SYSTEM_PRINCIPAL_ID` for every read: the read scope 

81has now widened past the single `ListRuns` command this module started 

82with, to EIGHT commands across seven BCs (`GetRunHistory` joins the 

83original seven, still within the Run BC), which is exactly the trigger this 

84docstring named for standing up a dedicated seeded identity (mirroring 

85`agent/seed_calibration_watcher.py`). That identity is NOT built in this 

86change; doing so is a follow-up, tracked so the deferral is visible rather 

87than silently indefinite. Until then, a Trust Policy that denies any of the 

88eight read commands to `SYSTEM_PRINCIPAL_ID` blinds this feature for that 

89domain only (each drain is independently try/except-guarded; see 

90`_push_loop`), never the others. 

91 

92`_ActivityTail`'s read is a NINTH, and it is a different KIND of gap, not 

93just a bigger one: `EventActivityTrail` is a raw infrastructure port, not 

94a `list_*`/`get_*` command handler, so it never calls `deps.authz.authorize` 

95at all. Every other read here can be individually denied by a Trust Policy 

96naming its command; this one cannot be denied at all short of disabling 

97StatusPush entirely. That is acceptable for what it ships (event metadata 

98across every BC, never a value, never PII) but it is a real asymmetry with 

99the eight commands above, not an equivalent case of the same debt -- flagged 

100here so it is a deliberate, visible trade-off rather than something a future 

101reader has to rediscover by reading past the authorize call that is not 

102there.

229 """Page through a list_* handler call until `next_cursor` is `None`. 

230 

231 `call` closes over everything but the cursor (the query's other 

232 filters, the handler, the principal), so this stays generic across 

233 every domain's distinct item shape. 

234 """ 

235 items: list[Any] = [] 

236 cursor: str | None = None 

237 while True: 

238 page = await call(cursor) 

239 items.extend(page.items) 

240 if page.next_cursor is None: 240 ↛ 242line 240 didn't jump to line 242 because the condition on line 240 was always true

241 break 

242 cursor = page.next_cursor 

243 return items

246def _render_progress(run_id: UUID, witness_recorder: RunWitnessRecorder | None) -> dict[str, Any]: 

247 """The run's progress readings, JSON-safe, or `{}` when unavailable. 

248 

249 `{}` covers three cases alike, deliberately not distinguished on the 

250 wire: witnessing is disabled entirely (`witness_recorder is None`), the 

251 capture behind this run is not open in this process, and the capture is 

252 open but has not produced a reading yet. All three mean the viewer has 

253 no progress number to show; none of them is an error. 

254 """ 

255 if witness_recorder is None: 

256 return {}

258 if not readings: 

259 return {} 

260 return { 

261 role: { 

262 "value": observation.value, 

263 "commanded_total": observation.commanded_total, 

264 "observed_at": render_value(observation.observed_at), 

265 } 

266 for role, observation in readings.items() 

267 }

449class _DecisionTail: 

450 """Tail-follows `list_decisions` since this instance was created, 

451 keeping only the most recent `_DECISION_RING_SIZE`. 

452 

453 Decisions carry no "open" status to filter on and the table is 

454 unbounded, so re-draining from the beginning every tick (the shape 

455 every other domain in this module uses) is both wrong and slow: it 

456 would replay the facility's entire decision history into memory once 

457 per tick, forever. Instead this holds a cursor forward across ticks 

458 (and across reconnects: one instance lives for the whole `_push_loop` 

459 call, not per-connection) and only ever asks for what is new. 

460 

461 The cursor starts at "now" rather than the beginning of the stream, so 

462 the ring is genuinely empty on construction and only ever fills with 

463 Decisions made after this process started; there is no cheap way to 

464 seek a keyset cursor to "the last N rows" without a descending query, 

465 which `list_decisions` does not offer. 

466 """ 

467 

468 def __init__(self, *, started_at_cursor: str) -> None: 

469 self._cursor: str | None = started_at_cursor 

470 self._ring: deque[dict[str, Any]] = deque(maxlen=_DECISION_RING_SIZE) 

471 

472 async def poll( 

473 self, list_decisions: ListDecisionsHandler, deps: Kernel 

474 ) -> list[dict[str, Any]]: 

475 cursor = self._cursor 

476 newest_cursor = cursor 

477 while True: 

478 page = await list_decisions( 

479 ListDecisions(cursor=cursor, limit=_PAGE_LIMIT), 

480 principal_id=SYSTEM_PRINCIPAL_ID, 

481 correlation_id=deps.id_generator.new_id(), 

482 surface_id=NIL_SENTINEL_ID, 

483 ) 

484 for item in page.items: 

485 self._ring.append( 

486 { 

487 "decision_id": render_value(item.decision_id), 

488 "decided_by": render_value(item.decided_by), 

489 "choice": item.choice, 

490 "confidence_band": item.confidence_band, 

491 "created_at": render_value(item.created_at), 

492 } 

493 ) 

494 if page.next_cursor is None: 494 ↛ 496line 494 didn't jump to line 496 because the condition on line 494 was always true

495 break 

496 newest_cursor = page.next_cursor 

497 cursor = page.next_cursor 

498 self._cursor = newest_cursor 

499 return list(self._ring)

502class _RunHistoryTail: 

503 """Pushes each open run's full exact-timestamped history to the relay 

504 at checkpoints, over the SAME outbound socket the snapshot uses, as a 

505 separate message kind -- never inside the snapshot payload itself. 

506 

507 This is REWIND mode's entire feed. arcturus has no inbound 

508 reachability, so a browser cannot ask arcturus for one run's history 

509 on demand; instead arcturus proactively pushes full histories, and the 

510 relay caches a bounded ring of them for a browser to pull from later 

511 (`infra/status-relay/relay.py`). The cost is explicit and accepted: 

512 REWIND only reaches runs pushed since the relay's own cache was last 

513 populated, never arbitrary history from before this producer (or the 

514 relay) last restarted. 

515 

516 A run's history refreshes every `_RUN_HISTORY_REFRESH_TICKS` while 

517 open (cheap: a run visible in LIVE mode does not need its REWIND 

518 timeline refreshed at the live tick's own cadence) and once more, the 

519 instant it leaves the open-run set, with `terminal=True` -- this is 

520 the checkpoint that lets the relay keep a completed run's history 

521 after it drops off the live tables. Ring-capped at 

522 `_RUN_HISTORY_RING_SIZE`, mirroring `_DecisionTail`'s reasoning: 

523 tracking every run this process has ever seen would grow without 

524 bound over a long shift. 

525 

526 One instance lives for the whole `_push_loop` call, not 

527 per-connection, same as `_DecisionTail` -- `on_reconnect()` resets 

528 only the per-run refresh clocks (not the ring) after a reconnect, so 

529 every still-open run re-pushes promptly to repopulate the relay's own

608 """Tail-follows the whole `events` table for flowing mode's lanes:
