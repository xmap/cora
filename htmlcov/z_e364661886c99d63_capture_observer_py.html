1"""CaptureObserver port: substrate-driven capture-lifecycle observation stream. 

2 

3`CaptureObserver` is the BC-local async Protocol a Run-watching runtime 

4uses to drain capture readings from an external acquisition tool's 

5substrate (EPICS PV monitors, P4P PVA subscriptions, Tango attribute 

6callbacks). Substrate details live behind concrete adapters; the 

7runtime never touches substrate-specific symbols directly. Mirrors 

8`EnclosureObserver` ([[project_enclosure_stage1_design]] L-port-1 + 

9L-CHARTER-4) at every layer; the two ports differ only in what they 

10watch. 

11 

12## BC-local, not promoted to infrastructure/ports 

13 

14The sole consumer is the Run-watching composition-root runtime. There 

15is zero cross-BC consumption today: no other BC reads observations off 

16this port. Promote to `infrastructure/ports/` only on a real second 

17cross-BC consumer (rule-of-three), exactly the `RunChannelLookup` 

18precedent. 

19 

20## Two reading kinds, one stream 

21 

22`observe()` yields `AnyCaptureObservation`, the union of 

23`CaptureLifecycleObservation` (a phase claim: BEGUN / PROGRESSING / 

24ENDED / ABORTED / UNRECOGNIZED, or no claim at all on a probe-only or 

25disconnect reading) and `CaptureProgressObservation` (a numeric 

26progress counter, e.g. `ImagesSaved`). A consumer narrows with 

27`isinstance`. The two are peers, not a supertype and a subtype: a 

28single reading is never both a phase claim and a progress reading, so 

29one closed-over `CaptureObservation` name for "the default kind" would 

30have made an isinstance check on the lifecycle kind read as a 

31supertype check rather than the kind check it actually is. Kept 

32distinct instead, per R2/R4 (naming review, slice 10). 

33 

34## Domain vocabulary (substrate-neutral) 

35 

36- `CapturePhase` (re-exported from `cora.shared.capture_phase`, hoisted 

37 there because `cora.infrastructure` validates a deployment's declared 

38 literal table against it and cannot depend on `cora.run.ports`): the 

39 closed, facility-neutral lifecycle a capture passes through, as CORA 

40 understands it. NOT the literal vocabulary any one facility's tool 

41 emits: 2-BM's TomoScan reports free-text values ("Beginning scan", 

42 "Programming PSO", "Collecting dark fields", "Scan complete") on 

43 `ScanStatus`, and those strings belong to one tomoscan commit, never 

44 to this port or the spine. A deployment DECLARES the mapping from its 

45 own literals to `CapturePhase`; unmapped or unrecognized substrate 

46 values classify as `UNRECOGNIZED`, never silently as `PROGRESSING` or 

47 dropped. 

48- `CaptureLifecycleObservation`: one capture-lifecycle reading drained 

49 from the substrate, scoped by `capture_code` (the identity surface 

50 the runtime's configuration knows, e.g. a named acquisition path). 

51 Same reach-tier and dual-clock shape as `EnclosureObservation`. 

52- `CaptureProgressObservation`: one numeric progress reading (a 

53 monotonic counter such as images saved or collected) drained from a 

54 role the deployment declared under the same capture code. `role` is 

55 the CORA-owned role key (`images_saved`, `images_collected`), the 

56 same closed vocabulary `status` and `abort` already use; it is 

57 deliberately not named `channel_name`, which is a different, operator- 

58 authored identifier on the Run BC's `AppendObservations` write path 

59 (`cora.run.aggregates.run.state.ChannelName`) that this reading does 

60 not carry directly. A consumer that writes this value onward as an 

61 observation entry chooses its own `channel_name` at that boundary. 

62- `CaptureObserverScope`: the set of capture codes the substrate 

63 adapter should subscribe to. Empty scope is valid and yields no 

64 observations. 

65 

66## No terminal claims about a file 

67 

68A `CapturePhase.ENDED` observation states only that the external tool 

69reported its lifecycle as finished. It makes NO claim that any file 

70exists, is complete, or has arrived: 2-BM's own operations reopen the 

71HDF5 file to append theta AFTER reporting "Scan complete", and the 

72transfer-status messages mark transfer start, not arrival. Binding an 

73observed capture to a Dataset is a separate, later, independently- 

74verified act and is out of scope for this port entirely. Same rule for 

75`CaptureProgressObservation`: a progress count is not a claim about 

76what a file on disk contains, and `commanded_total` is not a claim 

77that the capture will, or did, reach it. 

78 

79## D6.L2-equivalent anti-lock posture 

80 

81There is no operator gesture on this port. `CaptureObserver` has no 

82write half: it is read-only by construction, mirroring the fact that 

83CORA's `ControlPort` at 2-BM is itself wrapped read-only. Every 

84observation that crosses this seam represents a substrate reading; the 

85inbound adapter is responsible for that constraint, exactly as 

86`EnclosureObserver`'s docstring states for its own seam. 

87 

88## Subscribe shape 

89 

90`observe` is a plain `def` returning `AsyncIterator[AnyCaptureObservation]` 

91directly (no surrounding coroutine), iterated with 

92`async for observation in observer.observe(scope):`. Connect setup may 

93happen lazily on the first `__anext__`. Mid-stream disconnect is the 

94adapter's concern. 

95"""

106@dataclass(frozen=True) 

107class CaptureLifecycleObservation: 

108 """One capture-lifecycle reading from the substrate. 

109 

110 `capture_code` is the identity surface the runtime's configuration 

111 knows (the deployment-declared name for the acquisition path being 

112 watched), not a Dataset or file identity. 

113 

114 `reported_status` is the raw string the adapter read from the 

115 substrate, or `None` when this observation makes no status claim 

116 at all (a probe-only re-affirmation read, mirroring 

117 `EnclosureObservation.observed_status`). `phase` is the same 

118 reading already classified against `CapturePhase` by the adapter 

119 using the deployment's declared literal table; carrying both 

120 lets a consumer log the facility's own words alongside CORA's 

121 classification of them. 

122 

123 `reach_tier` states what kind of evidence backed this observation 

124 (see `ReachTier`); required, not optional, so every adapter states 

125 its own evidence rather than letting a consumer infer it. 

126 

127 `observed_at` is the substrate's own time for the observation, and 

128 is `None` when the substrate supplied none. An adapter with no 

129 substrate time MUST answer `None` rather than supply its own 

130 clock: a synthesized time is indistinguishable from a reported one 

131 once it is written down. Same rule as `EnclosureObservation`. 

132 

133 `source_kind` and `source_id` are the attribution pair, carried 

134 unmodified onto any downstream record exactly as the Enclosure 

135 seam does for `monitor_ref`. 

136 """

139 reported_status: str | None 

140 phase: CapturePhase | None 

141 reach_tier: ReachTier 

142 observed_at: datetime | None

147@dataclass(frozen=True) 

148class CaptureProgressObservation: 

149 """One numeric progress reading from the substrate. 

150 

151 Not a phase claim: a progress role (`images_saved`, 

152 `images_collected`) reports how far a capture has gotten, never 

153 whether it began, ended, or was aborted. `role` is the CORA-owned 

154 role key the deployment declared this PV under in 

155 `Settings.capture_watch_pvs` (the same closed vocabulary `status` 

156 and `abort` already use), NOT the Run BC's operator-authored 

157 `ChannelName`. 

158 

159 `value` is the decoded numeric reading. An adapter that cannot 

160 decode a reading as a finite number emits nothing for it rather 

161 than guessing; see `_capture_observer.py`. 

162 

163 `commanded_total` is the substrate's own target count for this role 

164 when the reading carries one (2-BM's `"<reached>/<commanded>"` 

165 stringout format), or `None` when the reading has no such second 

166 half. It is NOT a completeness signal: `wait_camera_done()`'s poll 

167 loop returns on `CamAcquireBusy == 0` before a final 

168 `update_status()` call, so `value < commanded_total` is the normal 

169 terminal state of a successful scan, not evidence of a shortfall. 

170 Carried because a witnessed terminal needs the substrate's own 

171 target as evidence, never because `value == commanded_total` is a 

172 valid test; see `_capture_observer.py` and 

173 `CaptureProgressSnapshot`. 

174 

175 `reach_tier`, `observed_at`, `source_kind`, `source_id` carry the 

176 same meaning as on `CaptureLifecycleObservation`. 

177 """ 

178 

179 capture_code: str 

180 role: str 

181 value: float 

182 commanded_total: float | None

208class CaptureObserver(Protocol): 

209 """Async source of `AnyCaptureObservation` values from the substrate. 

210 

211 The substrate adapter owns the subscription lifecycle. A runtime 

212 iterates and forwards each observation onward; this port makes no 

213 claim about what the runtime does with what it drains. 

214 

215 Iteration semantics mirror `EnclosureObserver`: open-ended for live 

216 substrates, `StopAsyncIteration` is a clean teardown for one-shot 

217 observers (tests, stubs), and disconnect handling is the adapter's 

218 concern. 

219 """
