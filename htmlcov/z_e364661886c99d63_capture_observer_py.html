1"""CaptureObserver port: substrate-driven capture-lifecycle observation stream. 

2 

3`CaptureObserver` is the BC-local async Protocol a Run-watching runtime 

4uses to drain capture readings from an external acquisition tool's 

5substrate (EPICS PV monitors, P4P PVA subscriptions, Tango attribute 

6callbacks). Substrate details live behind concrete adapters; the 

7runtime never touches substrate-specific symbols directly. Mirrors 

8`EnclosureObserver` ([[project_enclosure_stage1_design]] L-port-1 + 

9L-CHARTER-4) at every layer; the two ports differ only in what they 

10watch. 

11 

12## BC-local, not promoted to infrastructure/ports 

13 

14The sole consumer is the Run-watching composition-root runtime. There 

15is zero cross-BC consumption today: no other BC reads observations off 

16this port. Promote to `infrastructure/ports/` only on a real second 

17cross-BC consumer (rule-of-three), exactly the `RunChannelLookup` 

18precedent. 

19 

20## Four reading kinds, one stream 

21 

22`observe()` yields `AnyCaptureObservation`, the union of 

23`CaptureLifecycleObservation` (a phase claim: BEGUN / PROGRESSING / 

24ENDED / ABORTED / UNRECOGNIZED, or no claim at all on a probe-only or 

25disconnect reading), `CaptureProgressObservation` (a numeric 

26progress counter, e.g. `ImagesSaved`), `CapturePreconditionBypassObservation` 

27(the optional `testing` role's tri-state reading, slice 11), and 

28`CapturePathObservation` (the optional `full_file_name` role's text 

29reading, slice 13). A consumer narrows with `isinstance`. 

30The four are peers, not a supertype and subtypes: a single reading is 

31never more than one of these at once, so one closed-over 

32`CaptureObservation` name for "the default kind" would have made an 

33isinstance check on the lifecycle kind read as a supertype check 

34rather than the kind check it actually is. Kept distinct instead, per 

35R2/R4 (naming review, slice 10). 

36 

37## Domain vocabulary (substrate-neutral) 

38 

39- `CapturePhase` (re-exported from `cora.shared.capture_phase`, hoisted 

40 there because `cora.infrastructure` validates a deployment's declared 

41 literal table against it and cannot depend on `cora.run.ports`): the 

42 closed, facility-neutral lifecycle a capture passes through, as CORA 

43 understands it. NOT the literal vocabulary any one facility's tool 

44 emits: 2-BM's TomoScan reports free-text values ("Beginning scan", 

45 "Programming PSO", "Collecting dark fields", "Scan complete") on 

46 `ScanStatus`, and those strings belong to one tomoscan commit, never 

47 to this port or the spine. A deployment DECLARES the mapping from its 

48 own literals to `CapturePhase`; unmapped or unrecognized substrate 

49 values classify as `UNRECOGNIZED`, never silently as `PROGRESSING` or 

50 dropped. 

51- `CaptureLifecycleObservation`: one capture-lifecycle reading drained 

52 from the substrate, scoped by `capture_code` (the identity surface 

53 the runtime's configuration knows, e.g. a named acquisition path). 

54 Same reach-tier and dual-clock shape as `EnclosureObservation`. 

55- `CaptureProgressObservation`: one numeric progress reading (a 

56 monotonic counter such as images saved or collected) drained from a 

57 role the deployment declared under the same capture code. `role` is 

58 the CORA-owned role key (`images_saved`, `images_collected`), the 

59 same closed vocabulary `status` and `abort` already use; it is 

60 deliberately not named `channel_name`, which is a different, operator- 

61 authored identifier on the Run BC's `AppendObservations` write path 

62 (`cora.run.aggregates.run.state.ChannelName`) that this reading does 

63 not carry directly. A consumer that writes this value onward as an 

64 observation entry chooses its own `channel_name` at that boundary. 

65- `CapturePreconditionBypassObservation`: one reading of the optional 

66 `testing` role (slice 11), drained from a role the deployment 

67 declared under the same capture code, same closed vocabulary as 

68 `status` / `abort` / the progress roles. The type and field names are 

69 facility-neutral (`beam_preconditions_bypassed`), NOT the substrate's 

70 own `testing` word, mirroring `CaptureProgressSnapshot`'s own 

71 precedent of keeping this domain vocabulary substrate-neutral even 

72 where the CONFIG-facing role key mirrors the PV name. Tri-state, not 

73 a phase claim and not a progress counter: 

74 `beam_preconditions_bypassed=True` is a positive claim the substrate 

75 is bypassing its own beam preconditions for this capture, `=False` is 

76 a positive claim it is NOT (a real acquisition), and `=None` means 

77 the reading did not decode or none has ever arrived. NOT 

78 `Observation.is_simulated`: that column answers whether the NUMBERS 

79 CORA recorded were invented (a simulator or replay feeder), an 

80 orthogonal question from whether the facility had beam. See 

81 [[project_run_witness_test_provenance_slice11]] for the full 

82 argument against collapsing the two. 

83- `CapturePathObservation` (slice 13): one reading of the optional 

84 `full_file_name` role, the areaDetector file plugin's own filename 

85 readback (`FullFileName_RBV`), drained continuously and independently 

86 of any one capture (the file plugin fires this at file OPEN, which 

87 can land before, during, or after any particular capture's own BEGUN 

88 observation reaches this port). **`observed_path` is personal data**: 

89 2-BM's directory layout embeds `{UserLastName}-{ProposalNumber}` 

90 (`tomoscan_2bm.py:474-477`), so every real reading of this role 

91 carries a person's surname. A consumer of this observation MUST NOT 

92 log it, put it on an event, or persist it anywhere but the dedicated 

93 `run_capture_path` PII vault (`CapturePathStore`, mirroring 

94 `actor_profile` / `ProfileStore`). Recording an observed path is 

95 NOT a claim the file is complete, so it does not violate "No terminal 

96 claims about a file" below; it says only that the file plugin opened 

97 a file at this substrate time, nothing about what it contains or 

98 whether writing to it has finished. 

99- `CaptureObserverScope`: the set of capture codes the substrate 

100 adapter should subscribe to. Empty scope is valid and yields no 

101 observations. 

102 

103## No terminal claims about a file 

104 

105A `CapturePhase.ENDED` observation states only that the external tool 

106reported its lifecycle as finished. It makes NO claim that any file 

107exists, is complete, or has arrived: 2-BM's own operations reopen the 

108HDF5 file to append theta AFTER reporting "Scan complete", and the 

109transfer-status messages mark transfer start, not arrival. Binding an 

110observed capture to a Dataset is a separate, later, independently- 

111verified act and is out of scope for this port entirely. Same rule for 

112`CaptureProgressObservation`: a progress count is not a claim about 

113what a file on disk contains, and `commanded_total` is not a claim 

114that the capture will, or did, reach it. 

115 

116## D6.L2-equivalent anti-lock posture 

117 

118There is no operator gesture on this port. `CaptureObserver` has no 

119write half: it is read-only by construction, mirroring the fact that 

120CORA's `ControlPort` at 2-BM is itself wrapped read-only. Every 

121observation that crosses this seam represents a substrate reading; the 

122inbound adapter is responsible for that constraint, exactly as 

123`EnclosureObserver`'s docstring states for its own seam. 

124 

125## Subscribe shape 

126 

127`observe` is a plain `def` returning `AsyncIterator[AnyCaptureObservation]` 

128directly (no surrounding coroutine), iterated with 

129`async for observation in observer.observe(scope):`. Connect setup may 

130happen lazily on the first `__anext__`. Mid-stream disconnect is the 

131adapter's concern. 

132"""

143@dataclass(frozen=True) 

144class CaptureLifecycleObservation: 

145 """One capture-lifecycle reading from the substrate. 

146 

147 `capture_code` is the identity surface the runtime's configuration 

148 knows (the deployment-declared name for the acquisition path being 

149 watched), not a Dataset or file identity. 

150 

151 `reported_status` is the raw string the adapter read from the 

152 substrate, or `None` when this observation makes no status claim 

153 at all (a probe-only re-affirmation read, mirroring 

154 `EnclosureObservation.observed_status`). `phase` is the same 

155 reading already classified against `CapturePhase` by the adapter 

156 using the deployment's declared literal table; carrying both 

157 lets a consumer log the facility's own words alongside CORA's 

158 classification of them. 

159 

160 `reach_tier` states what kind of evidence backed this observation 

161 (see `ReachTier`); required, not optional, so every adapter states 

162 its own evidence rather than letting a consumer infer it. 

163 

164 `observed_at` is the substrate's own time for the observation, and 

165 is `None` when the substrate supplied none. An adapter with no 

166 substrate time MUST answer `None` rather than supply its own 

167 clock: a synthesized time is indistinguishable from a reported one 

168 once it is written down. Same rule as `EnclosureObservation`. 

169 

170 `source_kind` and `source_id` are the attribution pair, carried 

171 unmodified onto any downstream record exactly as the Enclosure 

172 seam does for `monitor_ref`. 

173 """

176 reported_status: str | None 

177 phase: CapturePhase | None 

178 reach_tier: ReachTier 

179 observed_at: datetime | None 

180 source_kind: str

184@dataclass(frozen=True) 

185class CaptureProgressObservation: 

186 """One numeric progress reading from the substrate. 

187 

188 Not a phase claim: a progress role (`images_saved`, 

189 `images_collected`) reports how far a capture has gotten, never 

190 whether it began, ended, or was aborted. `role` is the CORA-owned 

191 role key the deployment declared this PV under in 

192 `Settings.capture_watch_pvs` (the same closed vocabulary `status` 

193 and `abort` already use), NOT the Run BC's operator-authored 

194 `ChannelName`. 

195 

196 `value` is the decoded numeric reading. An adapter that cannot 

197 decode a reading as a finite number emits nothing for it rather 

198 than guessing; see `_capture_observer.py`. 

199 

200 `commanded_total` is the substrate's own target count for this role 

201 when the reading carries one (2-BM's `"<reached>/<commanded>"` 

202 stringout format), or `None` when the reading has no such second 

203 half. It is NOT a completeness signal: `wait_camera_done()`'s poll 

204 loop returns on `CamAcquireBusy == 0` before a final 

205 `update_status()` call, so `value < commanded_total` is the normal 

206 terminal state of a successful scan, not evidence of a shortfall. 

207 Carried because a witnessed terminal needs the substrate's own 

208 target as evidence, never because `value == commanded_total` is a 

209 valid test; see `_capture_observer.py` and 

210 `CaptureProgressSnapshot`. 

211 

212 `reach_tier`, `observed_at`, `source_kind`, `source_id` carry the 

213 same meaning as on `CaptureLifecycleObservation`. 

214 """ 

215

217 role: str 

218 value: float

226@dataclass(frozen=True) 

227class CapturePreconditionBypassObservation: 

228 """One reading of the optional `testing` role: whether the substrate 

229 is bypassing its own beam preconditions for this capture code. 

230 

231 Named for the domain fact, not the substrate's own `testing` word 

232 (which stays confined to the `Settings.capture_watch_pvs` role key 

233 and `_capture_observer.py`), mirroring `CaptureProgressSnapshot`'s 

234 own precedent of keeping this domain vocabulary facility-neutral. 

235 

236 `beam_preconditions_bypassed` is the decoded tri-state claim, via 

237 `binary_code` (`_capture_observer.py`) applied to the raw reading: 

238 `True` (asserted) is a positive claim the substrate is bypassing 

239 its beam preconditions for this capture; `False` (clear) is a 

240 positive claim it is NOT, i.e. a real acquisition; `None` means the 

241 reading did not decode. Three states, not two: `None` must never 

242 collapse into `False`, since "unknown" and "confirmed real" are 

243 different claims a reader needs to tell apart. 

244 

245 `role` is not carried (unlike `CaptureProgressObservation`): the 

246 `testing` role is singular per capture code, so there is nothing 

247 to disambiguate between multiple readings of this kind. 

248 

249 `reach_tier`, `observed_at`, `source_kind`, `source_id` carry the 

250 same meaning as on `CaptureLifecycleObservation`. `observed_at` is 

251 the substrate's OWN time for this reading, never CORA's clock: the 

252 role is read continuously and independently of any one capture, so 

253 a consumer retaining the latest reading needs this to tell a fresh 

254 reading from a stale one still standing from hours earlier. 

255 """ 

256 

257 capture_code: str 

258 beam_preconditions_bypassed: bool | None 

259 reach_tier: ReachTier 

260 observed_at: datetime | None 

261 source_kind: str 

262 source_id: str

266class CapturePathObservation: 

267 """One reading of the optional `full_file_name` role: the 

268 areaDetector file plugin's own filename readback (`FullFileName_RBV`). 

269 

270 `observed_path` is PERSONAL DATA (see this module's docstring, 

271 "Domain vocabulary" bullet on this class). It MUST NOT be logged, 

272 placed on an event payload, or persisted anywhere but the 

273 `run_capture_path` PII vault. A consumer that retains this 

274 observation (e.g. to compare against a Run's own BEGUN time before

276 that path for this field. 

277

288 the substrate's OWN time for this reading, never CORA's clock: it

331@runtime_checkable 

332class CaptureObserver(Protocol): 

333 """Async source of `AnyCaptureObservation` values from the substrate. 

334 

335 The substrate adapter owns the subscription lifecycle. A runtime 

336 iterates and forwards each observation onward; this port makes no 

337 claim about what the runtime does with what it drains. 

338 

339 Iteration semantics mirror `EnclosureObserver`: open-ended for live 

340 substrates, `StopAsyncIteration` is a clean teardown for one-shot 

341 observers (tests, stubs), and disconnect handling is the adapter's 

342 concern. 

343 """ 

344
