1"""`cora-capture-path://` locators: indirect references CORA mints so an 

2automated ingest never writes a personal-data path onto an event. 

3 

4## Why this exists 

5 

62-BM's directory layout embeds `{PIlastname}-{GUP#}` (a real person's 

7surname) in every scan path. `DatasetRegistered.uri` / 

8`DistributionRegistered.uri` are immutable, INSERT-only event fields 

9with no erasure path today. A human pasting a path into the ordinary 

10`ingest_scan` POST route has always been able to do this; `slice 17`'s 

11`CaptureScanIngestor` makes it automatic and unconditional, for every 

12run, which is the difference that makes it worth closing rather than 

13accepting. 

14 

15The disposition table (`cora.infrastructure.record_export._dispositions`) 

16already drops `uri` from the published, redacted record, and has no 

17person-name field anywhere else. This scheme is what keeps that true of 

18the INTERNAL record too: `mint_capture_path_locator` is the only thing 

19`CaptureScanIngestor` calls to build a locator, so the automated path 

20never constructs a `file://` URI carrying the real, personal-data path. 

21 

22## Structured, not opaque 

23 

24The real path is never in the locator; the personal segment is replaced 

25with a `run-<uuid>` token resolved through `run_capture_path` (the 

26same erasable vault `capture_path.py` already keeps `observed_path` 

27in, for the identical reason -- see that module's docstring). Host and 

28tier stay visible because neither is personal data and both are real 

29provenance a reader benefits from, unlike a fully opaque 

30`cora-capture-path://<uuid>`. 

31 

32Keeping them structured has two consequences. `_filename_of` 

33(ingest_scan's own Dataset-naming helper) keeps working unmodified, 

34because the locator's last path segment is still a real filename. And 

35host and tier are LOAD-BEARING at resolve time: they are the key this 

36module looks the vault row up by, since a Run may hold one row per 

37storage location (acquisition tier, archive tier) and a locator naming 

38one must never resolve to the other's bytes. 

39 

40That is a change from this module's first version, which keyed the 

41lookup on `run_id` alone and argued that re-verifying host and tier 

42would be decorative -- correctly, at the time: both had been chosen 

43unilaterally at mint time from the same settings a resolve-time check 

44would have compared against, and a check against your own output is 

45not independent (see [[project_independent_check_principle]]). Once the 

46vault holds more than one row per Run, they stop being a self-comparison 

47and become a genuine selector against independently written rows. 

48 

49The filename comparison remains the module's other real cross-check: 

50its two sides come from separate reads (the candidate query at mint 

51time, a fresh `get` at resolve time), so a drift between them is a 

52signal rather than decoration. 

53 

54## Scope 

55 

56Understood ONLY by `ingest_scan`'s own read path (this module's 

57`resolve`, called once from its handler). `record_attestation`'s 

58checksum verifier map (`cora.data.wire._build_checksum_verifiers`) has 

59no entry for this scheme and never will as part of this slice: 

60verifying a Distribution registered through the SSH transport is a 

61pre-existing gap this slice does not create or widen (no 

62`ChecksumVerifier` exists for a plain SSH-sourced `file://` Distribution 

63either, and `SshPosixChecksumComputer`'s own docstring already deferred 

64building one "per the rule-of-three"). Also NOT registered with 

65`launch_argv`'s allowed schemes or the compute port's path resolver: a 

66recipe or job spec must not reference an indirect locator directly. 

67Nothing today wires a Dataset/Distribution URI into a launch spec 

68automatically, so this is a documented boundary, not a fitness test. 

69 

70## Residual risk: `resolve` is a pass-through, not an authorization check 

71 

72`resolve` is called unconditionally on every `IngestScan` locator, not 

73only the ones `CaptureScanIngestor` mints. A caller of the ordinary POST 

74route or MCP tool who is authorized for `IngestScan` (but review this 

75against whatever else that principal holds) could hand-craft a 

76`cora-capture-path://.../run-<uuid>/<filename>` string naming a DIFFERENT 

77run than the one they intend, and have `ingest_scan` read, digest, and 

78register a Dataset from THAT run's real bytes -- `run_id` is not 

79brute-forceable, but is exposed to any `GetRun`-authorized caller via 

80`observed_capture_path`, and the filename-match check this module makes 

81(see above) only catches accidental drift, not a caller who already 

82knows both. If that same principal already holds `GetRun`, this adds no 

83new confidentiality capability (they could already read the real path 

84directly); the residual case is a principal authorized for `IngestScan` 

85without also being authorized to read Run capture paths. Fixing this 

86structurally would mean identity-gating this scheme to the one pinned 

87agent principal that is supposed to mint it, which would couple this 

88Data BC module to an `cora.api`/`cora.agent`-owned identity constant -- 

89a worse cross-layer dependency than the risk it would close. Deployments 

90should keep `IngestScan` and Run capture-path read access commensurately 

91scoped rather than relying on this module to enforce that boundary. 

92"""

106class CapturePathLookup(Protocol): 

107 """The one method this module ever calls on Run BC's `CapturePathStore`. 

108 

109 A consumer-local narrowing, in the spirit of the 

110 port-shaped-by-consumer convention though not the same shape as it: 

111 `ClearanceLookup`/`SupplyLookup`/`DatasetDistributionLookup` are 

112 Kernel-injected cross-BC ports in `cora.infrastructure.ports`, 

113 satisfied by an adapter in the owning BC. This is narrower than 

114 that, a Protocol declared where it is consumed over a concrete 

115 class, and hoisting it for one consumer would be premature. The 

116 principle it borrows is only that the CONSUMER shapes the surface 

117 it actually uses, even though `cora.data` 

118 is separately sanctioned to import the full `CapturePathStore` 

119 Protocol directly (`tach.toml` already permits `cora.data` -> 

120 `cora.run.aggregates`). That sanctioned IMPORT PATH is not a license 

121 to require more surface than this module calls: `resolve` only ever 

122 reads, so requiring a caller to also supply `upsert` would be 

123 asking for capability this module has no use for and no business 

124 depending on. `PostgresCapturePathStore` / `InMemoryCapturePathStore` 

125 satisfy this structurally, unchanged. 

126 """

138def active_scan_transport(deps: Kernel) -> tuple[str, tuple[str, ...]]: 

139 """(host_label, configured_roots) for whichever transport 

140 `cora.data.wire._build_scan_ingest_pair` would select for this 

141 deployment. 

142 

143 Shared by both callers -- minting here, pair selection in 

144 `wire.py` -- so a locator's host/tier segments always describe the 

145 SAME transport that will actually read it, rather than two copies 

146 of this conditional drifting apart under a future settings change. 

147 """ 

148 host = deps.settings.scan_probe_remote_host 

149 if host is not None: 

150 return host, deps.settings.scan_probe_allowed_roots 

151 return "localhost", deps.settings.posix_checksum_roots

154def mint_capture_path_locator( 

155 *, 

156 observed_path: str, 

157 run_id: UUID, 

158 host: str | None, 

159 root: str | None, 

160) -> str | None: 

161 """Build an indirect `cora-capture-path://` locator for `observed_path`. 

162 

163 `host` and `root` are the location the VAULT ROW RECORDED at 

164 observation time, not a fresh match against current settings. That 

165 is the point: `resolve` looks the row up by exactly these two 

166 values, so deriving them here from settings that may have moved 

167 since the row was written would mint a locator that resolves to 

168 nothing, silently. Passing the row's own location makes the two 

169 sides the same fact rather than two reads of a mutable one. 

170 

171 Returns `None` when either is `None`, which is how a row observed 

172 under no configured root (or written before the vault recorded 

173 location at all) declines to produce a locator instead of getting a 

174 fabricated one. The caller (only `CaptureScanIngestor` today) 

175 treats `None` as this candidate is stuck, mirroring its existing 

176 missing-binding SKIP. 

177 

178 The personal segment is never inspected: everything strictly 

179 between the matched root and the filename is discarded, regardless 

180 of how many directory levels it spans or what it is named. This is 

181 what makes the scheme correct for any facility's layout, not just 

182 2-BM's `{PIlastname}-{GUP#}` convention. 

183 

184 CAUTION for whoever configures the storage roots: `root` is 

185 embedded in the locator VERBATIM, trusted as safe with no way for 

186 this function to verify that from the string alone. Configured 

187 roots MUST name the facility-level storage tier (`/local1/2BM`), 

188 never a path that itself contains personal data (an experiment 

189 folder). A root 

190 misconfigured to the latter would leak that data into the locator's 

191 supposedly-safe tier segment, defeating this module's whole purpose. 

192 

193 At 2-BM this is a live hazard rather than a hypothetical: alongside 

194 the beamline tree at `<tier>/2BM/`, the analysis tiers carry 

195 per-person workspaces directly at their root (`/data3/vnikitin`, 

196 `/data3/sboyer`), so a root pointed at one of those would embed a 

197 username. The correct roots there are `<tier>/2BM` exactly. How 

198 many levels sit below that root is irrelevant here, which is just 

199 as well, because it varies: the experiment folder is nested under a 

200 year-month on `/data2` and flat on `/local2`. 

201 """ 

202 if host is None or root is None: 

203 return None 

204 filename = Path(observed_path).name 

205 return f"{CAPTURE_PATH_SCHEME}://{host}{root}/{_RUN_SEGMENT_PREFIX}{run_id}/{quote(filename)}" 

206

208async def resolve_capture_path_locator( 

209 locator: str, 

210 *, 

211 capture_path_store: CapturePathLookup, 

212) -> str | None: 

213 """Resolve `locator` to the real `file://` URI the scan reader / 

214 checksum computer can act on. 

215 

216 Pass-through for every scheme other than `cora-capture-path`: the manual 

217 `ingest_scan` POST route and MCP tool keep sending real `file://` 

218 URIs directly, unaffected by this module, per the scope decision 

219 that only the automated sweep mints indirect locators. 

220 

221 Returns `None` -- never a reason string -- on every failure mode 

222 (malformed locator; no vault row at all; a row that exists but not 

223 at the location the locator names; filename mismatch), so a caller 

224 cannot accidentally log or surface anything that touches 

225 `observed_path`. The vault row's absence is treated the same as a 

226 malformed locator: this is also what an erasure would look like 

227 once a forget-style slice calls `CapturePathStore`'s (currently 

228 unused) `DELETE` grant, so refusing quietly here is already the 

229 right behavior for that future, not a placeholder for it. 

230 """ 

231 parsed = urlparse(locator) 

232 if parsed.scheme != CAPTURE_PATH_SCHEME: 

233 return locator 

234 

235 segments = [segment for segment in parsed.path.split("/") if segment] 

236 if len(segments) < 2: 

237 return None 

238 run_segment, filename_segment = segments[-2], segments[-1] 

239 host = parsed.netloc 

240 root = "/" + "/".join(segments[:-2]) if len(segments) > 2 else "" 

241 if not run_segment.startswith(_RUN_SEGMENT_PREFIX): 

242 return None 

243 try: 

244 run_id = UUID(run_segment[len(_RUN_SEGMENT_PREFIX) :]) 

245 except ValueError: 

246 return None 

247 

248 row = await capture_path_store.get(run_id, host=host, root=root) 

249 if row is None: 

250 return None 

251 

252 # The one genuine cross-check this module makes: the filename 

253 # minted into the locator (read from the vault at candidate-lookup 

254 # time) against the vault's OWN current basename (a fresh read). 

255 # Host and tier are the LOOKUP KEY above, not a post-hoc 

256 # comparison; see the module docstring. 

257 if Path(row.observed_path).name != unquote(filename_segment): 

258 return None 

259 

260 return "file://" + quote(row.observed_path)
