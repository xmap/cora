1"""Activity entry: per-Procedure procedural step row. 

2 

3Fourth concrete entry kind in CORA after `Verdict`, 

4`Inference`, and `Observation`. Same per-category 

5writer pattern: a typed dataclass + per-category Postgres adapter 

6alongside the owning aggregate, with a category-local `ActivityStore` 

7Protocol (NOT a shared cross-BC port). 

8 

9## Storage shape: Path C in the cross-BC trichotomy 

10 

11Per [[project_logbook_entry_storage]] §"The rule (the trichotomy)", 

12Activity sits at **Path C** (polymorphic table with discriminator 

13column + JSON-payload column): 

14 

15 - **Path A** (typed sibling tables, one per kind) → Verdict, 

16 Inference. Pick when shape diverges AND per-kind volume / 

17 queryability matter. 

18 - **Path B** (polymorphic + typed value columns) → Observation. Pick 

19 when shape is uniform across kinds. 

20 - **Path C** (polymorphic + JSON payload) → Activity. Pick when 

21 shape diverges BUT per-kind volume is low / no per-kind read-side 

22 projection is planned. 

23 

24Activity's body shape DIVERGES across kinds (setpoint = 

25channel + target_value + units? + ramp_rate?; action = action_name + 

26params; check = channel + passed + expected? + actual? + tolerance?), 

27so typed columns would mean lots of mostly-NULL per-kind columns. But 

28per-kind row volume at MVP scale is in the hundreds, and operator 

29queries don't filter by kind alone, so 3 sibling tables would be 

30overkill. JSON `payload` column with per-kind Pydantic validation at 

31the API layer is the right shape. 

32 

33Standards precedent for Path C: OPC UA Part 10 §5.2.5-5.2.6 emits 

34SEPARATE events per program state transition (each transition has 

35its own audit event with transition-specific payload); Bluesky 

36event-model uses separate documents per phase (RunStart / Descriptor 

37/ Event / RunStop); 21 CFR Part 11 favors independent-action audit 

38records; modern event-sourcing consensus is JSON-payload-with- 

39discriminator over typed columns when per-kind shape evolves at code 

40speed. 

41 

42## Logbook + Entry skeleton (shared with Observation + Inference + Verdict) 

43 

44The body-shape encoding diverges from Observation, but the SKELETON is 

45identical: lazy open-on-first-write envelope event, three timestamps, 

46per-category `<EntryNoun>Store` port with InMemory + Postgres adapters, 

47dedicated `entries_<aggregate>_<entry_noun_plural>` table, batch 

48`Append<...>` slice. See [[project_logbook_entry_storage]] §"Naming 

49family (cross-BC)" for the full shape. 

50 

51## Three timestamps 

52 

53 - `sampled_at`: phenomenonTime -- when the step physically happened 

54 in the field (operator-recorded or instrument-clock; mandatory). 

55 - `occurred_at`: when the handler appended the entry (CORA Clock 

56 port; same convention as the events table and other entries). 

57 - `recorded_at`: when Postgres wrote the row (`DEFAULT now()`; same 

58 convention as the events table and other entries). 

59 

60## Why writes batch from day one 

61 

62`append(rows: list[Activity])` always takes a list. Operator 

63workflows often record several steps at once (an alignment 

64with 5 setpoints + 5 checks); batch shape avoids N round-trips. Empty 

65lists are a no-op. 

66 

67## Why no read shape today 

68 

69The retrieval query lands when a real consumer asks for it. Today the 

70table is write-only from the application's perspective; ad-hoc SQL 

71covers any operator queries. Same posture as the prior three entry 

72kinds. 

73"""

331@dataclass(frozen=True) 

332class Outcome: 

333 """One row in the per-Procedure steered-pass outcome logbook. 

334 

335 Sixth concrete entry kind (after `Verdict`, `Inference`, `Observation`, 

336 `Activity`, `Diagnostic`), and the third on the Procedure aggregate. It 

337 records, per steered-conduct pass, the SELF-DESCRIBING observation the brain 

338 fit against: the coordinate it measured at (`point`, the "x") AND the 

339 measured values there (`measurements`, the "y"). Its purpose is RESUME: on 

340 restart of a crashed GP-steered run, the optimizer's observation history is 

341 rebuilt directly from these rows instead of re-measuring hardware. Distinct 

342 from `Diagnostic` (the fitted model's internal scalars) and `Activity` (the 

343 physical steps): this is the observed result of a pass. 

344 

345 ## Self-describing: point + measurements in one row 

346 

347 An early design recorded only `measurements` and recovered the point by a 

348 POSITIONAL join to `ProcedureIterationEnded.advised_next_point` (outcome k 

349 paired to the prior pass's advice). That join broke after an abandoned pass 

350 (a mid-pass crash inserts an extra iteration event, permanently drifting the 

351 0-based outcome ordinal from the 1-based iteration index). Carrying `point` 

352 on the row removes the join entirely: reconstruction is sort-by-index then 

353 map, and index gaps left by abandoned passes are harmless (a sort preserves 

354 order regardless of gaps). No off-by-one, no gap-free precondition. 

355 

356 Path C (polymorphic JSON payload): `measurements` is a list of Measurement 

357 dicts (value / kind / quality / name / units) and `point` is a coordinate 

358 map, both of beamline-varying shape, so single jsonb columns beat typed 

359 sibling columns; per-row volume is low (one row per steered pass). Mirrors 

360 the `Diagnostic` skeleton in this same aggregate. 

361 

362 `iteration_index` is the ORDERING key for reconstruction (ascending = pass 

363 order) and an audit cross-reference to the FSM iteration that produced the 

364 row; it is 0-based and may have gaps after an abandoned pass, which the 

365 sort-then-map reconstruction tolerates. `succeeded` mirrors the 

366 SteeringObservation success flag (a failed acquisition is a real datum); 

367 `actuation_kind` threads the Physical / Simulated / Hybrid provenance so a 

368 resumed fit can distrust a simulated outcome. 

369 

370 `event_id` is the producer-assigned UUIDv7 identity, the dedup key under 

371 at-least-once delivery (table PRIMARY KEY). `correlation_id` / 

372 `causation_id` thread from the originating command's envelope. 

373 """ 

374 

375 event_id: UUID 

376 procedure_id: UUID 

377 logbook_id: UUID

472 def for_procedure(self, procedure_id: UUID) -> list[Outcome]: 

473 """Return a procedure's recorded outcomes, ascending by iteration_index.""" 

474 rows = [row for row in self._rows.values() if row.procedure_id == procedure_id] 

475 rows.sort(key=lambda row: row.iteration_index) 

476 return rows
