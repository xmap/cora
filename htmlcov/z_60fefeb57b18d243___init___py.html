1"""Run bounded context. 

2 

3Owns the actual-execution layer of CORA. Per the BC map's recipe 

4ladder, Run is the keystone — Method (≈ ISA-88 General Recipe) → 

5Practice (≈ Site Recipe) → Plan (≈ Master/Control Recipe) → **Run** 

6(actual batch execution; immutable, has FSM, audit trail, references 

7to Subject(s)). 

8 

9A Run binds a `Plan` (which itself binds a Practice + Asset set) 

10and an optional `Subject` (sample being measured; null for dark- 

11field / flat-field calibration runs per beamline-domain convention, 

12where calibration data is consumed alongside sample data within the 

13same analysis pipeline). 

14 

15Track A BC. Depends on: 

16 - `Recipe.Plan` (referenced by `Run.plan_id`; loaded at Run-start 

17 for re-validation of capability superset against current Asset 

18 state) 

19 - `Equipment.Asset` (transitive via Plan; loaded at Run-start to 

20 re-check that no bound Asset has been Decommissioned) 

21 - `Subject.Subject` (referenced by `Run.subject_id` if non-null; 

22 must be in Mounted or Measured state) 

23 

24 

25Full lifecycle FSM closed: 

26 - `id` + `name` (RunName: 11th bounded-name VO) 

27 - `plan_id: UUID`, eventual-consistency ref; existence verified 

28 at handler-load time 

29 - `subject_id: UUID | None`, null for calibration / dark-field 

30 runs; if non-null, Subject must be in Mounted | Measured 

31 - `status: RunStatus` (`Running | Held | Completed | Aborted | 

32 Stopped | Truncated`) 

33 

34Cross-aggregate validation at Run-start (gate-review Q2 / Q5 

35locked answers): handler pre-loads Plan + Subject (if subject_id) 

36+ each bound Asset (from `plan.asset_ids`); decider receives 

37`RunStartContext` and validates as opaque domain inputs (same 

38canonical pattern as Plan's PlanBindingContext). Per 

39gate-review Q5: Run-start re-validates capability superset 

40against CURRENT Asset state (Plan-bind validated against then- 

41current; drift is real, Run is the last gate). 

42 

43Active-phase transitions (6f-2 + 6f-3): 

44 - `complete_run` (Running → Completed): single-source. Completion 

45 claims active achievement, so requires the Run to be actively 

46 running; an operator wanting to complete a held Run must 

47 Resume → Complete. Slim payload by design. 

48 - `abort_run` (Running | Held → Aborted): multi-source. Carries 

49 free-form `reason: str` (1-500 chars). Emergencies during a 

50 hold are real and should not require an intervening Resume. 

51 - `hold_run` (Running → Held): single-source pause. No reason 

52 field — matches PackML / Bluesky precedent that pause is a 

53 routine operation. 

54 - `resume_run` (Held → Running): single-source un-pause. Hold ⇄ 

55 Resume is bidirectional and unlimited-cycle (PackML + Bluesky 

56 precedent). 

57 - `stop_run` (Running | Held → Stopped): multi-source controlled 

58 exit. Carries free-form `reason: str` (1-500 chars). Distinct 

59 from abort: stop = data valid up to the stop point; abort = 

60 data flagged as potentially invalid (PackML + Bluesky lifecycle- 

61 layer distinction; observation-channel cleanup semantics materialize in 

62 6f-5+). 

63 - `truncate_run` (Running | Held → Truncated): multi-source 

64 cleanup terminal for a Run that became de-facto dead through 

65 interruption (power loss, process crash, hardware fault) and 

66 is being closed retroactively. Carries free-form `reason: str` 

67 (1-500 chars) plus optional `interrupted_at: datetime | None` 

68 (operator's best guess at when the actual interruption happened; 

69 distinct from `occurred_at` which is when truncation was 

70 processed). The system itself does not detect de-facto-dead 

71 Runs; operators must call truncate explicitly. Stale-RUNNING 

72 detection is a separate liveness concern (out of scope). 

73 

74Why complete_run is single-source while abort/stop are multi- 

75source (gate-review 6f-3 Q1 lock): completion claims achievement, 

76which requires active work. Exits don't require active work, only 

77any non-terminal state. The asymmetry isn't arbitrary — it 

78reflects the semantic difference between positive achievement and 

79controlled / emergency termination. 

80 

81Phase history: 

82 - 6f-1: Run + start_run + get_run (the keystone slice) ✅ 

83 - 6f-2: complete_run + abort_run (terminal happy + emergency 

84 exit) ✅ 

85 - 6f-3: hold_run + resume_run + stop_run (pause cycle + 

86 controlled-exit terminal) ✅ 

87 - 6f-4: truncate_run (partial-data terminal for known-dead Runs 

88 being closed retroactively; closes the lifecycle FSM) ✅ 

89 - 6f-5 (deferred): Additional observation channels + per-frame 

90 trigger channel (high-cardinality telemetry); when Run gains 

91 logbooks, truncate_run extends to auto-close them per gate- 

92 review L4. 

93 

94Known gaps (early sequencing decisions, accepted by design): 

95 - **Supply availability check** (Track B Supply BC not shipped): 

96 Run-start does NOT verify beam / power / gas availability today. 

97 Operator-trusted; documented as gap. Lands when Supply BC ships. 

98 - **Decision approval check** (Decision BC not shipped): 

99 Run-start does NOT require an Approved Decision referencing 

100 the Plan today. Operator-trusted; documented as gap. Lands 

101 when Decision BC ships. 

102 

103Layout (mirrors Recipe / Equipment / Trust / Subject): 

104 aggregates/run/ -- aggregate state, events union, evolver, read 

105 features/<verb>_<noun>/ -- vertical slice: command/query + decider? + handler + route + tool 

106 wire.py -- RunHandlers bundle + wire_run(deps) 

107 routes.py -- register_run_routes(app) 

108 tools.py -- register_run_tools(mcp, *, get_handlers) 

109"""
