1"""Run aggregate state, value objects, status enum, and domain errors. 

2 

3`Run` is the actual-execution layer in CORA's recipe ladder 

4(Method → Practice → Plan → **Run**). One Run = one execution 

5instance with batch identity, FSM, audit trail, and references to 

6the bound Plan + (optional) Subject. 

7 

8Per the BC map, Run is a **Lifecycle Aggregate**: terminal states 

9(`Completed`, `Aborted`, `Stopped`, `Truncated`) end the stream 

10naturally. After 6f-2+ ships those, the design implication (per 

11`project_fold_cost_principles.md`) is that the completion event 

12should carry summary state so downstream consumers don't have to 

13re-fold per-step history just to ask "what happened in Run X?". 

14 

15## Aggregate scope 

16 

17Run state: 

18 - `id` + `name` (RunName: 11th bounded-name VO) 

19 - `plan_id: UUID` — eventual-consistency ref to the Plan being 

20 executed; loaded at handler-load time for re-validation 

21 - `subject_id: UUID | None` — the Subject being measured, or 

22 None for dark-field / flat-field calibration runs (per 

23 beamline-domain convention; calibration data is consumed 

24 alongside sample data within the same analysis pipeline) 

25 - `status: RunStatus` (`Running` only at 6f-1; transitions in 

26 6f-2+) 

27 

28The active steady-state is named `Running` (not `Started`) per 

29the gerund/adjective convention used by ISA-88 / PackML 

30(`Execute`) and Bluesky beamline software (`running`). Past- 

31participle names like `Started` linguistically suggest a point- 

32in-time event, not an ongoing state — those belong on event 

33classes (`RunStarted` is correctly named) but not on the status 

34enum. See the 6f-2 gate review for the rename rationale. 

35 

36Run does NOT directly reference Asset(s) — those are reachable via 

37`plan.asset_ids`. State stays slim per Q4-style reasoning: only 

38fields decider invariants need. 

39 

40## Why subject_id is Optional (not Required) 

41 

42Beamline operations frequently include calibration runs that have 

43no Subject: 

44 - Dark-field: detector measures background noise (no beam, no sample) 

45 - Flat-field: detector measures beam profile (beam, no sample) 

46 - Energy calibration: standard reference samples (different from 

47 user Subject) 

48 

49These produce data consumed by the analysis pipeline for actual 

50sample Runs. They share the Run lifecycle, audit, and FSM with 

51sample runs — only the Subject binding differs. Modeling them as 

52the same aggregate with `subject_id: UUID | None` is cleaner than 

53a discriminator field or a separate `CalibrationRun` aggregate. 

54 

55Confirmed by Bluesky / beamline-software domain research: dark- 

56field acquisition is "an integral part of beamline operations". 

57Subject-optional Run is the right modeling choice. 

58 

59## Cross-aggregate validation at Run-start (gate-review Q2 / Q5) 

60 

61The `start_run` handler pre-loads Plan + Subject (if subject_id) + 

62each bound Asset (from `plan.asset_ids`), bundles them into a 

63`RunStartContext`, and hands it to the pure decider. The decider 

64treats them as opaque domain data and validates: 

65 

66 - state must be None (defensive: stream collision) 

67 - plan must not be Deprecated 

68 - subject (if present) must be in {Mounted, Measured} 

69 - no bound Asset may be Decommissioned 

70 - capability superset RE-VALIDATED: union(asset.capabilities) ⊇ 

71 method.needs_capabilities (from current Asset state, not the 

72 Plan-bind snapshot — drift is real and Run is the last gate) 

73 - name validation (via RunName VO) 

74 

75Same canonical pattern as `PlanBindingContext` (6e-1). Documented 

76in CONTRIBUTING.md as the cross-aggregate-validation idiom. 

77 

78## Status as enum-in-state, derived-from-event-type-in-evolver 

79 

80Same precedent as Method / Practice / Plan / Capability / 

81Subject / Asset. RunStatus is a `StrEnum`; the evolver derives 

82the new status from the event TYPE per match arm. Status is NOT 

83carried in event payloads. 

84 

85## Eleventh bounded-name VO 

86 

87`RunName` calls the shared `validate_bounded_text` helper hoisted in 

886e-1 (`cora.infrastructure.bounded_text`). Same pattern as the prior 10. 

89 

90## Known gaps documented (gate-review Q3) 

91 

92 - **No Supply availability check**: Track B Supply BC not shipped; 

93 Run-start does NOT verify beam/power/gas availability. Lands 

94 when Supply BC ships. 

95 - **No Decision approval check**: Decision BC not shipped; Run- 

96 start does NOT require an Approved Decision. Lands when 

97 Decision BC ships. 

98"""

114class RunStatus(StrEnum): 

115 """The Run's lifecycle state. 

116 

117 6f-4 closes the FSM with the partial-data terminal. The full 

118 set is now: Running plus the Held pause-state plus four 

119 reachable terminals (Completed, Aborted, Stopped, Truncated). 

120 

121 Running (6f-1) 

122 ⇄ Held (6f-3 hold/resume; bidirectional cycle, unlimited) 

123 → Completed (6f-2 happy-path; single-source from Running) 

124 → Aborted (6f-2 emergency; multi-source from Running | Held) 

125 → Stopped (6f-3 controlled exit; multi-source from Running | Held) 

126 → Truncated (6f-4 partial-data terminal; multi-source from 

127 Running | Held) 

128 

129 Stopped vs Truncated (6f-4 lifecycle-layer distinction): 

130 Stopped is a controlled exit while the system is responsive and 

131 the operator decides to end the Run early; data up to the stop 

132 point is valid. Truncated is a cleanup terminal for a Run that 

133 became known-dead through interruption (power loss, process 

134 crash, hardware fault) and is being closed retroactively. The 

135 Run was already de-facto over before the operator could mark 

136 it; truncation captures that fact plus the operator's best 

137 guess at when the actual interruption occurred (optional 

138 interrupted_at on RunTruncated). The system does not detect 

139 de-facto-dead Runs itself today (gate-review L4-followup); 

140 operators must call truncate explicitly. 

141 

142 Why complete_run is single-source while stop/abort_run are 

143 multi-source (gate-review 6f-3 Q1 lock): completion claims 

144 achievement, which requires active work happening at the 

145 moment of completion. Stop and abort are exits — they don't 

146 require active work, only any non-terminal state. Operators 

147 wanting to mark a held run as complete must Resume → Complete, 

148 which preserves clearer audit semantics than a bare Held → 

149 Complete transition. 

150 

151 Plus transient states (Starting, Stopping, Aborting, 

152 Holding, Unholding, Completing) get evaluated when DAQ-channel 

153 integration arrives (6f-5+) — only added if there's a real 

154 async period between command-arrival and event-emit at the 

155 application layer (today there isn't). 

156 

157 Naming convention (per 6f-2 gate review): gerund / adjective 

158 for the active steady-state (matches ISA-88 / PackML's 

159 `Execute` and Bluesky's `running`); past-participle for 

160 pause-state and terminals (`Held`, `Completed`, `Aborted`, 

161 `Stopped`) consistent with our own Subject precedent. 

162 

163 Enum values are PascalCase strings (matches BC-map status 

164 vocabulary; log lines and DTOs read naturally without mapping). 

165 """
