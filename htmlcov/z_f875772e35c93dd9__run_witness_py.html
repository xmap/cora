1"""RunWitness runtime: shadow-observe an external tool's captures, and 

2(behind a second, independent kill switch) promote a BEGUN capture to a 

3real witnessed Run. 

4 

5Background loop draining a `CaptureObserver` and logging each 

6observation's classified phase. Shadow mode (the default, and the only 

7behavior until `Settings.run_witness_recording_enabled` is turned on) 

8writes nothing anywhere, ever: no event append, no entries-table write, 

9no Run command issued. When recording is enabled, a `BEGUN` observation 

10for a capture with no open Run promotes one via `record_witnessed_run`, 

11with per-capture-code dedup so a single in-progress capture is never 

12promoted twice (see `RunWitnessRecorder`). 

13 

14Hosted at the composition root (`cora.api`), like `_run_initiator.py` 

15and `_enclosure_permit_observer.py`: it composes a Run BC command with 

16an Agent principal, and only `cora.api` may depend on both. 

17 

18## Log lines, one per observation 

19 

20- `run_witness.capture_begun` 

21- `run_witness.capture_progressing` 

22- `run_witness.capture_ended` 

23- `run_witness.capture_aborted` 

24- `run_witness.capture_unrecognized`: `phase` is `UNRECOGNIZED`, meaning 

25 `reported_status` did not match the deployment's declared literal 

26 table. A vocabulary drift (a tool upgrade renaming a status), not 

27 routine progress; worth an operator's attention. 

28- `run_witness.capture_unreached`: `phase` is `None`, meaning this 

29 observation made no status claim at all (a probe-only re-affirmation 

30 read, or a disconnect the adapter reported with nothing to classify). 

31 

32Every line carries `capture_code`, `reported_status`, `source_kind`, 

33`source_id`, and `observed_at` (nullable; see `CaptureLifecycleObservation`'s 

34own docstring on why an adapter must never substitute a synthesized 

35time for an absent one). These log lines are unconditional: they fire 

36identically whether or not recording is enabled. 

37 

38## Coverage trail (slice 16), independent of the recording switch 

39 

40Every observation reaching `RunWitnessRecorder.observe_capture` also 

41writes one `CaptureProbe` row (see `cora.run.aggregates.run.capture_probes` 

42for the full design argument), gated on its OWN kill switch, 

43`Settings.capture_probe_recording_enabled` -- NOT on 

44`run_witness_recording_enabled`. This is deliberate: the trail's value 

45is realized specifically while recording is off, since it scopes on 

46`capture_code` rather than a promoted Run's id. The write happens 

47BEFORE the `run_witness_recording_enabled` early-return below, mirrors 

48`enclosure._monitor.record_observation`'s failure posture exactly (skip 

49with a log line while `deps.schema_posture == "degraded"`; otherwise 

50catch, log, and continue on any other exception -- never raise into the 

51drain loop), and never suppresses the log line above it or the 

52promotion/termination logic below it. 

53 

54## Promotion and termination (when run_witness_recording_enabled is True) 

55 

56Per capture_code, a small dedup state machine: 

57 

58 - `BEGUN` while no Run is open for this code: call `record_witnessed_run` 

59 and, on success, remember the returned run_id as OPEN. On failure 

60 (any raised error, including an authorization misconfiguration), 

61 log and stay unopened so the next `BEGUN` retries. On success, also 

62 call the configured `CaptureBaselineReader` (slice 12) exactly once 

63 to snapshot the genesis-baseline PVs against the new Run; a failure 

64 there is logged and never unwinds the promotion that already 

65 committed (see `RunWitnessRecorder._read_baseline`). Also calls the 

66 configured `CaptureExperimentIdentityReader` (slice 14a) exactly once, same 

67 posture, to vault the proposal / ESAF / ESAF-DOI PVs against the new 

68 Run (see `RunWitnessRecorder._read_experiment_identity`). Before the 

69 `RecordWitnessedRun` command is even built, consumes the retained 

70 `orchestrator_ref` reading for this code (if any) through the 

71 consume-once staleness guard, so the promoted Run's genesis can 

72 carry an external orchestrator's own run identifier as a second 

73 `external_refs` entry (see "Orchestrator-ref pairing" below). 

74 - `BEGUN` while a Run is already open for this code: the previous 

75 terminal was missed (dropped CA transition, or the substrate 

76 restarted mid-capture). `TruncateRun` the stale Run first 

77 (`interrupted_at=None`: CORA does not know when it actually ended, 

78 only that it did not see the terminal), then promote the new 

79 capture as if idle. A truncate failure does not block the 

80 promotion: the new capture is a real fact regardless of whether the 

81 stale Run could be closed. 

82 - `ENDED` / `ABORTED` while a Run is open: call 

83 `record_witnessed_run_outcome` (`Ended` -> `RunCompleted`, 

84 `Aborted` -> `RunAborted`), carrying the observation's own 

85 `observed_at`. On success, clear the local dedup entry. On failure, 

86 leave the entry open: the next `BEGUN` for this code truncates it 

87 and promotes fresh, so the truncation path doubles as retry. 

88 - `ENDED` / `ABORTED` while nothing is open, or `PROGRESSING` / 

89 `UNRECOGNIZED` / a `None` phase in any state: no-op. 

90 

91`RunWitnessRecorder`'s dedup state is seeded once at boot (see 

92`rebuild_open_captures`) from every currently-Running Witnessed Run's 

93`external_refs`, so a still-open capture at process restart is never 

94re-promoted.

96## Closing the abort/success gap needs a deployment change too 

97 

98`CaptureLifecycleObservation.phase` classifies the `status` role's literal off 

99the deployment's declared table, and separately, `ControlPortCaptureObserver` 

100now also reads an optional `abort` role: a decoded-asserted reading on 

101it is a direct `ABORTED` claim (see that module's docstring), landing 

102here as a terminal `_record_outcome` call ahead of whatever the 

103`status` PV says next. At 2-BM, `fly_scan()`'s exception handlers for 

104`ScanAbortError` / `CameraTimeoutError` / `FileOverwriteError` still 

105run `finally: self.end_scan()`, which writes the identical 

106`'Scan complete'` literal a genuine success writes. 

107 

108The `abort` role only closes ONE of those three. `AbortScan` is written 

109only by `abort_scan()` (upstream `tomoscan.py`), itself reachable only 

110by an operator or automation writing to that PV directly; that is the 

111path that raises `ScanAbortError`. `CameraTimeoutError` and 

112`FileOverwriteError` write to NO PV at all before `end_scan()`'s 

113`'Scan complete'`, so no role this observer can subscribe to 

114distinguishes them from a genuine success (see tomography/tomoscan#181, 

115filed against this gap directly). `capture_progress_snapshot` on the 

116resulting `RunCompleted` is the complementary, deployment-independent 

117mitigation: the retained `collected` / `saved` counts are evidence a 

118reader can weigh even when no role fired, though (per that VO's own 

119docstring) they are evidence, never a verdict CORA computes itself. 

120 

121The `abort` role's code capability exists as of the commit that added 

122it; the operator-abort slice of the gap only closes once a 

123deployment's `capture_watch_pvs` also declares the role for each code 

124(2-BM: `"abort": "2bmb:TomoScan:AbortScan"`). A code with no `abort` 

125entry watches `status` only, unchanged, so `ENDED` still unconditionally 

126maps to `RunCompleted` for it. Nothing in this file or in `Settings` 

127gates recording on the abort role being configured; the locked 

128deployment decision is to keep `run_witness_recording_enabled` off at 

1292-BM until both this effort's code and its own deployment config 

130change (adding the `abort` role) are live.

132## Accepted residual: a reconnect can misread a still-open capture as new 

133 

134The `BEGUN`-while-open heuristic assumes a second `BEGUN` for the same 

135code always means the prior terminal was missed. That is not quite 

136total: `camonitor`-style subscriptions deliver the PV's CURRENT value 

137immediately on a fresh subscribe (see `EpicsCaControlPort`), and the 

138observer resubscribes after every disconnect (see "Retry + resilience" 

139below). If a reconnect happens to land in the narrow window where the 

140substrate's status PV still genuinely reads the `BEGUN` literal for a 

141capture that has not actually restarted, this recorder cannot tell that 

142apart from a real new capture: it truncates the still-live Run 

143(spurious `RunTruncated`) and promotes a duplicate. The window is the 

144duration of one `BEGUN`-classified literal (milliseconds, per the 

145measured arcturus phase durations), and the outcome is a data-quality 

146degradation (an extra Run pair for one physical scan), not a control or 

147interlock concern. No narrower signal (comparing against the 

148last-observed reading, or `reach_tier`) is implemented; revisit if this 

149is ever observed in practice. 

150 

151## Accepted residual: the `status` and `abort` pumps have no enforced ordering 

152 

153`_capture_observer.py` runs the `status` and `abort` roles as two 

154independent pumps feeding one merged queue; nothing in this file or 

155that one enforces that an `ABORTED` reading is processed before a 

156later, causally-dependent `ENDED` reading from the other pump, only 

157that it usually will be, because 2-BM's own `abort_scan()` writes 

158`AbortScan` before its caller's `finally: end_scan()` writes 

159`ScanStatus`. This is a real ordering dependency on realistic, 

160network-driven CA delivery interleaving the two subscriptions fairly, 

161not a structural guarantee; a deliberately adversarial or bursty 

162delivery pattern (confirmed by constructing exactly this case against 

163a fake `ControlPort` that does not yield between readings, in 

164`test_run_witness_capture_replay.py`) could let the trailing `ENDED` 

165arrive first, in which case that capture records as `Completed` and 

166the correct `ABORTED` observation lands on the now-idle no-open-Run 

167path, a no-op. Same outcome, same severity, as the coalesced-abort 

168residual in `_capture_observer.py`'s own docstring: a real 2-BM abort 

169degrading to a `Completed` record, never a corrupted attribution to a 

170different Run.

172## Accepted residual (slice 10): a post-restart missed terminal writes a trail into the wrong Run 

173 

174The reconnect-during-BEGUN residual above already accepts that a 

175process restart mid-capture can leave a stale Run open with nothing to 

176truncate it until the NEXT capture's `BEGUN`. Before slice 10 that 

177window produced at most one wrong terminal event. With the progress 

178feeder wired, every flush tick during that window writes the NEW 

179capture's `images_saved` / `images_collected` readings into the STALE 

180Run's observation trail, because `rebuild_open_captures` seeds 

181`code -> stale_run_id` at boot and camonitor's first delivery on a 

182fresh subscribe is whatever literal the PV currently holds -- typically 

183a `PROGRESSING` one mid-capture, which triggers no `BEGUN` and so never 

184corrects the map. Detectable signature: the channel's value regresses 

185against the prior rows for the same Run instead of monotonically 

186increasing. Accepted rather than fixed here: closing it needs either a 

187staleness timer (explicitly out of scope per the locked slice-9 

188decision) or a monotonicity guard per (run_id, channel), which is a 

189real fix but a separate, deliberate design decision, not a wiring 

190change.

192## Accepted residual (slice 10): CA's redeliver-on-resubscribe can misattribute a stale reading 

193 

194If a reconnect lands between a new capture's `BEGUN` and its first 

195progress update, EPICS CA can redeliver the PREVIOUS capture's final 

196progress string with the PREVIOUS capture's own substrate timestamp on 

197the fresh subscribe. That reading is buffered under the current 

198capture_code and, having a real (if stale) `observed_at`, is not 

199skipped by the no-substrate-time guard; the next flush writes it 

200against the NEW Run, one row bearing an out-of-order timestamp lower 

201than the Run's own start. Same class as the reconnect-during-BEGUN 

202residual above (an artifact of CA's own resubscribe semantics, not a 

203bug in this code), and the same posture: a data-quality degradation 

204(one out-of-order row), never a claim this code cannot tell is 

205suspect. No freshness guard (rejecting a reading whose `observed_at` 

206predates the Run's own promotion) is implemented; it would need 

207threading a promotion timestamp through `RunWitnessRecorder`, a real 

208fix but, again, a deliberate design decision to make later if this is 

209ever observed in practice, not a wiring change.

211## Capture path pairing (slice 13) 

212 

213Closes the "which file did this Run produce" findability gap (auto- 

214correlation stays deferred; this only makes the manual pairing 

215possible). Source is the areaDetector file plugin's own filename 

216readback (`full_file_name` role, `_capture_observer.py`), NOT 

217tomoscan's own `FullFileName`: upstream `tomoscan.py`'s `end_scan()` 

218writes `ScanStatus='Scan complete'` (CORA's terminal) FOUR statements 

219BEFORE it writes `FullFileName`, so a synchronous read at the terminal 

220against that PV would return the PREVIOUS scan's filename. The 

221areaDetector PV is written at file OPEN, i.e. before the terminal, so 

222it does not have this race -- but "written before the terminal" is not 

223by itself sufficient: the file plugin also fires independently of any 

224one capture, so a value retained from a PREVIOUS capture (or a 

225reconnect redelivering one) could still be sitting in 

226`_last_capture_path` when THIS capture's terminal arrives. 

227 

228The guard: `_promote` records the BEGUN observation's OWN substrate 

229time into `_begun_at[code]` (never CORA's clock -- comparing two 

230substrate timestamps from the same control system avoids a 

231CORA-host-vs-IOC clock-skew question this guard does not need to 

232answer). At the terminal, `_resolve_capture_path` accepts the retained 

233reading only if its `observed_at` is at or after that value. This is 

234the freshness guard the "CA's redeliver-on-resubscribe" residual above 

235names as a real fix "if this is ever observed in practice" for 

236progress readings -- implemented here, scoped to this one role, because 

237Finding A makes it load-bearing rather than optional: without it, this 

238feature would silently pair Runs with the WRONG file on every 

239reconnect-during-BEGUN window, not just degrade one row's ordering. 

240 

241`observed_path` is personal data (2-BM's directory layout embeds a 

242surname and a proposal number,`tomoscan_2bm.py:474-477`), so it is 

243never written to `RunCompleted` / `RunAborted` or any other event: it 

244goes to the `run_capture_path` PII vault (`CapturePathStore`, 

245mirroring `actor_profile` / `ProfileStore`) via `_write_capture_path`, 

246called at the end of `_record_outcome`'s success branch -- the outcome 

247has already committed by then, so (mirroring `_read_baseline`'s exact 

248posture) a vault-write failure is logged and never unwinds it. Gated 

249on the fifth kill switch, `capture_path_recording_enabled`. No log 

250line in this section ever includes `observed_path` itself; only 

251`capture_code` / `run_id` / lengths.

253## Orchestrator-ref pairing 

254 

255Joins a witnessed Run to an external orchestrator's own run identifier 

256for the same capture (e.g. a Bluesky RunEngine start-document uid), 

257carried as a second `external_refs` entry on `RunStarted` alongside 

258`capture-code`. Closes the "which Bluesky run produced this CORA Run" 

259findability gap the same way slice 13 closes the file-identity one; 

260CORA still never talks to the orchestrator directly, it only reads 

261whatever run identifier the orchestrator wrote to the substrate before 

262triggering the act `CaptureObserver` watches. 

263 

264The ordering is the INVERSE of the capture-path guard above: a run uid 

265is written BEFORE the capture it names begins, never after, so there 

266is no "did the file open before or after BEGUN" question here -- the 

267question is "did this retained uid lead the current BEGUN by a 

268plausible amount, or is it a stale leftover from some earlier capture 

269whose BEGUN this recorder never saw close it out." 

270 

271The guard, in `_consume_orchestrator_ref`: a retained reading is 

272CONSUMED (popped, never merely read) the moment a `BEGUN` for its 

273capture code is promoted, whether or not the reading passes the 

274checks below -- the structural fix, not a heuristic. A reading that 

275fails a check is simply gone; it cannot be reused by a LATER capture 

276the way a bug in a peek-without-pop implementation would allow. Then, 

277only if consumption returned something: 

278 

279 - `observed_at` must be present on both the retained reading and 

280 the current BEGUN. Either missing means there is no substrate time 

281 to compare, so the guard fails closed (mirrors `_resolve_capture_ 

282 path`'s identical posture when `_begun_at` has no entry). 

283 - The lead (`begun_at - observed_at`) must be non-negative: a 

284 negative lead means the uid reading's own substrate timestamp is 

285 AFTER this BEGUN's, which should not happen if the orchestrator 

286 writes its uid first, and signals either substrate clock skew 

287 between two channels or the two pumps having delivered out of 

288 their causal order (see the residual below). 

289 - The lead must not exceed `capture_orchestrator_ref_max_lead_ 

290 seconds` (deployment-declared, not hardcoded): a uid retained far 

291 longer than a real orchestrator-to-BEGUN gap is more likely a 

292 stale leftover from a capture whose own BEGUN this recorder never 

293 promoted (a reconnect, or a non-orchestrator-driven scan that 

294 started while the substrate still held the previous run's uid) 

295 than genuine evidence for the current one. 

296 - The `(scheme, value)` pair must construct a valid `Identifier`: 

297 `Identifier.__post_init__` bounds both fields' length and rejects 

298 empty/whitespace-only text, the same validation `capture-code` 

299 itself is subject to. 

300 

301Gated on the TENTH kill switch, `capture_orchestrator_ref_recording_enabled`, 

302independently of `run_witness_recording_enabled`'s sibling switches for 

303the personal-data-adjacent roles: unlike an observed capture path, a 

304run uid is not personal data, but it IS a second identity a facility 

305may want to withhold from the record independently of witnessing 

306itself (e.g. while `tomo-bits`' own plan is still being validated 

307against production). Retention (`observe_orchestrator_ref`) is gated 

308only on `run_witness_recording_enabled`, matching 

309`observe_capture_path`'s declare-vs-record split, so flipping the 

310tenth switch later does not miss whatever was already retained. 

311 

312### Accepted residual: a stray scan inside the lead-time window can inherit a stale ref 

313 

314The lead-time bound above narrows the exposure but does not close it: 

315if the orchestrator writes a uid, its own process is killed before it 

316clears the PV (a `finally` never runs), and a DIFFERENT tool starts a 

317real scan on the SAME capture code within the configured lead-time 

318window, this recorder cannot tell the two apart -- it attaches the 

319stale-but-recent uid to a Run the orchestrator never actually drove. 

320Same severity class as the reconnect-during-BEGUN residual above (a 

321data-quality degradation: one Run carries a ref that does not 

322describe it, never a corrupted attribution to a DIFFERENT Run's 

323event stream), and the same posture: no narrower signal is 

324implemented here; revisit if this is ever observed in practice. 

325 

326### Accepted residual: the orchestrator-ref and status pumps have no enforced ordering 

327 

328Mirrors the accepted `status`/`abort` pump-ordering residual above 

329exactly, for the same structural reason (`_capture_observer.py` runs 

330one pump per role, all feeding one unordered merge queue): if a 

331reconnect or an adversarial delivery pattern lets a capture's own 

332`BEGUN` reading reach this recorder BEFORE its paired 

333`orchestrator_ref` reading (despite the orchestrator having 

334written the uid to the substrate first), `_promote` finds nothing 

335retained and the Run promotes with no orchestrator ref at all -- never 

336a wrong one. The uid reading, arriving moments later, is then retained 

337for whatever capture comes NEXT, which is exactly the stale-leftover 

338shape the lead-time bound above exists to catch on that next 

339promotion. 

340 

341## Retry + resilience 

342 

343Mirrors `run_enclosure_permit_monitor`: `observe()` ending (stream 

344terminated or raised) triggers a bounded sleep then re-subscribe. A 

345single bad observation is logged and skipped so the loop survives it. 

346Cancellation (lifespan shutdown) propagates. 

347 

348## No startup-readiness gate 

349 

350`enclosure_permit_monitor_lifespan` waits for a settled read before 

351yielding because a real precondition (the run-start preflight) reads 

352`permit_status` right after boot. Nothing downstream depends on this 

353runtime settling, so there is no boot race to close and no wait is 

354needed.

814 """

816 begun_at = self._begun_at.get(code) 

817 if observation is None or begun_at is None: 

818 return None 

819 if observation.observed_at is None or observation.observed_at < begun_at: 

820 return None 

821 return observation.observed_path, observation.observed_at

850 def _consume_orchestrator_ref(self, code: str, begun_at: datetime | None) -> Identifier | None: 

851 """Pop and validate the retained `orchestrator_ref` reading 

852 for `code`, applying the lead-time guard (see "Orchestrator-ref 

853 pairing" above). ALWAYS pops, whether the guard passes or not: 

854 a rejected reading must not survive to be reused by a LATER 

855 promotion -- the structural fix this module's docstring 

856 describes, not a heuristic. 

857 

858 `begun_at` is the CURRENT BEGUN's own substrate time (already 

859 recorded into `self._begun_at[code]` by the caller before this 

860 runs), never CORA's clock, mirroring `_resolve_capture_path`'s 

861 identical choice to compare two substrate timestamps rather 

862 than involve a CORA-host-vs-IOC clock-skew question this guard 

863 does not need to answer. 

864 

865 Returns `None` on any rejection (nothing retained, no 

866 reference time to compare against, a negative or over-bound 

867 lead, or a malformed `(scheme, value)` pair); every rejection 

868 branch logs its own reason. `None` is a legitimate, expected 

869 outcome on most captures (no orchestrator involved at all), so 

870 the caller must not treat it as an error, only as "no ref to 

871 attach." 

872 """ 

873 observation = self._last_orchestrator_ref.pop(code, None) 

874 if observation is None: 

875 return None 

876 if begun_at is None or observation.observed_at is None: 

877 _log.warning( 

878 "run_witness.orchestrator_ref_rejected_no_reference_time", 

879 capture_code=code, 

880 ) 

881 return None 

882 lead_seconds = (begun_at - observation.observed_at).total_seconds() 

883 if lead_seconds < 0: 

884 _log.warning( 

885 "run_witness.orchestrator_ref_rejected_reordered", 

886 capture_code=code, 

887 lead_seconds=lead_seconds, 

888 ) 

889 return None 

890 if lead_seconds > self._settings.capture_orchestrator_ref_max_lead_seconds: 

891 _log.warning( 

892 "run_witness.orchestrator_ref_rejected_stale", 

893 capture_code=code, 

894 lead_seconds=lead_seconds, 

895 ) 

896 return None 

897 try: 

898 return Identifier(scheme=observation.scheme, value=observation.value) 

899 except InvalidIdentifierError: 

900 _log.warning( 

901 "run_witness.orchestrator_ref_rejected_malformed", 

902 capture_code=code, 

903 ) 

904 return None

923 # nothing to compare against; a stale prior entry must not

925 # promotion (see `_resolve_capture_path`).
