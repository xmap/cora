1"""RunWitness runtime: shadow-observe an external tool's captures, and 

2(behind a second, independent kill switch) promote a BEGUN capture to a 

3real witnessed Run. 

4 

5Background loop draining a `CaptureObserver` and logging each 

6observation's classified phase. Shadow mode (the default, and the only 

7behavior until `Settings.run_witness_recording_enabled` is turned on) 

8writes nothing anywhere, ever: no event append, no entries-table write, 

9no Run command issued. When recording is enabled, a `BEGUN` observation 

10for a capture with no open Run promotes one via `record_witnessed_run`, 

11with per-capture-code dedup so a single in-progress capture is never 

12promoted twice (see `RunWitnessRecorder`). 

13 

14Hosted at the composition root (`cora.api`), like `_run_initiator.py` 

15and `_enclosure_permit_observer.py`: it composes a Run BC command with 

16an Agent principal, and only `cora.api` may depend on both. 

17 

18## Log lines, one per observation 

19 

20- `run_witness.capture_begun` 

21- `run_witness.capture_progressing` 

22- `run_witness.capture_ended` 

23- `run_witness.capture_aborted` 

24- `run_witness.capture_unrecognized`: `phase` is `UNRECOGNIZED`, meaning 

25 `reported_status` did not match the deployment's declared literal 

26 table. A vocabulary drift (a tool upgrade renaming a status), not 

27 routine progress; worth an operator's attention. 

28- `run_witness.capture_unreached`: `phase` is `None`, meaning this 

29 observation made no status claim at all (a probe-only re-affirmation 

30 read, or a disconnect the adapter reported with nothing to classify). 

31 

32Every line carries `capture_code`, `reported_status`, `source_kind`, 

33`source_id`, and `observed_at` (nullable; see `CaptureLifecycleObservation`'s 

34own docstring on why an adapter must never substitute a synthesized 

35time for an absent one). These log lines are unconditional: they fire 

36identically whether or not recording is enabled. 

37 

38## Promotion and termination (when run_witness_recording_enabled is True) 

39 

40Per capture_code, a small dedup state machine: 

41 

42 - `BEGUN` while no Run is open for this code: call `record_witnessed_run` 

43 and, on success, remember the returned run_id as OPEN. On failure 

44 (any raised error, including an authorization misconfiguration), 

45 log and stay unopened so the next `BEGUN` retries. 

46 - `BEGUN` while a Run is already open for this code: the previous 

47 terminal was missed (dropped CA transition, or the substrate 

48 restarted mid-capture). `TruncateRun` the stale Run first 

49 (`interrupted_at=None`: CORA does not know when it actually ended, 

50 only that it did not see the terminal), then promote the new 

51 capture as if idle. A truncate failure does not block the 

52 promotion: the new capture is a real fact regardless of whether the 

53 stale Run could be closed. 

54 - `ENDED` / `ABORTED` while a Run is open: call 

55 `record_witnessed_run_outcome` (`Ended` -> `RunCompleted`, 

56 `Aborted` -> `RunAborted`), carrying the observation's own 

57 `observed_at`. On success, clear the local dedup entry. On failure, 

58 leave the entry open: the next `BEGUN` for this code truncates it 

59 and promotes fresh, so the truncation path doubles as retry. 

60 - `ENDED` / `ABORTED` while nothing is open, or `PROGRESSING` / 

61 `UNRECOGNIZED` / a `None` phase in any state: no-op. 

62 

63`RunWitnessRecorder`'s dedup state is seeded once at boot (see 

64`rebuild_open_captures`) from every currently-Running Witnessed Run's 

65`external_refs`, so a still-open capture at process restart is never 

66re-promoted. 

67 

68## Closing the abort/success gap needs a deployment change too 

69 

70`CaptureLifecycleObservation.phase` classifies the `status` role's literal off 

71the deployment's declared table, and separately, `ControlPortCaptureObserver` 

72now also reads an optional `abort` role: a decoded-asserted reading on 

73it is a direct `ABORTED` claim (see that module's docstring), landing 

74here as a terminal `_record_outcome` call ahead of whatever the 

75`status` PV says next. At 2-BM, `fly_scan()`'s exception handlers for 

76`ScanAbortError` / `CameraTimeoutError` / `FileOverwriteError` still 

77run `finally: self.end_scan()`, which writes the identical 

78`'Scan complete'` literal a genuine success writes. 

79 

80The `abort` role only closes ONE of those three. `AbortScan` is written 

81only by `abort_scan()` (upstream `tomoscan.py`), itself reachable only 

82by an operator or automation writing to that PV directly; that is the 

83path that raises `ScanAbortError`. `CameraTimeoutError` and 

84`FileOverwriteError` write to NO PV at all before `end_scan()`'s 

85`'Scan complete'`, so no role this observer can subscribe to 

86distinguishes them from a genuine success (see tomography/tomoscan#181, 

87filed against this gap directly). `capture_progress_snapshot` on the 

88resulting `RunCompleted` is the complementary, deployment-independent 

89mitigation: the retained `collected` / `saved` counts are evidence a 

90reader can weigh even when no role fired, though (per that VO's own 

91docstring) they are evidence, never a verdict CORA computes itself. 

92 

93The `abort` role's code capability exists as of the commit that added 

94it; the operator-abort slice of the gap only closes once a 

95deployment's `capture_watch_pvs` also declares the role for each code 

96(2-BM: `"abort": "2bmb:TomoScan:AbortScan"`). A code with no `abort` 

97entry watches `status` only, unchanged, so `ENDED` still unconditionally 

98maps to `RunCompleted` for it. Nothing in this file or in `Settings` 

99gates recording on the abort role being configured; the locked 

100deployment decision is to keep `run_witness_recording_enabled` off at 

1012-BM until both this effort's code and its own deployment config 

102change (adding the `abort` role) are live. 

103 

104## Accepted residual: a reconnect can misread a still-open capture as new 

105 

106The `BEGUN`-while-open heuristic assumes a second `BEGUN` for the same 

107code always means the prior terminal was missed. That is not quite 

108total: `camonitor`-style subscriptions deliver the PV's CURRENT value 

109immediately on a fresh subscribe (see `EpicsCaControlPort`), and the 

110observer resubscribes after every disconnect (see "Retry + resilience" 

111below). If a reconnect happens to land in the narrow window where the 

112substrate's status PV still genuinely reads the `BEGUN` literal for a 

113capture that has not actually restarted, this recorder cannot tell that 

114apart from a real new capture: it truncates the still-live Run 

115(spurious `RunTruncated`) and promotes a duplicate. The window is the 

116duration of one `BEGUN`-classified literal (milliseconds, per the 

117measured arcturus phase durations), and the outcome is a data-quality 

118degradation (an extra Run pair for one physical scan), not a control or 

119interlock concern. No narrower signal (comparing against the 

120last-observed reading, or `reach_tier`) is implemented; revisit if this 

121is ever observed in practice. 

122 

123## Accepted residual: the `status` and `abort` pumps have no enforced ordering 

124 

125`_capture_observer.py` runs the `status` and `abort` roles as two 

126independent pumps feeding one merged queue; nothing in this file or 

127that one enforces that an `ABORTED` reading is processed before a 

128later, causally-dependent `ENDED` reading from the other pump, only 

129that it usually will be, because 2-BM's own `abort_scan()` writes 

130`AbortScan` before its caller's `finally: end_scan()` writes 

131`ScanStatus`. This is a real ordering dependency on realistic, 

132network-driven CA delivery interleaving the two subscriptions fairly, 

133not a structural guarantee; a deliberately adversarial or bursty 

134delivery pattern (confirmed by constructing exactly this case against 

135a fake `ControlPort` that does not yield between readings, in 

136`test_run_witness_capture_replay.py`) could let the trailing `ENDED` 

137arrive first, in which case that capture records as `Completed` and 

138the correct `ABORTED` observation lands on the now-idle no-open-Run 

139path, a no-op. Same outcome, same severity, as the coalesced-abort 

140residual in `_capture_observer.py`'s own docstring: a real 2-BM abort 

141degrading to a `Completed` record, never a corrupted attribution to a 

142different Run. 

143 

144## Accepted residual (slice 10): a post-restart missed terminal writes a trail into the wrong Run 

145 

146The reconnect-during-BEGUN residual above already accepts that a 

147process restart mid-capture can leave a stale Run open with nothing to 

148truncate it until the NEXT capture's `BEGUN`. Before slice 10 that 

149window produced at most one wrong terminal event. With the progress 

150feeder wired, every flush tick during that window writes the NEW 

151capture's `images_saved` / `images_collected` readings into the STALE 

152Run's observation trail, because `rebuild_open_captures` seeds 

153`code -> stale_run_id` at boot and camonitor's first delivery on a 

154fresh subscribe is whatever literal the PV currently holds -- typically 

155a `PROGRESSING` one mid-capture, which triggers no `BEGUN` and so never 

156corrects the map. Detectable signature: the channel's value regresses 

157against the prior rows for the same Run instead of monotonically 

158increasing. Accepted rather than fixed here: closing it needs either a 

159staleness timer (explicitly out of scope per the locked slice-9 

160decision) or a monotonicity guard per (run_id, channel), which is a 

161real fix but a separate, deliberate design decision, not a wiring 

162change. 

163 

164## Accepted residual (slice 10): CA's redeliver-on-resubscribe can misattribute a stale reading 

165 

166If a reconnect lands between a new capture's `BEGUN` and its first 

167progress update, EPICS CA can redeliver the PREVIOUS capture's final 

168progress string with the PREVIOUS capture's own substrate timestamp on 

169the fresh subscribe. That reading is buffered under the current 

170capture_code and, having a real (if stale) `observed_at`, is not 

171skipped by the no-substrate-time guard; the next flush writes it 

172against the NEW Run, one row bearing an out-of-order timestamp lower 

173than the Run's own start. Same class as the reconnect-during-BEGUN 

174residual above (an artifact of CA's own resubscribe semantics, not a 

175bug in this code), and the same posture: a data-quality degradation 

176(one out-of-order row), never a claim this code cannot tell is 

177suspect. No freshness guard (rejecting a reading whose `observed_at` 

178predates the Run's own promotion) is implemented; it would need 

179threading a promotion timestamp through `RunWitnessRecorder`, a real 

180fix but, again, a deliberate design decision to make later if this is 

181ever observed in practice, not a wiring change. 

182 

183## Retry + resilience 

184 

185Mirrors `run_enclosure_permit_monitor`: `observe()` ending (stream 

186terminated or raised) triggers a bounded sleep then re-subscribe. A 

187single bad observation is logged and skipped so the loop survives it. 

188Cancellation (lifespan shutdown) propagates. 

189 

190## No startup-readiness gate 

191 

192`enclosure_permit_monitor_lifespan` waits for a settled read before 

193yielding because a real precondition (the run-start preflight) reads 

194`permit_status` right after boot. Nothing downstream depends on this 

195runtime settling, so there is no boot race to close and no wait is 

196needed. 

197"""

266"""Phases where the recorder may close or replace a Run (slice 10). 

267`run_witness_loop` flushes a capture's buffered progress readings 

268BEFORE the recorder acts on one of these, so a reading already 

269BUFFERED at that instant is attributed to the Run it belongs to rather 

270than lost to a closed logbook or attached to the wrong Run after a 

271truncate-then-promote. This narrows the window; it does not close it: 

272`_capture_observer.py` runs a status/abort/images_saved/images_collected 

273pump per role, all feeding one unordered merge queue, and slice 9 

274already accepts that pump ordering is not structurally guaranteed, only 

275realistic CA delivery. A progress reading whose callback lands AFTER 

276this dispatch (rather than before) is either dropped 

277(`capture_progress.dropped_no_open_run`) or, on the rarer truncate-then-

680async def run_witness_loop( 

681 *, 

682 observer: CaptureObserver, 

683 capture_codes: frozenset[str], 

684 recorder: RunWitnessRecorder | None = None, 

685 feeder: CaptureProgressFeeder | None = None, 

686 reconnect_delay_seconds: float = _RECONNECT_DELAY_SECONDS, 

687) -> None: 

688 """Drain the observer, logging (and, with a recorder, promoting) 

689 each observation; re-subscribe on stream end. 

690 

691 A `CaptureProgressObservation` fans out to TWO independent sinks: 

692 `recorder.observe_progress()` (retains the latest per-role reading 

693 so a terminal can carry it as evidence; see `RunWitnessRecorder 

694 ._build_progress_snapshot`) and `feeder.offer()` (buffers it for 

695 the next `AppendObservations` flush). Order between the two is 

696 immaterial: both are synchronous and neither raises in normal 

697 operation. A `CaptureLifecycleObservation` on a phase in 

698 `_FLUSH_TRIGGER_PHASES` triggers `feeder.flush_capture()` BEFORE the 

699 recorder acts on it, so a capture's buffered progress trail is 

700 attributed to its Run before that Run can close or be replaced; 

701 this ordering is unchanged by the fan-out above; `recorder 

702 .observe_progress` retains independently of the flush and is not 

703 itself flushed. `feeder=None` (recording off, or 

704 `capture_progress_recording_enabled=False`) and `recorder=None` 

705 each make their own branch a no-op independently. 

706 """ 

707 if not capture_codes: 

708 return 

709 scope = CaptureObserverScope(capture_codes=capture_codes) 

710 while True: 

711 try: 

712 async for observation in observer.observe(scope): 

713 if isinstance(observation, CaptureProgressObservation): 

714 if recorder is not None: 

715 recorder.observe_progress(observation) 

716 if feeder is not None: 

717 feeder.offer(observation) 

718 continue 

719 if feeder is not None and observation.phase in _FLUSH_TRIGGER_PHASES: 

720 try: 

721 await feeder.flush_capture(observation.capture_code) 

722 except asyncio.CancelledError: 

723 raise 

724 except Exception: 

725 _log.exception( 

726 "run_witness.progress_flush_failed", 

727 capture_code=observation.capture_code, 

728 ) 

729 try: 

730 if recorder is not None: 

731 await recorder.observe_capture(observation) 

732 else: 

733 observe_capture(observation) 

734 except asyncio.CancelledError: 

735 raise 

736 except Exception: 

737 _log.exception( 

738 "run_witness.record_failed", 

739 capture_code=observation.capture_code, 

740 ) 

741 except asyncio.CancelledError: 

742 raise 

743 except Exception: 

744 _log.exception("run_witness.iteration_failed") 

745 await asyncio.sleep(reconnect_delay_seconds)
