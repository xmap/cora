1"""Cross-aggregate context the `define_plan` decider validates against. 

2 

3`PlanBindingContext` is built by the `define_plan` handler from 

4`load_practice` + `load_method` + `load_asset` calls before reaching 

5the pure decider. The decider treats these loaded entities as 

6opaque domain data and validates the binding without performing 

7any I/O. 

8 

9Per gate-review Q5: this is the canonical pattern for any future 

10decider that needs cross-aggregate state. The handler (impure 

11shell) loads what's needed; the decider (pure core) receives it as 

12plain values. Keeps the decider referentially transparent — same 

13inputs, same outputs, no need to mock loaders in unit tests. 

14 

15Slice-local module by design: only `define_plan` uses it today. 

16Sibling pattern: `cora.run.features.start_run.context.RunStartContext` 

17holds Plan + Subject (optional) + assets, same shape, slice- 

18specific entities. Each cross-validating slice produces its own 

19context dataclass; promote to a shared form only after the Rule of 

20Three. 

21""" 

22 

23from dataclasses import dataclass, field 

24from uuid import UUID 

25 

26from cora.equipment.aggregates.asset import Asset 

27from cora.equipment.aggregates.family import Affordance 

28from cora.recipe.aggregates.capability import Capability 

29from cora.recipe.aggregates.method import Method 

30from cora.recipe.aggregates.practice import Practice 

31 

32 

33@dataclass(frozen=True) 

34class PlanBindingContext: 

35 """Snapshot of upstream aggregate state at Plan-bind time. 

36 

37 `practice` and `method` are the two recipe-ladder ancestors the 

38 Plan binds (Practice always, Method via `practice.method_id`). 

39 `assets` is the loaded set of bound Asset instances keyed by 

40 their id. 

41 

42 All three carry their own status / lifecycle fields so the 

43 decider can reject Deprecated / Decommissioned upstreams. The 

44 family-superset check uses each Asset's `family_ids` and 

45 the Method's `needed_family_ids` (gate-review Q3: bound-Asset- 

46 only, no hierarchy walk). 

47 

48 Cross-BC affordance-cover additive: `capability` and 

49 `family_affordances` carry the Capability template + per-Family 

50 affordance summaries needed 

51 for the affordance-cover guard. 

52 

53 - `capability` is the universal Capability template the bound 

54 Method realizes (loaded via `method.capability_id`). None when 

55 Method has no `capability_id` (legacy shape), in that 

56 case the decider SKIPS the affordance-cover guard entirely. 

57 - `family_affordances` maps Family.id → that Family's `affordances` 

58 set. The handler loads every Family referenced by any bound 

59 Asset's `family_ids` set. Empty dict when `capability is None` 

60 (no point loading Families if we won't validate them). 

61 

62 The decider unions `family_affordances` across `asset.family_ids` 

63 and asserts the union covers `capability.required_affordances`. 

64 """ 

65 

66 practice: Practice 

67 method: Method 

68 assets: dict[UUID, Asset] 

69 capability: Capability | None = None 

70 family_affordances: dict[UUID, frozenset[Affordance]] = field( 

71 default_factory=dict[UUID, frozenset[Affordance]] 

72 )
