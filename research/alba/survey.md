## 1. Executive summary

Online material for ALBA is **rich on the control-system layer and facility/beamline directory, thinner on per-beamline hardware inventory, and gated for facility-internal code**. ALBA is the originating institution of the Tango-based **Sardana** experiment-control suite and the **Taurus** GUI framework, and the **IcePAP** motion controller, so the framework documentation (`sardana-controls.org`, `taurus-scada.org`) and upstream source (GitLab) are authoritative and current ([sardana users overview](https://sardana-controls.org/users/overview.html), [taurus intro](https://taurus-scada.org/users/introduction.html)). ALBA's public GitHub org ([github.com/ALBA-Synchrotron](https://github.com/ALBA-Synchrotron), 121 repos, active through June 2026) exposes device servers, Sardana plugins, beamline scan macros, and the ICAT data-catalogue stack, but **most beamline-control source of record now lives on GitLab** (`gitlab.com/sardana-org`, `gitlab.com/icepap-organization`, `gitlab.com/alba-synchrotron`), with the GitHub copies archived. The official beamline directory ([cells.es](https://www.cells.es/en/instruments/beamlines)) gives a complete, current code/name/technique roster (14 beamlines), and several beamline pages carry detailed optics/energy/detector facts; however, **per-beamline detector and motion-controller assignments are largely NOT published** and must be confirmed with ALBA staff. The biggest gaps are: ALBA's self-hosted git (`*.cells.es`, credential-gated), the User Office software product identity, and current per-beamline hardware manifests.

## 2. Control system & inventory sources

ALBA is **Tango-native**, with **Sardana** as the experiment-control/orchestration layer and **Taurus** as the operator UI. This is the floor/edge boundary a CORA deployment must model (analogous to the 2-BM EPICS-floor / TomoScan-orchestration seam, but here the floor is Tango and the orchestration is Sardana).

- **Tango (floor / device layer).** Device servers are processes implementing device classes; each device has mandatory state plus 0..N commands, attributes, pipes; a centralized MariaDB/MySQL database stores startup config and acts as name server; each system is scoped by `TANGO_HOST` ([Tango overview 9.3.4](https://tango-controls.readthedocs.io/en/9.3.4/overview/overview.html)). Tango uses CORBA (sync) + ZeroMQ (async) ([same](https://tango-controls.readthedocs.io/en/9.3.4/overview/overview.html)). *Generic Tango fact, not ALBA-specific.*
- **Sardana (orchestration / DAQ).** A Sardana Server (SDS) is a Tango device server running the Sardana kernel; it hosts a **Pool** (controllers, motors, counters, experiment channels, pseudo-motors, measurement groups, trigger/gate) and a **MacroServer** (runs macros; clients connect through **Door** objects). A single server holds at most one Pool and one MacroServer ([Sardana devel overview](https://sardana-controls.org/devel/overview/overview.html), [Pool API](https://sardana-controls.org/devel/api/api_pool.html)). Tango is the only implemented communication protocol (the protocol is a plug-in) ([devel overview](https://sardana-controls.org/devel/overview/overview.html)).
- **ALBA provenance.** Sardana was **initially developed at ALBA** (the name is a Catalan dance); it extends Tango rather than replacing it; macros are Python functions/classes auto-exposed in CLI (Spock) and GUI ([Sardana users overview](https://sardana-controls.org/users/overview.html), [sardana-controls.org home](https://sardana-controls.org/)). Backed by a consortium: ALBA, DESY, MAX IV, Solaris, ESRF ([sardana-controls.org home](https://sardana-controls.org/)). *Relevant to CORA's MAX IV growth-ladder rung.*
- **Taurus (UI / data access).** MVC Python framework, originated at CELLS/ALBA, now independent but sharing developers with Sardana; control-system-agnostic since v4 via schemes ([taurus intro](https://taurus-scada.org/users/introduction.html)). **Verified scheme set** (refuting an earlier "h5file scheme" claim): `taurus.core` ships `tango` (`tango://`, `tango-nodb`), `epics` (`ca`, `epics`), `evaluation` (`eval`, `evaluation`), and `resource` (`res`, `resource`), there is **no h5file core scheme** ([verified via GitLab source](https://gitlab.com/api/v4/projects/taurus-org%2Ftaurus/repository/tree?path=lib/taurus/core&ref=develop)).

### Device / motor modeling (inventory shape for CORA)
- **Controller->axis is one-to-many**: a `MotorController` subclass manages many integer-indexed axes; each axis becomes an independent Tango device with its own alias. Lifecycle via `AddDevice(axis)`/`DeleteDevice(axis)`; per-axis methods `ReadOne`/`StateOne`/`StartOne`/`StopOne`/`AbortOne` ([motor controller how-to](https://sardana-controls.org/devel/howto_controllers/howto_motorcontroller.html)).
- **Standard per-axis params**: `acceleration`, `deceleration`, `velocity`, `base_rate`, `steps_per_unit`; state enum On/Off/Moving/Alarm/Fault/Unknown ([same](https://sardana-controls.org/devel/howto_controllers/howto_motorcontroller.html)).
- **Pseudo-motors** transform pseudo<->physical axes via `calc_physical`/`calc_pseudo` (canonical slit gap/offset example) ([users overview](https://sardana-controls.org/users/overview.html)).
- **Taurus model naming** mirrors Tango paths: `motor/icepap/01/state`, `.../position`, `.../velocity`, `.../acceleration`, confirms three-field device path + attribute, with IcePAP as the canonical example ([taurus intro](https://taurus-scada.org/users/introduction.html)).

### ALBA-specific controller/macro naming (from `sardana-alba`)
ALBA's common plugin repo shows its conventions ([sardana-alba](https://github.com/ALBA-Synchrotron/sardana-alba)):
- Pseudomotor controllers: `AlbaBlTripodTablePseudomotor`, `AlbaBlTwoLeggedTablePseudomotor`, `AlbaBlCommonDirectionSlitPseudomotor`, `AlbaBlTwoXStagePseudomotor`, `MoveableMaskPseudomotor`, `TwoCoupledPseudoMotor` (file pattern `AlbaBl<Mechanism>Pseudomotor.py`).
- Counter/timer controllers (pattern `<Vendor/Tech><Function>Ctrl.py`, `CoTi`=Counter/Timer): `LimaCoTiCtrl`, `LimaRoICoTiCtrl`, `LimaTwoDController`, `LimaXspress3CTCtrl`, `AmptekPX5CoTiCtrl`, `FeIORCtrl`.
- Class metadata fields: `gender`/`model`/`organization`/`image`/`logo`, with `organization='CELLS - ALBA'` ([same](https://github.com/ALBA-Synchrotron/sardana-alba)).
- Beamline-specific kinematics are **hardcoded per beamline**: `TripodTableController` hardcodes a 45 degree azimuth at BL22-CLAESS with a "change per beamline" comment ([same](https://github.com/ALBA-Synchrotron/sardana-alba)).
- Cross-control-system seam: **`TangoEpics`** is a generic Tango device server bridging Tango to EPICS PVs (1 PV -> 1 dynamic Tango attribute, via PyEpics Channel Access), evidence Tango is primary and EPICS is foreign at ALBA. Now moved to the Tango community GitLab ([TangoEpics](https://github.com/ALBA-Synchrotron/TangoEpics)).

> **Flag:** Sections of the controls model above (Pool/MacroServer, controller->axis, pseudo-motors, scheme set) are **generic Sardana/Taurus/Tango facts** authored by ALBA but not ALBA-deployment-specific. The `sardana-alba` naming and the BL22 azimuth are **ALBA-specific**.

## 4. Equipment & hardware sources

Hardware evidence is strongest from ALBA's device-server and Sardana-plugin repos; **per-beamline assignment is not published** (see section 8). Vendor/format facts below are flagged where inferred.

**Motion control**
- **IcePAP**, ALBA-designed motor-controller hardware; pure-Python access library `icepap` (renamed from `pyIcePAP`); raw TCP socket, default port 5000; addressing up to 16 racks x 8 drivers (`rack*10 + driver`) ([pyIcePAP/icepap](https://github.com/ALBA-Synchrotron/pyIcePAP); live source [gitlab.com/icepap-organization/IcePAP](https://gitlab.com/icepap-organization/IcePAP)). Config tooling: **IcepapCMS** (config management) + **IcepapOSC** (diagnostics) ([IcepapCMS](https://github.com/ALBA-Synchrotron/IcepapCMS)). Sardana bridge: `sardana-icepap`.
- **Vendor motion plugins**: `sardana-pmac` (Delta Tau PMAC), `sardana-pihexapod` (PI C-887 hexapod, 6 axes X/Y/Z/U/V/W via PIPython + GCS DLL), `smaract` (SmarAct) ([sardana plugin family](https://github.com/orgs/ALBA-Synchrotron/repositories?q=sardana-)).

**Detectors (via the Lima framework)**
- Lima controllers in `sardana-alba`: `LimaCoTiCtrl` (master-axis CounterTimer wrapper over 2D Lima), `LimaRoICoTiCtrl`, `LimaTwoDController`, `LimaXspress3CTCtrl` (Quantum Detectors Xspress3 fluorescence/SDD, vendor *inferred from class name*) ([sardana-alba](https://github.com/ALBA-Synchrotron/sardana-alba)).
- Detector repos/sims: `sls-detector` (SLS Mythen), `eiger-simulator` (Dectris Eiger sim), `hamamatsu` (lib + Lima plugin), `AmptekPX5`/`AmptekPX5DS` (Amptek PX5 MCA), MarCCD/Rayonix macros (`marccdmacros_lib`) ([device-server family](https://github.com/orgs/ALBA-Synchrotron/repositories?q=GaugeController)).
- **Lima upstream is ESRF, not ALBA, and not migrated**, `github.com/esrf-bliss/Lima` is the live canonical library; only ALBA's `sardana-limaccd` plugin is archived/moved ([verification](https://github.com/esrf-bliss/Lima); [sardana-limaccd](https://github.com/ALBA-Synchrotron/sardana-limaccd)).

**Counting / timing / electrometers**
- `sardana-ni660x` (NI 6601/6602 counter cards; most recently active hardware plugin, 2026-04), `sardana-albaem` (ALBA EM#/EM electrometer; README authored by the MAX IV kits team), `sardana-adlink`, `sardana-locum` ([sardana plugin family](https://github.com/orgs/ALBA-Synchrotron/repositories?q=sardana-)).
- Beam diagnostics: XBPM (`xbpm_scan` macro), Bergoz BCM-RF, Libera bunch-by-bunch ([device-server family](https://github.com/orgs/ALBA-Synchrotron/repositories?q=GaugeController)).

**Sample environment / vacuum / power**
- Vacuum (shared `VacuumController` library): MKS/Pfeiffer/Leybold/Axtran/MVC3 gauge controllers, Varian DUAL, Agilent 4UHV, IonPump ([VacuumController set](https://github.com/orgs/ALBA-Synchrotron/repositories?q=GaugeController)).
- Cryo/temperature: `cryocon` (CryoCon M24C), `OxfCryo700` (Oxford Cryostream 700), `julabo`, `linkam`, `NorhofSCPIServer` (LN2) ([same](https://github.com/orgs/ALBA-Synchrotron/repositories?q=GaugeController)).
- Power/bake-out: `BrukerEC_PS`, `BakeOutControlDS` (Elotech) ([same](https://github.com/orgs/ALBA-Synchrotron/repositories?q=GaugeController)).

**MX-specific hardware/software**
- `mxcube`, `HardwareRepository` (MXCuBE back-end), `edna-mx`, `PyCATS` (CATS sample-changer robot) ([ALBA-Synchrotron org](https://github.com/ALBA-Synchrotron)). These name the **MX method**, not one beamline (ALBA runs BL13 XALOC and BL06 XAIRA).

**Data formats**
- NeXus/HDF5 (NXtomo), **Xradia/Zeiss `.xrm`/`.txrm`** (BL09 TXM), SPEC files ([ALBA org findings](https://github.com/ALBA-Synchrotron); [BL09](https://www.cells.es/en/instruments/beamlines/bl09-mistral)). `.xrm`=Xradia/Zeiss format is **independently confirmed** (DOE dxchange docs + ZEISS product line) ([dxchange reader](https://raw.githubusercontent.com/data-exchange/dxchange/master/dxchange/reader.py), [ZEISS XRM](https://www.zeiss.com/microscopy/en/products/x-ray-microscopy.html)). BL09 acquisition is driven by **TXM-XMController** (named in the repo); its attribution to Xradia/Zeiss is **not independently confirmed** ([txmcommands.py](https://github.com/ALBA-Synchrotron/bl09_collect_macros/blob/master/macros_lib/collectlib/txmcommands.py)).

> **Flag:** No org-level per-beamline hardware manifest exists; detector/motion assignment per beamline is **inference** and must be verified ([verification](https://github.com/ALBA-Synchrotron)).

## 5. Operations, experiment & scheduling sources

**Scan / acquisition model (the observe/orchestrate seam).**
- Sardana **Generic Scan Framework**: step scans (`ascan`/`dscan`/`mesh`...), software continuous (`ascanc`/`meshc`), and **hardware-timed continuous fly-scans** (`ascanct`/`meshct`) ([sardana scan source](https://gitlab.com/sardana-org/sardana); [scan docs](https://sardana-controls.org/users/scan.html)). Fly-scan macros are the floor-side equivalent that would remain below a CORA Conductor, paralleling the 2-BM seam.
- **Measurement Group** selects acquired channels (decoupled from the macro); **trigger/gate** synchronizers handle HW vs SW timing ([ICALEPCS 2017, Reszela et al.](https://proceedings.jacow.org/icalepcs2017/papers/webpl06.pdf)). ALBA reported continuous scans giving ~20x speedup over step scans ([same](https://proceedings.jacow.org/icalepcs2017/papers/webpl06.pdf)).
- Typical ALBA beamline deployment: **two Device Pool instances + one MacroServer** per beamline; clients are Taurus GUI + Spock CLI ([same](https://proceedings.jacow.org/icalepcs2017/papers/webpl06.pdf)).

**Data pipeline / NeXus / HDF5.**
- Recorders: `NXscanH5_FileRecorder` (writes the **NXscan** NeXus application definition in HDF5, with write sessions + optional **SWMR**), plus SPEC, FIO, SPS/Shm, JSON/Output ([scan docs](https://sardana-controls.org/users/scan.html)). File layout via `ScanDir`/`ScanFile`/`ScanID`; `PreScanSnapshot` captures device metadata once at scan start ([same](https://sardana-controls.org/users/scan.html)).
- ALBA's documented recommendation: **HDF5 following NeXus conventions**, with SPEC still widely used and custom recorders supported ([ICALEPCS 2017](https://proceedings.jacow.org/icalepcs2017/papers/webpl06.pdf)).
- ALBA customizes NeXus output via **`sardana-nexus`** (NeXus recorder with YAML-configurable application definitions, e.g. `NXmonopd.yaml`) ([sardana-nexus](https://github.com/ALBA-Synchrotron/sardana-nexus)).

**Data catalogue / data-of-record (ICAT).**
- ALBA runs **ICAT** as its data catalogue, branded "ALBA Data Catalogue (ICAT)" at `data.cells.es`; features include an **elogbook**, **DOI generator**, and a **LIMS** for MX ([data portal page](https://www.cells.es/en/users/your-experiment/data-portal)).
- Deployment: ICAT on **Kubernetes since 2023** via the `icat-k8s` Helm chart; **ESRF-developed Data Portal** as UI; data catalogued **preferably in NeXus** ([icatproject ALBA page](https://icatproject.org/collaboration/facilities/alba/)). The ICAT core runs on Payara + MariaDB with `icat.server`, IDS, and authn plugins (`db`/`anon`/`oidc`) plus a custom `es.cells.icat.authn_alba` ([icat-k8s findings](https://github.com/orgs/ALBA-Synchrotron/repositories?q=icat)).
- **PACER** (`icat-pacer`) = event-driven, **RabbitMQ-based** high-throughput ingestion router into ICAT (schema: Investigation/Dataset/Datafile/Sample/Instrument/User), syncing users/proposals from the **User Office System** via `uos_user.sync` / `uos_proposal.sync` routing keys, minting DOIs via **DataCite** (`doi.cells.es`, publisher "ALBA Synchrotron", funder ROR `02j9n6e35`, CC-BY-4.0) ([icat repos findings](https://github.com/orgs/ALBA-Synchrotron/repositories?q=icat); [icat-pacer](https://github.com/ALBA-Synchrotron/icat-pacer)).
- **VISA** = remote data-analysis VM platform (`visa-k8s-cloud-provider-poc`, `visa-cups`), downstream of the catalogue ([icat repos](https://github.com/orgs/ALBA-Synchrotron/repositories?q=icat)).
- **CORA seam implication:** ALBA's data-of-record is ICAT; the clean integration point is **publishing into ICAT the way PACER ingests today** (RabbitMQ -> Investigation/Dataset/Datafile), not replacing ICAT ([icat repos findings](https://github.com/orgs/ALBA-Synchrotron/repositories?q=icat)).

**Data policy.**
- ALBA is data custodian with **>=5-year access guarantee** and a **3-year embargo** (PaN model) before data becomes open ([new data portal news](https://www.cells.es/en/public/news/a-new-data-portal-is-available-for-users)). The 3-year PaN embargo is independently corroborated ([Synchrotron Radiation News / DRAC](https://www.tandfonline.com/doi/pdf/10.1080/08940886.2024.2432816)). A 2017 data-policy PDF exists but sits under a `/deprecated/` path; the current version was not located ([2017 policy PDF](https://www.cells.es/en/users/call-information-1/bases/deprecated/2017_07_data_policy_alba_approved-cr.pdf)).

**User Office / proposals / scheduling.**
- Portal at `userofficesystem.cells.es` for proposal submission, experiment registration, and report submission; **underlying UO software product not identified online** ([UO portal](https://userofficesystem.cells.es/)).
- Review: Peer Review Committee; four criteria (technical feasibility, scientific merit, prior ALBA record, resource availability); grades **A+ (granted) / A (reserve) / B (refused)**; results ~4 months after deadline; proposals are 2000-word + 3-page PDF + 300-word abstract; A+ proposers get a safety evaluation ([apply for beam time](https://www.cells.es/en/users/access/apply-for-beam-time)).
- Calls: **two regular calls/year** (cycle I Jan-Jun, cycle II Jul-Dec; deadlines ~early Sept and late Feb/early March) plus special calls; access modes Standard, BAG, **Rapid Access** (MX, <=3 weeks); MX beamlines run year-round ([call information](https://www.cells.es/en/users/access/call-information)).

## 7. Verified facts (adversarial check)

**Confirmed**
- IcePAP and other vendor controllers are **not** in the main Sardana repo tree; they live in separate plugin repos ([verification](https://gitlab.com/api/v4/groups/sardana-org/projects)).
- BL22=CLAESS and BL04=MSPD mappings ([cells.es list](https://www.cells.es/en/instruments/beamlines)); BL09=MISTRAL ([BL09](https://www.cells.es/en/beamlines/bl09-mistral)).
- No org-level per-beamline hardware manifest on GitHub; only `bl09-*` and `BL22ClearData` carry beamline codes ([verification](https://github.com/ALBA-Synchrotron)).
- `cells.es` is ALBA's authoritative domain (`albasynchrotron.es` 301-redirects to `cells.es`) ([verification](https://www.cells.es/)).
- Sardana repo: 17 release objects vs 62 tags is a real tags-vs-Releases gap ([GitLab API](https://gitlab.com/api/v4/projects/sardana-org%2Fsardana/releases?per_page=100)).
- Taurus 5.4.0 supports PyQt6/PySide6 (Qt6) in addition to Qt5; the getting-started doc naming only PyQt5/PySide2 is outdated ([verified via 5.4.0 CHANGELOG](https://gitlab.com/taurus-org/taurus/-/raw/5.4.0/CHANGELOG.md)).
- Taurus license split: **LGPL for code, CC-BY-3.0 for docs** ([LICENSE.txt](https://gitlab.com/taurus-org/taurus/-/raw/develop/LICENSE.txt)).
- Taurus GitLab "created 2021-03-17" is a migration date; project predates it (GitHub created 2016, v3.4 tag 2015) ([verification](https://api.github.com/repos/taurus-org/taurus)).
- `.xrm` = Xradia/Zeiss format ([dxchange](https://raw.githubusercontent.com/data-exchange/dxchange/master/dxchange/reader.py), [ZEISS](https://www.zeiss.com/microscopy/en/products/x-ray-microscopy.html)).
- `sardana-alba` factual signals (3 stars, no deployment manifest, git-tag-only distribution, not on PyPI) ([verification](https://github.com/ALBA-Synchrotron/sardana-alba); [PyPI 404](https://pypi.org/pypi/sardana-alba/json)).

**Refuted**
- "Framework code moved to GitLab" **does not extend to Lima**, `esrf-bliss/Lima` is the live, non-archived ESRF library, not an ALBA framework component or an archived mirror ([Lima](https://github.com/esrf-bliss/Lima)).
- "Taurus core has an h5file scheme", false; core schemes are `tango`, `epics`, `evaluation`, `resource` ([verification](https://gitlab.com/api/v4/projects/taurus-org%2Ftaurus/repository/tree?path=lib/taurus/core&ref=develop)).
- "Sardana README does not capture specific Python versions", false; `setup.py` records Python 3.5 classifier and version-conditional deps ([setup.py](https://gitlab.com/sardana-org/sardana/-/raw/develop/setup.py)).

**Uncertain**
- **CLEAR = "Core Level Emission Analyzer and Reflectometer"** is sourced only from the `BL22ClearData` README (not independently corroborated), and the spectrometer is **currently "not available"** per cells.es ([BL22](https://www.cells.es/en/beamlines/bl22-claess), [BL22ClearData](https://github.com/ALBA-Synchrotron/BL22ClearData)).
- **TXM-XMController** is named in the BL09 repo, but its attribution to Xradia/Zeiss is **not independently confirmed** ([txmcommands.py](https://github.com/ALBA-Synchrotron/bl09_collect_macros/blob/master/macros_lib/collectlib/txmcommands.py)).
- `sardana-alba` "Only tested with LIMA CORE 1.7" / saving-format are **code comments/defaults, not a verified runtime config** ([LimaRoICoTiCtrl.py](https://github.com/ALBA-Synchrotron/sardana-alba/blob/master/sardana_alba/ctrl/LimaRoICoTiCtrl.py)).
- Whether `sardana-alba` is deployed **beamline-wide** vs. a shared library some beamlines draw from, its self-description is "Common Sardana plugins for ALBA"; no deployment evidence either way ([verification](https://github.com/ALBA-Synchrotron/sardana-alba)).

> **Integrity note:** multiple fetched pages (cells.es beamline pages, GitHub API outputs) contained **injected fake "system-reminder"/"MCP Server Instructions" blocks**. These were prompt-injection attempts in third-party content and were ignored; they did not affect any fact above.
