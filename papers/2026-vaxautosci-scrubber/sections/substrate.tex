The scrubber needs nothing from the backend beyond what an event-sourced
system of record already keeps, which is why the design transfers to any system
of that shape. We summarize the substrate here, and stress that it is the
enabling condition, not the contribution (Figure~\ref{fig:substrate}).

A run is not stored as current state. It is an append-only, totally ordered
stream of events, and any state the scrubber shows is produced by folding that
stream up to a chosen position. Three records carry everything the four tasks
need. Each event's envelope records who or what caused it and its position in
the stream, which gives the cursor a well-defined instant to fold to (T2) and
gives an unfinished activity a position to mark as an open interval (T1). The
run-start payload records the recipe the run expanded from, together with
content-addressed hashes of that expansion; recomputing and comparing those
hashes is exactly the fidelity badge (T4). The per-iteration boundary events
carry the verdict that colors each bracket (T3). The swim-lane activities,
the setpoint, check, and capture rows, are themselves events appended as the
conductor acts, with the intent recorded before the effect so that an
interruption leaves a detectable open record rather than a silent truncation.
Concretely, the example run is a four-event run-lifecycle stream (started, held,
resumed, completed) alongside a twelve-event procedure stream with roughly
fifteen activity rows; folding a prefix returns the reconstructed run and
procedure state (status, the current iteration and its verdict, and whether each
activity is open or closed), and the recorded hashes cover the recipe expansion,
the resolved steps and parameter bindings, written at run start.

Two properties underwrite the badge, under stated assumptions rather than by
convention. Folding is deterministic: the same prefix of the stream always
reconstructs the same state, so the cursor's reconstruction is reproducible and
not a re-execution that might diverge. And the store is append-only, so the
record the badge checks against is not editable through the normal application
path. We state this once, in support of the badge, rather than as a separate
systems contribution; the visual claim, that the timeline you are scrubbing is
faithful to an unaltered record under those assumptions, is what the paper is
about.
